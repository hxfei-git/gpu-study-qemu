1. 概述¶

Host 上的应用准备输入和 AQL 包，由原生 RV64 CP 取包、解析 Kernel 描述对象并启动 RV64 计算执行器。用户访存先完成 GPUVM 翻译和权限检查，再按页属性读写 dcache 或直接访问存储；CP 在结果可见后发布 Signal 和 IH 通知。

本手册按协议版本 7 描述以下硬件接口：

  • PCIe 配置空间、BAR0 控制寄存器、BAR2 VRAM、BAR4 Doorbell 与 MSI-X 中断。
  • CP 复位与访存窗口、HQD 驻留队列、AQL 分发和 Signal／IH 完成路径。
  • GPUVM 上下文、四级页表、组相联 TLB、同步失效和每槽首次故障。
  • 设备级共享 dcache、页缓存属性、维护命令，以及 BAR2／DMA 的旁路维护。
  • VRAM／Outbound 物理路由和 Host↔VRAM DMA。
  • 逐 Lane 推进的 SIMT 执行模型、启动 CSR 和 RV64 计算指令子集。

先沿 3.1 节理解提交与访存路径，再查 BAR0 总览。GPUVM 与 TLB 见第 17 章，Outbound 见第 18 章，dcache 见第 19 章。组件版本要求见 PROTOCOL_V7.md；构建、运行命令和验证结果只在软件栈说明维护。

2. 文档约定¶

2.1 数值与端序¶

  • 以 0x 开头的数值为十六进制，其余数量和状态编号为十进制；超过 4 位的十六进制数按 4 位分组，如 0x1001_8000，下划线不改变数值。
  • 地址均为 字节地址（byte addressable）。
  • 所有多字节寄存器访问均按 小端序（little-endian） 解释。

2.2 术语¶

  • 未定义（undefined）：实现可以产生任意结果；软件不得依赖其行为。
  • 实现定义（implementation-defined）：实现必须在某处给出选择；若未给出，软件仍不得依赖。
  • R / W / R/W / W1C：分别表示只读、只写、可读写、写 1 清除；W1C 位写 0 不改变状态。表中复位值指设备冷复位或 GLOBAL_CTRL.RESET 后的值，单独 CP 复位的影响另行列出。

3. 系统架构¶

3.1 顶层框图¶

下面是逻辑访问路径，不表示物理布局。例子采用默认 GPUVM 开启、2 GiB VRAM；Host 已建立页表并发布一个 AQL 任务。箭头表示提交、地址翻译或存储访问。

Host CPU / Linux 应用
  ├─ 准备输入与 AQL 包，保证写入可见
  ├─ BAR0 → 配置 CP、HQD、GPUVM、IH、Outbound 与缓存维护
  ├─ BAR2 → 读写 VRAM；DMA 引擎 → Host↔VRAM 搬运
  └─ BAR4 Doorbell → 提示 HQD 有工作 → 原生 RV64 CP 取包
                                      → 分发 → RV64 计算执行器

CP 用户窗口 / 计算执行器 → 用户地址、VMID、源槽、读／写／取指操作
  ├─ gpuvm=on：GPUVA → GPUVM
  │     ├─ TLB 命中 → 取得物理页、权限与页缓存属性
  │     └─ 未命中 → 四级页表遍历 → 缓存叶子翻译
  │     命中或遍历成功后 → 检查本次权限 → GPU 物理地址 + WB / DEVICE
  └─ gpuvm=off：检查用户保护区与路由 → GPU 物理地址 + DEVICE
                         ↓
统一访存入口（翻译、权限与范围检查完成后）
  ├─ WB 数据读写 → 设备共享 dcache，命中时直接读写缓存行
  │                  └─ 未命中：必要时回写旧脏行，再回填新行
  ├─ DEVICE 数据读写 → 回写并失效重叠行 → 直接读写后备存储
  └─ 取指 → 直接读取后备存储，不查 dcache
                         ↓（需要访问后备存储时）
GPU 物理路由：按物理地址选择存储
  ├─ VRAM → 设备本地后备 RAM
  └─ Outbound → Host IOVA → PCIe DMA → 系统 IOMMU（启用时）→ Host RAM

CP 管理窗口、页表遍历、IH、BAR2、DMA
  └─ GPU 物理地址 + DEVICE → 同一访存入口（DMA 维护两端后搬运）

计算终态 → CP 读取结果并 ACK → 回写全部脏行 → Signal → 通知槽 → IH
         → INVALID Header → 消费进度；Host 复查 Signal 后读取结果

TLB 保存“用户页映射到哪里、允许怎样访问”，dcache 保存翻译后物理行中的数据。可缓存数据先取翻译结果，再按物理地址查找数据；两种缓存各有独立维护接口，见 17.5 节。CP 自身的固件取指、全局变量和栈走VRAM 的原生 RAM 别名，不走图中的用户访存路径；其使用边界见 10.4 节和 19.5 节。

3.4 双进程的 BAR、DMA 与中断路径¶

[DESIGN] A57 Linux 运行在进程 A，通过 vfio-user-pci 访问进程 B 的 gpu0。进程 B 使用 gpgpu-cp machine，保存设备寄存器、GPUVM／TLB、dcache、VRAM 和中断状态，运行原生 RV64 CP 与 RV64 计算执行器。CP 由 TCG 执行，默认保持复位；任务经 AQL 队列交给 CP，DMA 引擎负责存储拷贝。

进程 A：A57 Linux
  └─ PCIe 设备代理
       ├─ 配置空间、BAR0/BAR2/BAR4 请求 ─→ 进程 B：GPGPU
       ├─ PCI DMA 接口 ←─ B 的读写请求       ├─ RV64 计算执行器
       │    └─ SMMUv3（启用时）→ Host RAM    └─ 原生 RV64 CP
       └─ Linux 驱动 ←─ 完成与错误中断            └─ 共用 GPUVM、dcache 与物理存储

none 与 smmuv3 都使用 x-dma-via-socket=on：B 把设备 DMA 地址、方向和数据请求发送给 A，A 调用该 PCI 设备的 DMA 接口，并返回数据或错误。SMMUv3 的翻译、权限检查和故障记录保留在 A。该启动选项只选择通信方式，不增加硬件寄存器。

BAR 访问通过消息转发，MSI-X 表和屏蔽状态在两端同步。Signal 完成通过 IH 通知；DMA 完成和错误事件沿相应向量传给 A 的 Linux 驱动。DMA 继续同步搬运数据，并通过原定时器报告完成。本版不支持断线重连和迁移。

4.3 MMIO 访问规则¶

  • BAR0 寄存器采用小端、4 字节对齐的 32 位访问。64 位地址由低、高两个寄存器保存，完整地址为 (HI << 32) | LO；不得用一次 64 位访问代替两次寄存器访问。
  • BAR2 VRAM 支持 1～8 字节访问。BAR4 Doorbell 的访问规则见 11.5 节。
  • 表中标记为保留的位必须写 0；读值及非法访问的处理以各寄存器组的规定为准。
  • 落在单一寄存器子区域内的 BAR0 非法宽度或未对齐访问不更新目标寄存器，读返回 0，并置位 ERROR_STATUS.INVALID_CMD。IH 区域还记录 PROTOCOL 故障。HQD 和 CP 本地入口的权限见各节。
  • CP 控制窗口可读取 GPUVM 控制组、分发、IH、dcache 和全局错误；只允许写入固件握手、分发、IH_SUBMIT 和 dcache 命令参数。GPUVM 故障组与 Outbound 不向 CP 开放；越权访问读零或忽略写入，并锁存 ERROR_STATUS.INVALID_CMD。HQD 和访存窗口另有独立本地入口，见 4.4 节。
  • BAR0 已实现组内的保留偏移按各组规定处理；未映射的 BAR0 背景区读零、忽略合法宽度的写入。未映射的 CP 本地地址产生访存异常，HQD 槽号不截断或折返。

[BOUNDARY] BAR0 由多个子区域组成。跨子区域边界的非对齐 8 字节访问可能被 QEMU 拆成两次 4 字节访问；软件必须使用规定的对齐 32 位访问，不能依赖跨区访问的原子性或统一拒绝行为。

4.5 GPU 物理存储映射

用户地址经 GPUVM 翻译或直通检查后，得到 32 位 GPU 物理地址。统一访存入口按访问类型处理缓存，需要访问后备存储时再按下列布局路由；缓存与取指的分流见 3.1 节。默认 2 GiB VRAM 下：

[0x0000_0000, 0x8000_0000)     VRAM
[0x8000_0000, 0x1_0000_0000)   Outbound → Host IOVA → PCIe DMA

上述 VRAM 范围是物理存储范围，不表示用户可访问全部字节。用户域在两种 GPUVM 状态下均不能访问 VRAM 首页及固定固件区 [0x7fc0_0000, 0x8000_0000)；GPUVM 开启时还逐页检查权限。管理域不使用这些用户页权限，软件负责防止用户对象映射驱动页表和其他管理存储。

VRAM 与 Outbound 在 0x8000_0000 边界相邻，两段均为半开区间。Outbound 未使能或路由范围非法时，用户访问记 GPUVM 故障，CP 管理域访问记队列错误，DMA 置 DMA_FAULT。窗口配置与换算见第 18 章。RV64 CP 自己的代码、栈和寄存器仍按 4.4 节的 CP 本地地址解释。

6.5 软复位行为¶

Host 写 GLOBAL_CTRL.RESET = 1 后，设备按依赖顺序处理：

  1. 先检查物理在途访问；非零时整体拒绝，锁存 INVALID_CMD，不做部分复位。
  2. CP 保持复位，执行器停止并释放当前任务，不再产生新访问。
  3. 在 Outbound 与后备存储仍有效时，回写并失效全部 dcache 行。回写失败则停在此步：失败行仍有效且脏，DCACHE_FAULT 保持锁存，已停止的 CP 与任务不自动恢复；此前成功的维护不回退。
  4. 维护成功后，清空 GPUVM 上下文、TLB、故障及统计，复位 HQD、Doorbell、IH、分发、DMA、中断和全局状态；Outbound 停用，dcache 命令与统计清零。

成功后 GLOBAL_STATUS = READY、DISPATCH_STATUS = IDLE，CP 继续保持复位，启动入口和访存窗口清零，VRAM 内容保留。单独 CP 复位见 10.5 节；冷复位的丢弃边界见 19.4 节。

7.5 IH_SUBMIT 与记录发布

CP 在固件私有 VRAM 的 0x7fc0_0000～0x7fff_ffff 内准备一条 32 字节、小端记录，起始偏移至少按 8 字节对齐，整条记录必须位于该范围内。先保证记录内容可见，再将起始偏移写入 IH_SUBMIT。写操作同步返回；CP 随后读取 LAST_SUBMIT_RESULT，此时可复用临时缓冲区。

记录内偏移位宽含义
0x0032类型：1 = SIGNAL_NOTIFY，2 = QUEUE_ERROR，3 = DEVICE_ERROR。
0x0432HQD 槽号：SIGNAL_NOTIFY 为 2～3；QUEUE_ERROR 为 0～3；DEVICE_ERROR 为 0xffff_ffff。
0x0864完整 MQD 物理字节地址，至少按 8 字节对齐；DEVICE_ERROR 填 0。
0x1032类型 1：非零事件编号；类型 2：CP_HQD_ERROR 编号 1～10；类型 3：必须为 GPGPU_ERR_FIRMWARE（bit 4），否则按 RECORD 错误拒绝；设备只锁存 FIRMWARE。
0x14～0x1f96保留，填 0。

令 N = IH_SIZE / 32，记录地址为 IH_BASE + (IH_WPTR mod N) × 32。WPTR、RPTR 均按模 2^32 推进，不是字节偏移。(WPTR − RPTR) mod 2^32 = N 时 Ring 满，设备拒绝新记录，不覆盖未消费记录；写入失败不推进 WPTR。

设备先完整写入记录，再发布 WPTR，最后置位 IH 中断。Host 读取发布进度并同步后消费记录，再写回 RPTR；新 RPTR 的前进量不能超过尚未消费的记录数。更新 RPTR 后，向 IRQ_ACK 的 bit 2 写 1；若 Ring 仍非空，IH 位立即重新置位并再次通知。ACK 不推进 RPTR，也不清除 IH 故障；重新使能 IH 中断时，非空 Ring 同样产生通知。

8.2 编程模型¶

CP 在 IDLE 时写入代码入口及长度、参数地址及长度、Grid/Block 尺寸和源队列标识，最后向 DISPATCH 写 1。设备保存配置与当前 GPUVM 状态，校验通过后进入 BUSY；校验失败直接进入 FAILED。

CP 从 24 字节 Kernel 描述对象提取代码与参数配置：偏移 0x00 为 64 位代码入口，偏移 0x10 的 kernel_abi_version 必须为 7，偏移 0x14 保留字段必须为 0；其他版本或非零保留字段被拒绝。描述对象和参数均使用所属用户地址空间。

执行器分段推进任务，同一个 Warp 继续执行时保留寄存器、PC 和启动状态。计算及相关访问结束后发布 DONE 或 FAILED。CP 读取结果并写 ACK 后，执行器才接受下一任务；缓存回写和完成通知的顺序见第 13 章。

参数基址至少按 8 字节对齐，代码和参数的完整范围都必须低于 248，GPUVM 关闭时超出 4 GiB 的地址在物理入口路由失败；无参数任务也提供 4 字节占位参数。各轴 Grid/Block 尺寸必须非零，每组最多 1024 个线程，最多 4096 个工作组，实际线程总数最多 65536；未使用轴填 1，SHARED_MEM_SIZE 填 0。

CP 的低地址映射到相同偏移的 VRAM。末尾 4 MiB，即 [0x7fc0_0000, 0x8000_0000)，保留给 CP 固件；入口为 0x7fc0_0000，最后 64 KiB 为栈，初始 sp = 0x8000_0000。Host 经 BAR2 装载固件，写入入口并确认存储可见后解除复位。完整分区与分配约定见 CP/MEC 规格第 3.1 节。

10.5 复位范围与固件替换

CP 单独复位保留 VRAM、启动入口、HQD、IH、DMA、分发、中断、GPUVM 上下文、TLB，以及 dcache 的数据与统计；只清零 CP 访存窗口配置和 GPUVM 固件握手。已有计算任务继续由执行器推进，队列资源仍须按原流程卸载。设备整体复位见 6.5 节。

替换固件前须确认相关计算和访存已结束，再保持 CP 复位并读回确认、装载固件、设置入口、保证写入可见，最后解除复位。仅观察到 RESET_HOLD = 1 或 HQD ACTIVE = 0 不能证明队列资源已可释放。

11. 队列寄存器（HQD 与 Doorbell）

设备保存 4 组 HQD，每组占用 0x100 字节地址范围：槽 0 为 KIQ，槽 1 为 HIQ，槽 2、3 为用户 AQL 队列。全部寄存器为 32 位，小端且按 4 字节对齐；设备整体复位时清零，单独 CP 复位保留。

每次完整写入 8 字节；宽度、对齐或高 32 位非法时，拒绝通知并置位 ERROR_STATUS.INVALID_CMD。读取返回 0，不保存可供读回的通知值。只有激活且 Doorbell 已使能的匹配 HQD 才接收通知；没有匹配项时不改变队列状态。

12. Warp/Lane 只读启动 CSR

计算线程启动时已经取得代码入口和参数地址，接下来用 CSR 读取自己的坐标与工作规模。每次创建新 Warp 时，执行器保存共享启动状态，再填写各有效 Lane 的线程坐标、PC、mhartid 和 a0：

新 Warp → startup_sgpr[9]：blockIdx、blockDim、gridDim，各含 X/Y/Z
       └→ 每个有效 Lane 的 startup_vgpr[3]：threadIdx.x/y/z
                  └→ CSRRS 只读 → 写入目标通用寄存器

同一 Warp 分段续跑：保留启动状态
下一个 Warp 开始：重新填写启动状态

这些启动值与 Kernel 可覆盖的通用寄存器分开保存。目标通用寄存器被改写后，再次读取 CSR 仍得到原来的值。坐标按 X 维变化最快的顺序计算，gridDim 保存 Block 数量。例如 blockDim 为 (8, 4, 1) 时，组内线性线程 10 的 threadIdx 为 (2, 1, 0)。

12.1 CSR 编号与访问规则

CSR 编号名称读取内容

0xCC3～0xCC5BLOCK_ID_X / Y / Z当前 Warp 所属 Block 的网格坐标。

13. 完成顺序与同步边界

执行器进入 DONE 或 FAILED 时，线程已经停止访问内存，结果写入可能仍保存在 dcache 脏行中。当前固件先取走执行结果，再把数据写回后备存储，最后按成功或失败路径发布通知：

执行器 DONE / FAILED
  → CP 读取并保存状态和错误 → DISPATCH_ACK = 1
  → DCACHE_CMD = CLEAN | ALL（0x05）→ 检查 DCACHE_STATUS
       ├─ 执行成功且回写成功
       │    → Signal = 0 → 通知槽 → IH → INVALID Header → 消费进度
       └─ 执行失败或回写失败
            → 记录 EXECUTOR 队列错误，不发布成功 Signal

Host 读到 Signal = 0 → 完成读取屏障 → 读取结果
释放队列及存储 → 还需排空并确认队列卸载

回写成功保留干净缓存行，后续任务可以继续命中。执行失败也先回写，失败前已完成的写入保留；回写失败时仍脏的行留在缓存内，不能据此归还存储。ACK 只确认执行结果，内存屏障只约束访问顺序，两者都不执行缓存维护。CPU 准备下一次输入的交接见 19.5 节。

当前执行器不提供组间或跨 Warp 屏障。旧 BAR0 的 THREAD_MASK、BARRIER 和线程身份教学寄存器已移除，线程身份统一通过第 12 章的 CSR 获取。

14.4 Warp 执行规则¶

  • 每轮依次推进所有活跃 Lane 各一条指令；各 Lane 保存独立 PC。
  • Lane 遇到 ebreak 时退出，对应 active_mask 位清零。
  • 当 active_mask == 0 时 Warp 执行结束。
  • 每 Warp 最多执行 100,000 轮，各分段累计计数，超出后任务报 BUDGET 错误。

shared_fetch=on 时，调度器仍要按 Lane 编号推进这一轮，只把同 PC 的取指与字段译码结果复用。例子中四个 Lane 属于同一 Warp、使用同一用户地址空间，代码已发布并在任务期间保持稳定；指令 A 写入各 Lane 自己寄存器中的值，指令 B 读取共同变量 x：

本轮执行顺序          取指与字段译码                 当前 Lane 的动作
Lane0，PC=0x1000  →  首次取指 A，检查 EXEC 与范围  →  写 x=7
Lane1，PC=0x1020  →  首次取指 B，检查 EXEC 与范围  →  读 x，得到 7
Lane2，PC=0x1000  →  复用 A 的静态字段             →  写 x=9
Lane3，PC=0x1020  →  复用 B 的静态字段             →  读 x，得到 9
本轮结束         →  丢弃 A、B；下一轮重新取指

不能先执行整个 A 组再执行 B 组，否则两次读取都会得到 9。寄存器、PC、CSR、动态舍入、浮点异常和退出标记始终由各 Lane 独立保存；若 Lane1 失败，Lane0 已完成的写入保留，Lane2/3 不再执行。

共享表不跨轮、分段、Warp 或 Dispatch 保留，不形成长期 icache。任务完成并按发布约定替换代码后，下一任务重新取指。执行期间自改代码、经别名回写代码或改写在途页表不受支持；仅把代码映射为 RX，不能证明不存在可写别名。关闭共享时保留逐 Lane 取指路径。

包含张量块指令的一轮仍按相同 Lane 顺序执行。调度器在整轮完成后提前让出本段，累计轮数预算保持不变；CP 仍要等整个 Dispatch 及其收尾完成，才选择其他队列。指令范围见第 15.4 节。

14.5 GPU 核心内存地址空间¶

计算线程的 a0 直接保存 64 位派发参数地址：GPUVM 开启时为高 16 位清零的 GPUVA，关闭时为 GPU 物理地址。当前用户库选择参数块 CPU 映射地址的数值作为 GPUVA，这一选择不改变硬件的翻译过程。参数、整数与浮点数据以及取指均经过用户访问入口；数据读写在权限检查后按页属性经过或绕过 dcache，取指走独立分支。物理路由见4.5 节。

GPUVM 开启时，0x8000_0000 和 0x9000_0000 都是普通 GPUVA。关闭时，两者只按 VRAM／Outbound 布局解释。线程坐标从 CSR 读取，参数按普通内存处理，只有派发与取指保留声明范围检查。

计算线程的 GPU 地址空间与 CP 的本地地址空间分别解释。CP 本地 0x8000_0000 窗口仍然存在，不对应计算线程的特殊页面。

15.4 有界张量块指令（自定义）¶

[DESIGN] Kernel 已拿到矩阵输入、权重、scale 和输出的 GPU 地址，需要算出完整输出。张量扩展让一个 Lane 处理有界的数据块，减少重复的标量索引和访存请求；参数读取、输入读取和结果写回仍经过用户访存。它使用项目自定义编码，不是标准 RISC-V 向量扩展，也不代表 MI300X 的硬件指令。

以 X[128,896]、INT8 权重 W[128,896] 和 FP32 scale[128] 计算 C[128,128] 为例。命令前缀保存这些 GPU 地址及 M=128、N=128、K=896；一个工作项负责至多 8 行、32 列，沿 K 每次推进至多 32 项：

Lane 的 GPR：命令 GPU 地址、线性工作块号、K 起点
  → 读固定参数前缀，核对维度、块号、K 起点及地址计算
  → 用户访存：读取本条块使用的 X、W、scale、旧 C 与末块 bias
  → 有界局部数组：W8 逐项乘 scale，再逐 K 执行 FP32 FMA
  → 用户访存：按实际连续行写回 C
  → Kernel 推进 K，完成本工作块后 EBREAK

本例：M/N 工作块 = ceil(128/8) × ceil(128/32) = 64
      每工作块的 K 指令数 = ceil(896/32) = 28
      单条上限 = 8 × 32 × 32 = 8192 MAC

15.4.3 访存、异常与宿主优化边界

指令先读完当前有界块的全部输入，再计算和写回。Linear/BMM 按 M 行写回；Conv 按输出通道写回各自连续的空间片段。输入读取失败不写输出；后行写回失败保留前行，当前行跨页失败也可能已写入一部分。首次故障仍归属派发的源槽，执行器返回 MEMORY，由 CP 按原队列错误协议收尾，不发布成功 Signal。

地址计算检查乘加溢出及元素对齐。只有逐项证明地址确实相邻时才合并访问，不跨 stride 空洞，不因块访问大于 8 字节就放宽 FP32／INT64 的元素对齐。GPUVM 开启时继续检查页权限和缓存属性；关闭时继续检查物理范围、首页和固件保护及 Outbound 路由。

tensor_native=off 使用逐次清局部异常的 SoftFloat 路径。开启后，仅在宿主支持 AVX2/FMA、输入与每一步结果均为正规有限值或零、且只出现允许的 inexact 时接受 SIMD 结果；否则从原部分和完整重算。SIMD 只在独立 N 输出之间并行，不重排单个输出的 K 顺序。尝试前保存宿主浮点环境，临时设 RNE、关闭 FTZ/DAZ，退出前恢复；失败尝试的结果和异常不提交给 Lane。该路径不调用模型框架或 CPU 参考程序。

17. GPUVM 上下文与地址翻译

CP 从用户 HQD 取得 VMID，计算执行器从任务快照取得相同的 VMID 和源槽。GPUVM 用这些信息翻译用户地址、检查本次权限，并把失败记到源槽。设备属性 gpuvm=on/off 在启动时固定，默认开启；两种状态均沿同一 AQL／CP／Signal 路径提交和完成。

源 HQD / 任务快照 → VMID 1 或 2、用户地址、READ / WRITE / EXEC
  ├─ GPUVM 开：GPUVA → TLB 或四级页表 → 物理页、权限、UNCACHED
  │                         → 检查本次权限 → GPU 物理地址 + 页属性
  └─ GPUVM 关：GPU 物理地址 → 检查保护区与路由 → DEVICE
                                  ↓
                    统一访存入口 → 按 3.1 节读写缓存或后备存储
                                  └─ 失败 → 源槽首次故障

关闭 GPUVM 时不创建页表，也不提供用户页权限隔离；队列仍保存 VMID 和源槽。管理访问由显式访问域指定，始终使用 GPU 物理地址，不能用 VMID == 0 代替访问域判断。

下面寄存器均采用对齐的 32 位小端访问。组内未定义偏移读零，非法寄存器写入保留目标配置并锁存全局 INVALID_CMD；开启模式下 VM_INV_REQ 的请求内容非法是例外，只通过 ACK 报错，见 17.2 节。关闭模式下仍可读版本、模式、握手和故障，Host 的页表配置及失效写入均被拒绝并锁存 INVALID_CMD。

设备在写 VM_INV_REQ 的同一次寄存器访问内完成失效并发布 ACK，没有异步忙状态。RANGE = 0 时忽略 START／END，清除所选 VMID 的全部 TLB 项；RANGE = 1 时只清闭区间 [START, END] 内的 VPN。范围寄存器先保存完整写值，在执行范围请求时才检查是否为有效 36 位范围。

例如 START = 0xf_fff8_a400、END = 0xf_fff8_a402、REQ = 0x0001_0002，清除 VMID 1 中 GPUVA 0x0000_ffff_8a40_0000～0x0000_ffff_8a40_2fff 的翻译；ACK 必须恰为 0x2。同时失效两个 VMID 的全部翻译时写 REQ = 0x6，成功 ACK 也是 0x6。

请求含保留位（包括 bit 0）、VMID 位图为空，或范围请求的 START 大于 END、END 不小于 236 时，整体拒绝，不清除任何 TLB 项；ACK 更新为 0x8000_0000，不另锁存全局错误。此规则只适用于 GPUVM 开启时已进入失效器的请求，不能套用于关闭模式或越权写入。

上下文未启用或所属 HQD 激活都不妨碍失效。设备持主锁同步执行，清除时没有进行到一半的翻译，也没有旧遍历随后填回；ACK 只确认翻译失效的完成范围，映射与资源的使用边界见 17.5 节。三个 TLB 计数全设备共用、32 位回绕，统计口径也见该节。

17.3 页表格式与访问检查

GPUVA 有效 48 位，位 63..48 必须为零，分为 L0 根目录索引 [47:39]、L1 目录索引 [38:30]、L2 目录索引 [29:21]、L3 叶表索引 [20:12] 和页内偏移 [11:0]。每张表占 4 KiB，64 位小端表项共 512 个。页表根保存 GPU 物理地址；各级表项的地址域按 SYSTEM 换算成 GPU 物理地址。遍历经公共物理入口读取表页，不递归经过 GPUVM 翻译。

位名称PDEPTE
0VALID下级目录有效目标页有效
1SYSTEM1：地址域为 Host IOVA，GPU 物理页为 0x8000_0000 + IOVA；0：地址域为 VRAM 偏移
2UNCACHED必须为 01：这一页的数据访问按 DEVICE 处理，不进入 dcache；0：按 WB 缓存
4 / 5 / 6EXEC / READ / WRITE必须为 0分别允许取指、读取、写入

其余位保留包括 bit 63:32；有效项中必须为 0，非法编码报页表错误。

地址掩码为 0xffff_f000。SYSTEM=1 时整页须落在 2 GiB IOVA 窗口内，例如叶子项 0x4100_2000 | SYSTEM | VALID | R | W 得到 GPU 物理页 0xc100_2000；SYSTEM=0 时整页须落在 VRAM 内并避开首页和末尾固件区，当前 2 GiB 配置的普通 VRAM 区间为 0x1000～0x7fbf_ffff。地址域与 SYSTEM 不符报页表错误，例如不带 SYSTEM 的 0xc100_2000。换算后的页同样由公共物理入口路由，Host 页要求 Outbound 已使能。软件负责保证表页不作为用户 BO 映射。SMMUv3 开启时，Outbound 得到的 IOVA 继续由系统 IOMMU 翻译。

UNCACHED 只在叶子项有效，目录项带它报页表错误。遍历把它与权限一起交给 TLB，TLB 命中时同样给出；跨页访问每页使用自己的属性。GPUVM 关闭时没有页表，用户数据访问一律按 DEVICE 处理。WB 与 DEVICE 的行为见 19.3 节，属性的传递见 GPUVM 规格第 3.2.1 节。

权限只取自叶子项，分别检查本次 EXEC、READ 或 WRITE；EXEC 和 WRITE 都不隐含 READ。无效表项报 UNMAPPED，有效项的保留位或地址编码非法报 TABLE，权限不足报 PERMISSION。本版只支持 4 KiB 页，不提供大页、中间级叶子或缺页重放。

用户入口先检查上下文和完整地址范围。长度不超过 8 字节的标量只接受自然对齐的 1／2／4／8 字节访问；更长的块传输可跨页，逐页检查目标与权限。翻译失败不尝试物理地址；后页失败保留前面已经完成的写入，不自动重试或回滚。

[BOUNDARY] 当前驱动把可分配 GPUVA 限定为 [0x1000, 0x1_0000_0000_0000)，用户库以对象的 CPU 映射地址作 GPUVA；这是软件分配策略，硬件没有单独禁止 GPUVA 零页。硬件只识别 VRAM 首页与固定固件区这两类物理保护范围，不能识别任意管理表页；驱动负责防止用户映射页表及其他管理存储。软件对象与绑定规则见 GPUVM 规格。

故障组基址为 0x0a00 + HQD 槽号 × 0x40，四组独立。访问入口携带源槽；每槽只保存首次错误，后续错误不覆盖。下面字段复位均为 0：

故障记录器只保存首次记录，不直接发中断。CP 窗口失败向固件返回访存异常，执行器失败交由 CP 收尾；固件再沿源队列错误和 IH 路径通知 Host。可归属的用户故障停止源队列，另一 VM 仍可继续运行。

恢复前先确认旧任务访问与通知已结束，读取并保留原队列故障，再清除空闲源槽的记录。CLEAR 只清寄存器，不补页、恢复指令或重放任务，也不清 HQD 错误；队列的重建与资源归还由驱动完成。整体复位清除上下文、TLB、三个计数、故障、ACK、VPN 范围和固件握手；CP 单独复位见 10.5 节。

17.5 TLB 查找、替换与映射更新

TLB 是全设备共享的 64 组 × 4 路缓存，共 256 项，只保存叶子翻译。以 VMID 1 读取 GPUVA 0x0000_ffff_8a40_0568 为例，叶子项映射到 VRAM 页 0x0123_4000，允许读写且 UNCACHED 清零：

GPUVA = 0x0000_ffff_8a40_0568
  ├─ VPN = GPUVA >> 12 = 0xf_fff8_a400 → 组号 VPN % 64 = 0
  └─ 页内偏移 = 0x568

TLB 第 0 组：比较各有效路的 (VMID = 1, VPN = 0xf_fff8_a400)
  ├─ 命中 → 取出物理页 0x0123_4000、R/W、WB
  └─ 未命中 → 按页表根读取四级表项 → 填入相同翻译
                         ↓
                 检查本次 READ 权限
                         ↓
       GPU 物理地址 = 0x0123_4000 + 0x568 = 0x0123_4568
                         ↓
               WB 数据请求 → dcache（第 19 章）

VMID 不参与选组，但参与标签比较。另一个 VMID 使用相同 GPUVA 时，可能竞争同组容量，不能命中 VMID 1 的翻译。TLB 项同时保存已换算的 GPU 物理页、R/W/X 权限和 UNCACHED 属性；命中后仍检查本次权限，再交给数据或取指路径。

每组按 True LRU 维护 MRU 到 LRU 的使用顺序。命中时将该路移到 MRU；未命中时同步遍历页表，遍历成功后优先填入编号最小的无效路，没有空路才替换 LRU 路。新项成为 MRU；失效只清有效标记，不改变使用顺序或清零统计。

HITS 和 MISSES 按每次页翻译查找计数，EVICTIONS 只计成功填入新翻译时替换有效项。权限检查在翻译查找之后，因此权限失败也可能已经命中、填入或替换 TLB；随后后备存储访问失败也不撤销翻译。计数不能当作成功访存次数，GPUVM 关闭时不产生这些查找。

修改映射的硬件操作顺序是：确认旧任务不再使用目标范围，写入新表项并保证可见，按 17.2 节请求失效并核对 ACK，然后允许新访问。TLB 失效只处理翻译，不回写或失效 dcache；dcache 命令也不改变 TLB。缓存属性改变、物理存储归还或 IOVA 映射撤销之前，还须完成 19.5 节的数据交接。失效 ACK 不证明任务完成或对象已经可释放。

18. Outbound 物理路由与窗口配置

Host 对象取得 IOVA 后，通过 GPU 物理地址 = 0x8000_0000 + IOVA 交给设备。公共物理入口先检查完整范围，再选择 VRAM 或 Outbound；Outbound 用窗口基址还原 IOVA，交给 PCIe DMA。

GPU_BASE       = 0x8000_0000（固定，与 vram_size 无关）
HOST_IOVA_BASE = 0
WINDOW_SIZE    = 0x8000_0000（2 GiB）

Host IOVA 0x4100_0000 → GPU 物理地址 0xc100_0000
设备访问 0xc100_0000 → 减去 GPU_BASE → IOVA 0x4100_0000 → PCIe DMA

IOVA 0 对应 GPU 物理地址 0x8000_0000，位于 Outbound 起点。驱动的 31 位 DMA mask 正好覆盖窗口对应的 2 GiB IOVA。窗口覆盖只说明路由存在，Host 存储或 IOMMU 映射缺失时访问仍会失败。所有范围与末端计算使用 64 位数，GPU 物理地址空间末端为 0x1_0000_0000（4 GiB）。

18.2 配置确认与停止条件

Host 在 CP 启动前读回核对基址和长度，再写 CONTROL 使能并确认 ACK。合法 CONTROL 写入把最近结果更新为 ACK；向布局、STATUS、未定义偏移写入，或 CONTROL 写入含保留位／不满足停止条件时，保留原配置，把结果更新为 ERROR，并锁存全局 INVALID_CMD。ACK 与 ERROR 保存最近一次结果，不使用 W1C；BUSY 在读取时反映全设备公共物理事务的在途计数，不只统计 Host 访问。

窗口由全设备共用，创建 BO、Queue 或切换进程时均不修改。写 CONTROL 要求 CP 保持复位、所有 HQD 停用、执行器和 DMA、IH 不忙且物理在途计数为零；基址和长度始终只读。停止时先确认设备访问已经结束，才能关闭窗口或重新初始化。关闭窗口前，设备先回写并失效窗口内的 dcache 行；回写失败时窗口保持打开，状态置 ERROR。CP 单独复位保留窗口；设备整体复位恢复上述初值并停用。

19. dcache 数据缓存

CP 用户窗口或计算线程读写数据时，先完成 GPUVM 翻译和权限检查；页属性为 WB 才进入设备共享的 dcache。数据容量固定为 32 KiB，64 字节行，4 路组相联，因此共有 128 组、512 条缓存行；组内使用 True LRU，采用写回和写分配。

缓存以 GPU 物理地址为标签，不含 GPUVA 或 VMID；不同映射落到同一物理行时读写同一份数据。VRAM 和 Outbound 内的 Host 数据均可缓存；Host 行存活期间，其 IOVA 映射必须保持有效。下面继续使用 17.5 节翻译得到的物理地址：

GPU 物理地址位   31 ........ 13 | 12 ..... 6 | 5 ..... 0
用途                  Tag       |    组号    |  行内偏移
位数                   19       |     7      |     6

0x0123_4568 → 行起点 0x0123_4540，组号 0x15，Tag 0x91a，行内偏移 0x28

控制器在组内比较有效标记与 Tag。命中后读写指定字节，写入置脏，并将该路移到 MRU。未命中先选编号最小的无效路；没有空路时替换 LRU 路，旧行脏则先整行回写，再读入新行。写未命中也先回填整行，保留本次未改写的字节；失败前完成的其他行不回滚。设计理由与替换过程的展开见 dcache 规格第 4 节。

19.3 访问类型：WB 与 DEVICE

用户数据的缓存属性只有页表这一来源。GPUVM 开启时，叶子项 UNCACHED 清零得到 WB，置位得到 DEVICE；TLB 缓存并返回同一属性，发起方不能把 DEVICE 改为 WB，编码见 17.3 节。GPUVM 关闭时没有叶子项，用户数据全部按 DEVICE 处理。页表遍历、CP 管理域、IH、BAR2 和 DMA 本来使用物理地址，也固定为 DEVICE。

WB 按本章开头的规则读写缓存。DEVICE 不分配行：入口先回写并失效请求范围重叠的行，再按请求宽度直接读写后备存储。这样，DEVICE 读取能取得旧脏行中的新数据，部分写入也不会被之后的旧行回写覆盖；维护失败就不开始原始读写。取指走独立分支，通过代码范围与执行权限检查后读取后备存储，不查 dcache、不自动回写代码行。

WB 用户访问中的回填或替换回写失败，沿本次用户访问保存 GPUVM 的 STORAGE 故障。显式或 DEVICE 旁路维护中的回写失败还锁存 DCACHE_FAULT，失败行继续有效且脏；清全局错误位不代替重试维护。DEVICE 只描述本设备“不缓存、同步访问后备存储”的行为，不复现 Arm Device 内存类型的排序与合并规则。

19.4 旁路访问与复位

BAR2、DMA、IH、页表遍历与 CP 管理域都按 DEVICE 访问，按 19.3 节先回写并失效重叠的行；维护失败时不开始这次访问。

  • BAR2：读失败返回 0；写失败时丢弃本次写入。成功的写入只改变请求的字节。
  • DMA：源、目的两端都回写并失效重叠的行；失败时 DMA_STATUS 置 ERROR，不拷贝。见 9.4 节。
  • Outbound 关闭：先回写并失效窗口内的行，见 18.2 节。
  • 整体复位：停止 CP 与执行器后回写并失效全部行，再复位各模块。GLOBAL_CTRL.RESET 回写失败时复位停止，见 6.5 节。
  • 设备冷复位（QEMU 系统复位或 vfio-user 设备复位）：同样先回写；回写失败时丢弃剩余的行并继续复位，随后清零 VRAM。写不回去的 Host 脏行随之丢失。

CP 固件在任务终态后的维护和通知顺序见第 13 章。本版不实现 icache、多级缓存、自动跟踪 CPU 写入的一致性协议或缓存周期时序；QEMU 原生 CP 的 TCG 翻译状态不属于本设备的 icache。

19.5 CPU／GPU 数据交接与代码发布

CPU 与 GPU 按整条缓存行交接可缓存对象，不能同时修改同一行的不同字节。以上一次任务已成功发布 Signal 的 Host 参数块为例，CP 已完成回写，CPU 接下来准备新参数：

确认上次任务结束、脏数据已回写
  → CPU 改写参数块
  → 对参数块范围执行 INVALIDATE，确认 STATUS = OK
  → 保证输入与包体先于有效 Header 可见，再写 Doorbell
  → GPU 读参数时重新回填，取得本次输入
  → 任务完成与结果回写按第 13 章执行

不能先让 CPU 覆盖数据，再回写 GPU 的旧脏行，否则旧行会覆盖 CPU 的新字节。Ring、共享进度、Signal 和通知页持续由 CPU／CP 交替访问，必须使用不可缓存映射；其他需要 CPU 直接修改的可缓存对象按上图交接。驱动和用户库的对象标志与 CACHE_SYNC 接口见 dcache 规格第 6 节，不向应用开放任意物理范围维护。

物理存储归还分配器或 IOVA 映射撤销前，要先确认相关任务与通知已结束，再回写并失效旧物理范围；维护失败时保留存储。自定义 CP 固件绕过访存窗口、通过原生 RAM 别名访问可缓存对象时，也须先完成交接，硬件不强制隔离这条路径。

若通过 WB 数据写入生成代码，执行前先回写对应 dcache 脏行，再保证代码发布顺序；取指不替软件做这次维护。BAR2 或 DMA 上传代码时由旁路维护处理旧缓存副本。本版不支持执行期间修改自身代码。

# QEMU Camp Tutorial

QEMU Camp Tutorial 是 QEMU 训练营的在线技术文档，聚焦 C/Rust 语言与 QEMU 虚拟化/模拟器技术的深度结合，旨在通过系列技术博客、代码示例、原理解析，帮助开发者理解 QEMU 内部机制（如设备模拟、内存虚拟化、中断处理等），并掌握用 C/Rust 开发 QEMU 组件、优化 QEMU 模块的方法。​

无论是虚拟化领域初学者、C/Rust 技术实践者，还是开源爱好者，都能从本项目中获取 QEMU 底层原理的清晰解读与 C/Rust 落地实践的参考案例。

## 本地开发

项目已经提供 `Makefile`，常用命令如下：

```bash
make setup   # 自动创建 .venv，并安装 Python / Node 依赖
make format  # 自动修复中文排版
make serve   # 自动使用 .venv 启动本地预览
make build   # 构建站点
```

make mdlint    # 默认只检查当前改动过的 Markdown 文件
make mdformat  # 默认只修复当前改动过的 Markdown 文件

make mdlint MD_FILES="README.md CONTRIBUTING.md"

make help
