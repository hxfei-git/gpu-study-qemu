本文审查第三阶段（协议版本 4）的核心设计：统一访存、GPUVM、DRM/GEM 固定存储和 CSR 启动信息，并与 AMD 的实现逐项对照。主线是一项向量加法从准备内存、提交队列到完成和释放的过程；各节围绕面试可能问到的问题，说明两侧怎样实现、教学设备省去了哪些环节，以及简化带来的限制。第 4 节沿对象寿命展开 Linux 驱动的内存管理；缺陷的根因放在相关章节，修法和改进草案集中在第 9 节。

阅读时要区分三类内容：第 2～8 节描述固定基线中的实现；D1～D7 指出其中的缺陷或限制；第 9 节提出尚未确认、也尚未实现的修法与升级方案。草案中的“应当怎样做”不能当作当前设备已经具备的能力。

本文只维护与 AMD 的差异分析、缺陷和改进草案。本设备已确认的设计以 [GPUVM 第一版规格](<./GPUVM 第一版规格.md>)、[CP/MEC 第一版规格](<./CP_MEC 第一版规格.md>) 为准，草案经确认后转入规格；构建与运行结果见[软件栈第 5 节](../software/gpgpu/README.md#build-and-validation)。

### 1.2 贯穿例子：一次向量加法经过的路径

应用计算 `Z[i] = X[i] + Y[i]`，共 17,003 个 `float`。Host CPU 负责准备数据和提交任务，GPU Kernel 读取 X、Y 并写 Z。本文对照的 AMD 环境是外部 Host CPU 加 MI300X 独立 GPU；本设备则由 QEMU 模拟，不把它的简化设计当作 MI300X 的硬件行为。

下面的地址是示例取值，与 GPUVM 规格中的例子一致：X 的 GPUVA 为 `0x0040_0000`，后备存储放在 VRAM 偏移 `0x0020_0000`；参数块（kernarg）放在 Host 内存，IOVA 为 `0x4100_2000`。参数块内保存 X、Y、Z 的 GPU 地址和元素数，Kernel 先读参数，再按数组地址访存。Ring 保存 AQL 包，进度对象保存提交与消费位置，Signal 保存任务完成值；这些共享对象也放在 Host。每个 VM 的通知页固定在 GPUVA `0xffff_f000`，用于中断到达后定位等待事件。

下图只比较执行路径，不表示两侧使用相同的地址编码、页表格式或硬件布局。

```text
本设备（gpuvm=on）
应用 → lib/rt → lib/kmt → DRM 驱动：BO_CREATE 分配存储，MAP 写页表，QUEUE_CREATE 装载队列
  → 应用写 AQL 包，8 字节写 Doorbell
  → RV64 CP：按管理域（GPU 物理地址）读 MQD，按队列的 VMID 读 Ring 与描述对象
  → RV32 执行器：CSR 给出线程坐标，a0 = kernarg 的 GPUVA，LW/SW 经 GPUVM
  → GPUVM：TLB（64 组 × 4 路）→ 三级页表 → GPU 物理地址
  → 公共物理入口：VRAM；或 Outbound（0x8000_0000 + IOVA）→ PCIe DMA → Host 内存
  → CP 依次写 Signal、通知槽、IH 记录 → 驱动唤醒等待者

AMD（MI300X）
应用 → HIP/ROCr → libhsakmt → KFD/AMDGPU：分配 BO，用户态选 GPUVA，驱动写页表
  → 应用写 AQL 包，写 Doorbell
  → MEC：用 VMID 0 读 MQD，用队列的 VMID 读 Ring
  → CU 上的 Wave：SGPR/VGPR 预置启动信息，按 GPUVA 访存
  → UTCL1 → UTCL2（含 PDE 缓存）→ 四级页表 → 物理地址
  → HBM；或 PTE 中的 DMA 地址 → PCIe（经 IOMMU）→ Host 内存
  → 完成信号原子递减，写事件槽，IH 记录带 PASID → KFD 唤醒等待者
```

两条路径的骨架相同：队列提交、CP 取包、执行单元访存、多级页表翻译、完成通知。差别集中在地址宽度、地址空间身份、映射何时可以修改，以及驱动怎样管理存储，后面各节分别展开。

### 1.3 评审结论

1. **翻译主路径与 AMD 的基本组织相同。** 两侧都按 VMID 选择页表根，用多级页表建立映射，用 TLB 缓存叶子翻译，并通过 REQ/ACK 确认失效；SYSTEM 位都用于区分显存与系统内存。本设备 PTE 的 VALID、SYSTEM、X、R、W 位还沿用了 AMDGPU 的位位置。这里相同的是这些对象的关系，不是完整硬件格式。主要简化是 32 位地址、固定 Outbound 窗口和只有两个用户 VMID，见[第 2 节](#review-address)、[第 3 节](#review-identity)。
2. **最大的语义差异在“什么时候可以改映射”。** AMD 允许队列运行时修改映射，靠 fence 和 TLB 刷新保证安全；本设备在队列存活期间冻结整个 VM，并依靠模拟器主锁让同步失效成立，见[第 5 节](#review-tlb)。
3. **驱动内存采用固定存储模型。** 对象创建时就分配连续存储，之后不迁移、不驱逐；AMD 用 TTM 管理放置与迁移，用 `dma_resv` 中的 fence 和 KFD 的 eviction fence 协调搬移与释放。固定模型的代价是按 2 的幂取整造成浪费、页表页不回收，以及结果未知时只能长期保留资源，见[第 4 节](#review-driver-memory)。
4. **有 3 个缺陷应优先修复**：MAP 失败后驱动与用户库状态不一致（[D1](#item-d1)）；卸载被 CP 拒绝后队列和 VMID 一直被占用（[D4](#item-d4)）；同一运行时连续派发时事件被复用，等待退化为忙循环，故障只报超时（[D7](#item-d7)）。
5. **最值得做的改进**是队列存活期间允许修改映射（[A2](#item-a2)）。VMID 已改为在队列驻留时绑定；引入 PASID（[A1](#item-a1)）和 TLB 分层（[A3](#item-a3)）主要用于对齐 AMD 的结构，按兴趣安排。

待优化项分三类：D 为缺陷，A 为对齐 AMD 的设计升级，E 为后续扩展。优先级 P0 表示影响状态一致或资源回收、应在版本 4 内先修；P1 是第四阶段候选；P2 是改进项；P3 是后续扩展。完整列表见[第 9.4 节](#review-index)。

## 2. 地址翻译与物理地址空间

面试可能问：一个 GPUVA 怎样变成物理地址？GPU 怎样访问主机内存？

### 2.1 AMD：四级页表，系统内存页直接填 DMA 地址

MI300X 上的 Kernel 已拿到 X 的 GPUVA，访存单元还需要知道“这次访问属于哪个地址空间”。队列携带的 VMID 选择页表根；TLB 未命中时，页表遍历器（Walker）从这个根开始逐级查表。

固定 Linux 基线为 GC 9.4.3 选择 48 位 VA、最多四级页表，默认路径为 PDB2 → PDB1 → PDB0 → PTB；VM 大小和块大小还可以用模块参数调整。前三层目录项指向下一张表，最后一层 PTE 指向实际数据页。每级用 9 位索引，一张表有 512 项，每项 8 字节，正好占一页 4 KiB。以 X 的 GPUVA `0x0040_0000` 为例：

```text
VMID → 页表根
  → PDB2[0]   GPUVA[47:39] = 0，找到 PDB1
  → PDB1[0]   GPUVA[38:30] = 0，找到 PDB0
  → PDB0[2]   GPUVA[29:21] = 2，找到 PTB
  → PTB[0]    GPUVA[20:12] = 0，取得数据页地址和属性
  → 数据页地址 + GPUVA[11:0]（本例偏移为 0）→ 访问 X[0]
```

PTE 需要回答三个问题：这一页是否有效、允许什么访问、实际存储在哪里。VALID 在 bit 0，执行／读／写权限在 bit 4～6；SYSTEM（bit 1）决定地址字段指向显存还是系统内存，SNOOPED（bit 2）和 MTYPE（bit 57～58）描述缓存与一致性属性。本例采用普通本地 BO 的默认属性和普通系统内存属性：

```text
X 在 HBM：
  PTE.addr = vram_base_offset + BO 在显存中的偏移
  SYSTEM = 0，MTYPE = RW（本地 BO 的默认缓存类型）

kernarg 在系统内存：
  PTE.addr = 该页的 DMA 地址（启用 IOMMU 时为 IOVA）
  SYSTEM = 1，SNOOPED = 1，MTYPE = UC（不缓存）
```

MTYPE 的 `RW` 是缓存类型的名称，和 PTE 中独立的读、写权限不是一组位。后文还会用到 FRAG（bit 7～11，连续片段信息）和 PDE-as-PTE（bit 54，让目录项直接映射大页）；其他位的完整定义留在下面的源码索引中，本文不展开与评审主线无关的功能。

系统内存对象的每一页分别填写自己的 DMA 地址。因此，连续的 GPUVA 可以映射到一组分散的系统内存页，不要求整个对象的 DMA 地址连续。

内核的 VMID 0 另有地址窗口和 GART：FB 窗口把一段 MC 地址线性对应到显存；AGP 窗口把一段 MC 地址线性对应到系统总线地址；GART 则通过页表映射分散的内核对象。前两者做线性换算，GART 做分页翻译，作用不要混在一起。在固定基线的 GC 9 路径上，AGP 默认关闭，只有 `amdgpu_agp=1` 时才启用。用户 VMID 通过自己的页表访问系统内存，不依赖 VMID 0 的这些窗口。

### 2.2 本设备：三级页表与固定 Outbound 窗口

本设备同样先按 VMID 找根，但 GPUVA 只有 32 位，固定使用三级页表：`[31:30]` 选择根表中的 4 个有效位置，`[29:21]`、`[20:12]` 分别选择下级表的 512 项，`[11:0]` 是页内偏移。同一个 `0x0040_0000` 的三级索引是 0、2、0。各张表仍占 4 KiB，根表中未用到的项也不挪作他用。

叶子项沿用 AMDGPU 的部分位位置：VALID 为 bit 0，SYSTEM 为 bit 1，X/R/W 为 bit 4/5/6，地址字段为 `[31:12]`。沿着 X 和 kernarg 两个对象，可以看清地址字段怎样变成设备最终访问的地址：

```text
X 的第 0 页：PTE = 0x0020_0000 | VALID | R | W = 0x0020_0061
  SYSTEM = 0 → 地址字段是 VRAM 偏移
  → GPU 物理页 0x0020_0000 → 公共物理入口 → VRAM

kernarg 页：PTE = 0x4100_2000 | SYSTEM | VALID | R = 0x4100_2023
  SYSTEM = 1 → 地址字段是 Host IOVA 0x4100_2000
  → 加 Outbound 起点：GPU 物理页 = 0x8000_0000 + 0x4100_2000 = 0xc100_2000
  → 公共物理入口识别为 Outbound，减去 0x8000_0000
  → IOVA 0x4100_2000 → vfio-user DMA → Host 内存
```

SYSTEM 在解释 PTE 时使用；公共物理入口只接收换算后的 GPU 物理地址，再按地址范围选择 VRAM 或 Outbound。因此，Host 页的 PTE 填 `0x4100_2000`，不能把已加窗口起点的 `0xc100_2000` 再填进去。页内偏移在翻译后保留：读取 `X[3]` 的 GPUVA 是 `0x0040_000c`，最终访问 VRAM 偏移 `0x0020_000c`。

GPU 物理空间也是 32 位：`[0, vram_size)` 为 VRAM，`[vram_size, 0x8000_0000)` 为不可路由的空洞，`[0x8000_0000, 0x1_0000_0000)` 为 2 GiB 的 Outbound 窗口。这是**翻译后的地址布局**；GPUVM 开启时，GPUVA 的相同数值并不自动代表 Outbound，仍须先查页表。

页表遍历、CP 管理域访问和 DMA 引擎也走这个公共物理入口，但它们本来就使用 GPU 物理地址，不再按用户 VMID 翻译。具体规则见 [GPUVM 规格第 3.2、3.3 节](<./GPUVM 第一版规格.md#gpuvm-addresses>)。

### 2.3 取舍与代价

**地址宽度。** 32 位 GPUVA 来自 RV32 执行器：寄存器和参数块中的地址字段都是 32 位，三级页表已经能覆盖 4 GiB。代价是每个 VM 最多 4 GiB，也没有大页；AMD 的 PDE-as-PTE 和 FRAG 都不存在。

**系统内存怎样接入。** AMD 的 SYSTEM PTE 直接保存 DMA 地址，固定基线的 DMA 地址能力是 48 位。本设备只定义了 32 位 GPU 物理空间，并把其中的高 2 GiB 留作 Outbound；PTE 中的 IOVA 因而要先加窗口起点，才能交给公共物理入口。**[INFERENCE]** 只看“线性地址换算”这一功能，它最接近 AMD VMID 0 的 AGP 窗口。但 AMD 的 AGP 只服务内核上下文，且默认关闭；本设备的管理域和用户 SYSTEM 页都依赖 Outbound，不能据此把两种完整访存路径视为相同。

这个布局带来两个限制：

- Host 对象的**完整 DMA 地址区间**必须落在低 2 GiB，驱动因此设置 31 位 DMA mask。DMA mask 限制的是设备能够发出的 DMA 地址。`IOMMU=none` 时，DMA 地址直接对应客体物理地址，超过这个地址范围的内存不能用于分配；启用 SMMUv3 时，限制的是 IOVA，背后的物理页可以位于更高地址。
- 管理域没有 GART，不能把分散的存储页拼成连续的管理地址。每个管理对象必须占一段连续的 GPU 物理地址；Host 对象对应连续 IOVA，不一定对应连续物理页。管理对象也不通过用户页表隔离。

**缓存属性。** 本设备没有模拟 GPU 数据缓存，VRAM 访问直接读写后备存储，Host 访问通过一致性 DMA 内存完成；因此没有 MTYPE、SNOOPED 的选择，也没有需要在完成时回写的 GPU 脏缓存。代价是无法演示 AMD 为显存选择 RW、为普通系统内存选择 UC 的一致性取舍。这里省去的是缓存维护，应用仍须遵守“先准备数据、再发布任务，先确认完成、再读结果”的访问顺序。

**`gpuvm=off` 只用于调试。** 关闭翻译后，用户 Kernel 可以访问 VRAM 首页和固件区以外的全部 VRAM，以及整个 2 GiB 的 IOVA 窗口。在当前的验证配置（1 GiB 客体内存、`IOMMU=none`）下，这包括全部客体内存，也包括 MQD、管理 Ring 和 IH。AMD 没有对应的模式：用户访问一律经过页表。

## 3. 地址空间身份：VM、VMID、PASID 与队列绑定

面试可能问：多个进程怎样隔离？VMID 只有 16 个，进程更多时怎么办？

### 3.1 AMD：PASID 是身份，VMID 只是硬件槽位

进程可以长期保留 GPU 内存和页表，硬件却只有有限的翻译上下文。AMD 因而把“地址空间属于谁”和“当前占哪个硬件槽”分开：

- **PASID 是稳定身份。** 在这里讨论的 KFD 进程路径中，它在进程地址空间存续期间保持不变。IH 记录携带 PASID，驱动据此找进程，也能以 PASID 为目标发起 TLB 失效。
- **VMID 是可复用槽位。** 它是硬件上下文寄存器组的下标，该组保存当前页表根和控制状态。每个 hub 有 16 个 VMID，0 留给内核；MI300X 对应的纯计算 GPU 路径中，KFD 从 VMID 3 开始使用。一个进程暂时不占槽位时，软件 VM 和页表仍可保留。

下面先用**非 HWS 模式**说明绑定过程：进程在该设备上的第一条队列创建时，KFD 分配 VMID，建立 PASID 与 VMID 的对应，写页表根并刷新 TLB；最后一条队列销毁时归还编号。没有空闲 VMID 时，这条路径不能仅靠已有页表就让新队列驻留。

**HWS 模式**把驻留调度交给 CP 固件。`MAP_PROCESS` 包携带 PASID、页表根和 SH_MEM（着色器访存环境）配置，固件安排当前驻留进程使用的 VMID。在支持的调度范围内，进程可以轮流驻留，因此进程总数可以多于同时可用的槽位数。不要把这种轮换能力套到非 HWS 路径上。

```text
AMD（非 HWS）
进程 P：PASID 0x8001 → amdgpu_vm（页表根在显存）
  第一条队列创建 → allocate_vmid：取空闲 VMID 9，建立 PASID 0x8001 ↔ VMID 9，写根，刷新 TLB
  MQD.cp_hqd_vmid = 9 → CP 用 VMID 9 访问 Ring、rptr、wptr
  最后一条队列销毁 → 归还 VMID 9；VM 与页表仍在，PASID 不变
```

CP 访问队列时也分两种上下文：读 MQD 使用 `CP_MQD_CONTROL` 中的 VMID（驱动保持为 0），访问用户 Ring 和 rptr/wptr 使用 `CP_HQD_VMID`，也就是队列所属的 VMID。

### 3.2 本设备：VMID 随队列驻留绑定，没有 PASID

本设备以一个 DRM 文件上下文为一个会话，每个会话有一个软件 VM；它不是按进程号全局合并 VM。首次 MAP 建好根表和通知页时，VM 还不占硬件槽。建队列时驱动才借用用户 VMID 1 或 2，把页表根装入对应上下文，并把编号写入 MQD。队列确认卸载后归还 VMID，软件 VM、页表和已绑定对象继续保留，绑定时机接近 AMD 非 HWS 模式。

CP 必须先读到 MQD，才知道访问用户 Ring 时应使用哪个 VMID，所以它的访存分两条路径：管理域用于 MQD、管理 Ring 和 IH，直接使用 GPU 物理地址；用户域用于用户 Ring、描述对象、Signal 和通知槽，按 MQD 中的 VMID 翻译。每次访问前，CP 在本地窗口中显式设置访问域和 VMID，不根据 `VMID == 0` 猜地址含义。`gpuvm=off` 时仍借用一个用户 VMID 管理队列来源，但不启用页表翻译。

以下流程以 `gpuvm=on` 为例：

```text
本设备
DRM 文件 A：VM_A（页表根在 VRAM）
  第一次 MAP → vm_init()：建根表和通知页；不取 VMID，不失效
  QUEUE_CREATE → gpgpu_vm_attach()：取 VMID 1 → 写根 → 失效整个 VMID → 启用上下文
  MQD.vmid = 1 → CP 窗口按 VMID 1 访问 Ring
  QUEUE_DESTROY 确认卸载并消费旧 IH → gpgpu_vm_detach()：停用 → 失效整个 VMID → 清根 → 归还 VMID 1
  VM_A 与页表仍在；下次建队列时取到的可能是 VMID 2
```

TLB 的标签只有 VMID 和虚拟页号，不知道同一编号前后属于不同 VM。假设 VM_A 和 VM_B 都使用 GPUVA `0x0040_0000`，VMID 1 从 A 交给 B 时，旧 TLB 项若还在，B 就可能命中 A 的存储。因此驱动取得和归还编号时都失效整个 VMID；归还前还要消费旧 IH，避免迟到通知被误认成新队列的通知。

当前 MAP、UNMAP 只能在没有存活队列时执行。正常情况下，此时 VM 已不占编号，旧翻译也已在归还时清除，所以 `vm_invalidate_range()` 直接返回，只修改页表。下次建队列再写根、整体失效并启用上下文。

驱动用两个字段区分软件准备状态和硬件驻留状态：`vm->ready` 表示通知页已建立，开启 GPUVM 时还包括根表和通知页映射；`vm->vmid` 表示当前占哪个槽，0 表示未占用。`ready = true`、`vmid = 0` 是正常状态，表示映射已准备好，但没有队列驻留。设备和固件只要求装载时 MQD 对应的上下文已经启用，因此这次绑定时机调整不需要修改设备、固件或协议。

### 3.3 取舍与代价

VMID 改为驻留时借用以后，页表根、TLB 标签、MQD 和故障记录仍然使用同一个编号，驱动不需要维护 PASID 到 VMID 的映射表。剩下的取舍有以下几点：

- **VM 的数量不再受 VMID 限制，同时驻留的队列仍然最多 2 条。** 用户 HQD 槽和用户 VMID 都是 2 个，每个 VM 最多一条队列，两个上限相等，VMID 不会成为额外瓶颈；三个进程轮流建队列的例子见 [GPUVM 规格第 5.1 节](<./GPUVM 第一版规格.md#gpuvm-context-tlb>)。AMD 每个 hub 有 16 个 VMID，HWS 模式下还能由固件轮换，进程数可以远多于槽位。
- **每次建队列、卸载队列都失效整个 VMID。** 队列重新驻留后，TLB 中没有本 VM 的翻译，要重新遍历页表。AMD 重新绑定 VMID 时同样要刷新。本设备的队列通常跑完一批任务才卸载，这部分开销可以忽略。
- **记录中没有独立的稳定地址空间编号。** IH 仍用 MQD 地址定位源队列，驱动能由队列找到会话，所以现有通知路由不受影响。但故障记录中的 VMID 只说明当时用了哪个槽；同一编号会先后属于不同会话，脱离队列和绑定时序就无法判断来源。按地址空间发起失效时，也要先找到它当前借用的槽位。AMD 的 PASID 提供了独立于槽位的身份。
- **GPU 翻译和系统 IOMMU 翻译使用不同上下文。** VMID 选择 GPU 页表；KFD 的 PASID 标识进程地址空间。系统 IOMMU 则按设备请求中的 StreamID 及可选 SubstreamID／PCIe PASID 选择自己的上下文，不能把 GPU VMID 直接当作 IOMMU 的编号。本设备启用 SMMUv3 时，设备共用一个 StreamID，不为各 VM 发送 PCIe PASID：GPU 页表先把 GPUVA 映射到 Host IOVA，SMMUv3 再把 IOVA 映射到客体物理页。[A1](#item-a1) 拟加入的稳定编号也只用于 GPU 侧记录，不自动增加 PCIe PASID 传递能力。

对应改进：[A1 引入 PASID](#item-a1)。

## 4. Linux 驱动的内存管理

面试可能问：驱动怎样分配 GPU 能用的内存，怎样建立映射？GPU 可能还在访问时，怎样安全地释放？显存不够时怎么办？

本节沿向量加法里两个对象的寿命，把驱动的内存代码逐段讲清：X 是放在 VRAM 的数组，kernarg 是放在 Host 的参数块。每一段先讲本设备，再讲 AMDGPU 的对应做法。

### 4.1 阅读顺序与对象寿命总图

驱动中与内存有关的代码，建议按下面的顺序读：

1. `gpgpu_drv.h` 的文件头，以及 `struct gpgpu_bo`、`struct gpgpu_vm`：对象关系、引用种类和锁的顺序；
2. `gpgpu_bo.c`：对象创建、句柄关闭、CPU 映射和 COPY；
3. `gpgpu_vram.c`：用 gpu_buddy 管理的 VRAM；
4. `gpgpu_dev.c` 中的 `gpgpu_dma_buf_alloc()`：Host 内存的分配和 Outbound 地址换算；
5. `gpgpu_vm.c`：页表、MAP/UNMAP、VMID 的取得与归还、会话清理；
6. `gpgpu_drm.c` 中的 `gpgpu_postclose()`：文件关闭时能否回收，不能回收时转为 orphan。

先分清三个动作：BO_CREATE 取得后备存储，MAP 为这份存储建立 GPU 地址绑定，建队列才让设备使用这个 VM。关闭 GEM 句柄只撤销应用查找对象的一个入口；对象是否释放，还要看绑定、mmap 等引用是否结束。下面以 `gpuvm=on` 沿两个对象的寿命展开：

```text
               X（VRAM，68,012 字节）                       kernarg（Host，16 字节）
BO_CREATE      buddy 分配 0x2_0000 字节连续块并清零           dma_alloc_coherent 一页并清零
               phys_addr = VRAM 偏移，例如 0x0020_0000        phys_addr = 0x8000_0000 + IOVA
               引用：会话列表、GEM 句柄                       引用：会话列表、GEM 句柄
准备内容       COPY：设备 DMA 从 Host 暂存对象搬入            mmap 后 CPU 直接写（mmap 再持一个引用）
MAP            写 17 个叶子 PTE                               写 1 个带 SYSTEM 的叶子 PTE
               取得绑定引用                                   取得绑定引用
               VM 还不占 VMID，不发失效
建队列         取得 VMID 1：写根 → 失效整个 VMID → 启用上下文
队列存活       整个 VM 冻结：BO_CREATE、MAP、UNMAP 都返回 -EBUSY
卸载队列       停用上下文 → 失效整个 VMID → 归还 VMID 1
UNMAP          清叶子 PTE → 放下绑定引用（不占 VMID，不发失效）
关闭句柄、munmap、会话关闭 → 最后一个引用放下 → bo_free() 归还存储
```

### 4.2 对象模型、引用与锁

**本设备。** BO 管“哪份存储还活着”，VM 管“某个 GPUVA 应找到哪份存储”。下面是只保留本节核心成员的简化定义，用于说明关系，不是完整源码摘录：

```c
struct gpgpu_bo {
	struct drm_gem_object gem; /* GEM 引用计数保护对象寿命。 */
	u64 size;                 /* 应用请求的字节数。 */
	u64 mapped_size;          /* 向上对齐到页的映射长度。 */
	u64 phys_addr;            /* 固定存储的 GPU 物理地址。 */
	u64 gpu_addr;             /* MAP 后提供给 Kernel 的地址。 */
	bool bound;               /* 是否持有 GPU 绑定。 */
	u32 permissions;          /* GPU 访问权限。 */
	u32 users;                /* 队列基础对象或 COPY 的占用计数。 */
};

struct gpgpu_vm {
	u32 vmid;                 /* 当前借用的槽位；0 表示未借用。 */
	u32 root;                 /* 页表根在 VRAM 中的偏移。 */
	bool ready;               /* 通知页及所需页表已经建立。 */
	bool failed;              /* 禁止继续修改或建队列。 */
};
```

完整 BO 还记录 Host／VRAM 种类，以及 `host` 或 `vram_blocks` 中的存储信息。对 X 来说，`phys_addr` 一直是 VRAM 偏移 `0x0020_0000`，MAP 后的 `gpu_addr` 是 `0x0040_0000`；GPUVA 映射把二者联系起来。`gpuvm=off` 时没有页表，但仍建立绑定并持有引用，此时 `gpu_addr` 使用固定的 `phys_addr`。

对象寿命由四类长期引用保护：会话列表、GEM 句柄、GPU 绑定和 CPU mmap。它们都增加 GEM 对象的引用计数，最后一个引用结束时才调用 `bo_free()` 归还存储。例如应用先关闭 X 的句柄，绑定引用仍在，X 的页表目标就不会提前被分配给别人。Host 对象即使已经解绑，只要 CPU mmap 还在，也不能归还存储。

`users` 解决的是另一个问题：**现在能否撤销绑定**。队列占用 Ring、进度对象，或 COPY 正在使用对象时，计数非零，UNMAP 必须拒绝。它不逐项追踪任意 Kernel 的参数和数组；X 的绑定在计算期间不能撤销，目前靠的是整个 VM 的冻结规则。

并发由设备级 `dev->lock` 保护对象状态，外层 `vm_serial` 把建队列、MAP、UNMAP 等会改变 VM 使用状态的操作串行化。等待设备完成时会释放 `dev->lock`，否则 IH 处理无法取得这把锁，等待者也就收不到完成。释放内层锁期间，仍需要外层串行化防止另一个线程建立队列或修改映射。

创建 GEM 句柄还有一个独立的竞争点：`drm_gem_handle_create()` 返回前，句柄已对其他线程可见，另一个线程可能立即关闭它；关闭回调 `bo_close()` 又需要 `dev->lock`。所以创建方先取临时对象引用，再解锁创建句柄，重新加锁后检查对象是否已被关闭。解锁避免回调死锁，临时引用保证对象在这段时间不会被释放。

**AMDGPU。** AMDGPU 把存储和映射分开得更细。`amdgpu_bo` 内嵌 TTM 的 `ttm_buffer_object`，TTM 对象再内嵌 GEM 对象；GEM 管对象寿命与用户接口，TTM 管当前存储位置以及搬移。BO 记录首选域、允许域（VRAM、GTT 等）和 placement（放置约束），因此可以在允许的域之间迁移。

```text
VM 的区间树 → 某段 GPUVA 映射 → amdgpu_bo_va → BO → TTM 当前存储

```

同一个 BO 因而可以在不同地址建立多段映射。`amdgpu_bo_va` 的 `queue_refcount` 非零时，说明队列基础资源还在使用这份映射，不能解除；它也不是每次 Kernel 访存的计数。KFD 再用 `kgd_mem` 管理计算内存对象及其在各 GPU 上的映射。

后文反复出现的 **fence** 是异步操作的完成凭据：操作尚未结束时，依赖它的一方等待；操作结束后 fence 被置为完成，也可以携带错误。比如 SDMA 搬运 X 后返回一个 fence，下一步必须等它完成，才能按新位置使用 X。fence 本身不搬数据，也不直接修改页表。

内存对象的同步以 reservation 为单位：BO 的 `dma_resv` 同时提供锁和 fence 容器，VM 的页表 BO 共享根目录的 reservation。锁使用 ww_mutex 协议；一次操作要取得多个对象锁时，用同一个 ww_acquire 上下文协调冲突，必要时退让重试，避免互相等待形成死锁。这部分内存管理不靠一把覆盖所有会话的设备级大锁。

### 4.3 存储从哪里来

**本设备。** BO_CREATE 就为整个对象取得存储，之后不迁移、不驱逐。VRAM 对象占一段连续显存，Host 对象占一段连续 DMA 地址；有 IOMMU 时，连续 DMA 地址背后的物理页可以分散。这里需要分别看三个长度：应用申请的 `size`、页对齐后的 `mapped_size`，以及分配器实际保留的长度。当前驱动还会把最后一个长度向上取为 2 的幂：

> **[SOURCE]** 本仓库 `0e7b8e7`：[gpgpu_bo.c](vscode://vscode-remote/wsl+Ubuntu/home/book/1.project/gpu_study/4.experiments/gpu-study-qemu/software/gpgpu/linux/gpgpu_bo.c:133:1) [第 133～145 行](vscode://vscode-remote/wsl+Ubuntu/home/book/1.project/gpu_study/4.experiments/gpu-study-qemu/software/gpgpu/linux/gpgpu_bo.c:133:1)，存储长度的计算。

```c
133	/* 分配存储：长度取页对齐与对齐要求中较大者，并向上取 2 的幂以满足对齐。 */
134	static int bo_storage_alloc(struct gpgpu_bo *bo, u64 alignment)
135	{
136		u64 size = roundup_pow_of_two(max_t(u64, bo->mapped_size, alignment));
137		int ret;
138
139		if (bo->kind == GPGPU_MEMORY_HOST) {
140			ret = gpgpu_dma_buf_alloc(bo->dev, &bo->host, size, alignment);
141			bo->phys_addr = bo->host.addr;
142			return ret;
143		}
144		return gpgpu_vram_alloc(bo->dev, size, &bo->vram_blocks, &bo->phys_addr);
145	}
```

第 136 行先把长度取整到 2 的幂，这是为了借助“自然对齐”满足对齐要求：

- **Host 对象**交给 `gpgpu_dma_buf_alloc()`。它调用 `dma_alloc_coherent()`，检查返回的 DMA 地址整段落在 2 GiB 窗口内，再把 `0x8000_0000 + DMA 地址` 作为设备协议使用的 GPU 物理地址，最后清零。DMA API 保证一致性分配按“不小于请求长度的最小页阶”对齐，所以只要请求长度不小于对齐要求，返回的地址就已经满足对齐。
- **VRAM 对象**交给 `gpgpu_vram_alloc()`。它向 gpu_buddy 申请一个连续块，块长和对齐都等于这个 2 的幂，再经 BAR2 用 `memset_io()` 清零。gpu_buddy 只管理固件区之前的 60 MiB，首页预先占住，页表页也从同一个池中分配。

以 X 为例，设对齐要求不大于页大小：17,003 个 `float` 共 68,012 字节，页对齐后 `mapped_size` 是 17 页（`0x1_1000`），实际却分配 32 页（`0x2_0000`）。其中只有前 17 页进入 X 的 GPUVA 映射，剩下 15 页仍被这个 BO 占住，不能分给别人。X、Y、Z 三个数组因此额外占用 45 页，即 180 KiB。这项浪费来自分配长度，不是页表多映射了这些页。

### 4.4 CPU 怎样读写对象

**本设备。** Host BO 可由 `dma_mmap_coherent()` 映射给用户态，要求覆盖整个映射长度、使用共享映射且不可执行。应用能直接在这段 CPU 地址中填写 kernarg。VRAM BO 不向用户态提供 mmap，所以准备 X 要多一次搬运：

```text
CPU 写 Host 暂存 BO → COPY(暂存 BO, X)
  → 驱动给两端 users 加一，防止解绑
  → 持 dma_lock，用两端 GPU 物理地址启动 DMA
  → 等待完成中断 → 确认成功后，X 的 VRAM 内容可供后续任务使用
```

COPY 不走用户 GPUVA，使用的是两个 BO 固定的 GPU 物理地址。等待最长 5 秒；只有确认成功后，调用者才能把数据当作已到位。超时只说明本次等待结束，不能证明 DMA 已停止，驱动会置全局 `dma_uncertain` 并继续保留两端对象。

### 4.5 GPU 映射的建立

**本设备。** X 的存储已经分配好，库接下来需要给 Kernel 一个 GPUVA。库在可分配区间内按首次适配寻找对齐且空闲的范围，再把所选地址交给 MAP；驱动校验地址归属、范围和重叠，不替库另选一个地址。以 X 的地址取 `0x0040_0000` 为例，当前顺序如下：

```text
MAP(X, address = 0x0040_0000, perms = R | W)
  1. 检查：VM 未失败、没有存活队列、对象未绑定、地址合法且不与已有绑定重叠
  2. vm_init()（仅首次）：分配通知页 → 分配根表 → 写通知页 PTE；不取 VMID
  3. 记录 gpu_addr、permissions、bound，并取得绑定引用
  4. 逐页写 X 的叶子 PTE（共 17 页）：
       vm_leaf() 从根表开始，经 BAR2 读取两级目录项
       → 缺中间表时分配表页、写 PDE → 找到叶子位置并写 PTE
       第 0 页写入 0x0020_0000 | VALID | R | W = 0x0020_0061
  5. vm_invalidate_range()：此时 VM 不占 VMID，直接返回，不写失效寄存器
```

MAP 成功返回，表示驱动已经登记绑定并写好页表。此时设备还没有可用来运行这条队列的上下文；建队列时，`gpgpu_vm_attach()` 才取得 VMID、写根、失效整个 VMID 并启用上下文。范围失效函数保留了“占有 VMID 时发请求”的分支，但当前 MAP 路径不会走到该分支，寄存器语义放在第 5.2 节说明。

**差异与代价。**

1. **失败时怎样收尾。** AMD 写表失败时会调用 `unmap_bo_from_gpuvm()`，撤销登记并尝试清除已写表项；个别清理步骤的错误会被忽略，因此不能把它概括成任何故障下都完全回滚。本设备先置绑定再写表，失败后保留绑定并禁止继续使用 VM，见 D1。
2. **同步与异步。** AMD 可以把写表交给 SDMA，由 fence 表示完成。本设备由 CPU 经 BAR2 同步写表，没有独立的异步写表任务；MAP 成功后还要经过建队列时的根配置和整体失效，设备才能使用该 VM。
3. **写入可见性。** AMD 的 CPU 经 BAR 写显存会经过 HDP，HDP 可能暂存写入，所以这条 CPU 写表路径在 `mb()` 后还要刷新 HDP。本设备没有 HDP；当前双进程实现的 BAR2 写和后续失效请求经 vfio-user 通道按序处理，驱动在发 REQ 前用 `wmb()` 保证写表先发布。这个结论依赖本设备的通道和回调模型，不能推广成真实 GPU 写页表只需屏障。
4. **写表效率。** 已有目录路径时，本设备每写一个叶子项仍要从根读两级目录，17 页对应 34 次 BAR2 读和 17 次叶子写；新建表页还会有额外分配和写入。AMD 用页表游标继续处理相邻范围，减少重复访问上层目录。这项简化主要增加写表开销。
5. **GPUVA 由谁选。** 两侧都由用户态选址、内核校验。本设备用首次适配选址、链表查重叠；AMD 的用户库管理地址区间，内核用区间树查重叠。内核建立页表，不代表地址也是内核选的。

### 4.6 解除映射与释放

**本设备。** 应用已经用完 X，但“撤销 GPUVA”和“归还 X 的存储”仍是两个动作。正常回收先停止提交、排空并卸载队列，再做 UNMAP：

```text
队列确认卸载 → 消费旧 IH → 停用上下文、整体失效并归还 VMID
  → UNMAP(X)：检查 VM 健康、没有存活队列、没有未知 DMA、X.users == 0
  → 清 X 的叶子 PTE，结束绑定并放下绑定引用
  → 句柄、会话列表、CPU mmap 等剩余引用也结束
  → 最后一个引用结束：bo_free() 归还存储
```

UNMAP 清表时不分配新表页，所以不会因表页空间不足而中途失败。正常进入这一步时 VM 已不占 VMID，TLB 中也没有本 VM 的翻译，范围失效函数直接返回；该函数中保留的“发请求、确认 ACK”分支当前不会执行。如果对象句柄此前已关闭，解绑时还会移除相应会话列表引用；Host 对象的 CPU mmap 若仍存在，则继续保活存储。

这条顺序分别处理两种设备访问：用户访存在队列确认卸载后结束，旧翻译在归还 VMID 前清除；COPY 不依赖用户队列，另由 `users` 和 `dma_uncertain` 阻止过早解绑。只关闭句柄，或只看到 Kernel 的结果，均不足以跳过这些回收步骤。

### 4.7 页表与 VMID 的寿命

**本设备。** 表页属于软件 VM，从首次建立后一直保留到会话清理；UNMAP 只清叶子项，不拆空目录、不归还空表页。例如先在一个 2 MiB 区段 MAP、UNMAP，再换到另一个区段，旧区段的叶表虽然全空，仍占 VRAM。因此表页占用取决于 VM 曾经触及过哪些区段，而不只取决于当前还映射了多少数据。

三级结构的上限可以直接算出：根表 1 页；根表有 4 个入口，最多需要 4 页 L1；每张 L1 有 512 个入口，最多需要 4 × 512 = 2,048 页 L2。合计 2,053 页，约 8 MiB/VM。这个数不是创建 VM 就一次分配的容量，而是逐步访问整个 32 位空间时可能积累的表页上限。

VM 总数不受两个 VMID 槽位限制，多个长期存在的 VM 可以累计占用超过 16 MiB 的表页；这些表页又与 BO 共用同一个 60 MiB VRAM 池。没有驻留队列的 VM 虽然归还了 VMID，页表和通知页仍在，不能把“编号已归还”当作“VM 内存已回收”。

### 4.8 结果未知时怎样处理

释放资源前，驱动必须确认队列已经卸载、相关 DMA 已经结束、旧翻译已经清除。等待超时只结束软件等待，不能证明这些设备操作已经完成。当前驱动用几个不同状态阻止继续使用或过早释放：

- `vm->failed` 表示 VM 已不能安全继续使用，禁止修改和建队列。它既用于失效未确认，也用于写表或初始化失败；D1 中确定的空间不足也会设置它，所以不能把这个字段统一解释为“硬件执行结果未知”。
- 队列的 `uncertain` 原本用于管理命令已发布、却无法确认结果的情况，防止释放 CP 可能还持有的资源。D4 的问题正是明确拒绝后也残留了这个标志。
- 设备的 `dma_uncertain` 表示某次 COPY 超时，无法确认 DMA 是否结束。当前标志是全局的，会阻止所有会话继续 COPY、解绑和清理。
- 会话的 `orphan` 是清理归属状态：文件已关闭，但驱动还不能安全回收，便把会话留在设备中管理。它不是又一种硬件故障，也不会自动重试失败任务。

当前 orphan 会话要等设备确认停止，即驱动移除路径完成停机后，才能统一回收。AMD 则有超时与复位恢复机制：先使设备不再执行旧访问，再让相关 fence 正常完成或带错误完成，后续按引用和依赖回收。关键仍是确认旧访问已经结束，不是简单给 fence 设置一个错误就能释放内存。

### 4.9 本节缺陷

每个缺陷写明根因、触发方式和影响，修法见[第 9.1 节](#review-fixes)。

<a id="item-d1"></a>

**D1 MAP 失败后，驱动与用户库的状态不一致（P0）。** 以 VM 已初始化、X 尚未绑定为例：MAP 先设置 `bound` 并取得绑定引用，再逐页写 PTE。如果中途需要新表页，而 VRAM 池已满，驱动返回 `-ENOSPC`，把 VM 置为 failed，却保留 X 的绑定和可能已写入的部分 PTE。

用户库把 `ENOSPC` 当作可撤销的确定失败，关闭句柄并丢弃用户态对象记录；只有 `EIO`、`ETIMEDOUT`、`ENOMEM` 被归入“结果未知”。于是库认为这次申请没有留下对象，驱动却保留了绑定，并拒绝该会话后续的 BO_CREATE、MAP、UNMAP 和建队列，返回 `-EBUSY`。应用只能关闭会话，不能简单释放一点显存后重试。

触发条件是 MAP 需要建立新目录路径，但 VRAM 已不足以分配表页；例如事先保留一个未绑定 BO，把池用到不足一页，再将它映射到新的 2 MiB 区段。[D2](#item-d2) 的空表页积累会更容易造成这种情况。首次 MAP 的 `vm_init()` 也有相关失败路径，但阶段不同：通知页、根表或通知页映射分配失败时，尚未登记这个 BO 的绑定，VM 却同样进入 failed，内部初始化资源可能已部分建立。修法必须同时处理初始化失败和写对象 PTE 失败。

<a id="item-d2"></a>

**D2 表页永不回收，并与 BO 共用 VRAM 池（P1）。** 反复在不同区段 MAP、UNMAP 的会话，表页只增不减，最多约 8 MiB/VM，会挤占 BO 的空间并触发 D1。

<a id="item-d3"></a>

**D3 存储按 2 的幂取整（P2）。** 见第 4.3 节：X 只需 17 页却占 32 页。两侧的预先取整都可以去掉；Host 侧在直接映射且不经 CMA 时，分配器内部仍按页阶整块分配。

<a id="item-d4"></a>

**D4 卸载被 CP 拒绝后，队列和 VMID 一直被占用（P0）。** `gpgpu_queue_destroy()` 发命令前先把队列置为 `UNLOADING`，并设置 `uncertain`，防止命令结果未确认时回收资源。问题出在收到明确拒绝之后：结果码已经有效，驱动仍只把队列标为 FAULTED，没有清除 `uncertain`。下一次 `QUEUE_DESTROY` 在入口就因这个标志返回 `-EBUSY`，无法再次询问 CP。

有效的失败结果对应不同设备状态，不能统一解释成“还在运行”或“已经卸载”：

- `RECOVERY_REQUIRED`：正常队列尚未排空，CP 没有执行停用。驱动先检查消费位置 R 等于提交位置 W；若此后还有线程预留新包，且 CP 再检查时新包尚未消费，就会拒绝卸载。这时 HQD 仍可运行，驱动却把队列标成 FAULTED。
- `MQD_FAULT`：CP 读取 W 失败时记录 RING 错误并停止 HQD；保存进度到 MQD 失败时，CP 已先停止取包，再记录 SAVE 错误。这两条路径都已停止取包，但仍保留槽位与 MQD 的绑定，不能直接当作卸载成功。
- `NOT_MAPPED`：CP 此时的占用表中找不到该 MQD。这只能说明当前未装载，不能推断这条队列历史上从未装载，也不能跳过旧 IH 的处理。

`uncertain` 残留后，软件队列无法变成 dead；文件关闭又因有存活队列而把会话转为 orphan，VMID、页表和对象一直保留到设备停止。若两条队列都卡住，两个用户 VMID 就都无法归还，其他会话再也建不了队列。

**D5 一次 COPY 超时冻结整个设备的内存回收，并漏减计数（P1）。** 这里有两个需要分开的情况：

1. 真正启动的 COPY 超时，驱动置全局 `dma_uncertain`，保留两端的 `users`，因为 DMA 可能仍在访问。这是有意的保守处理，但影响扩散到所有会话：后续 COPY 返回 `-EIO`，UNMAP 和会话清理返回 `-EBUSY`，关闭文件只能转为 orphan。要解除这种全局保留，需要第四阶段先确认 DMA 引擎停止。
2. 另一次 COPY 在进入前已存在 `dma_uncertain`。函数仍先给本次两端的 `users` 加一，随后才检查全局状态并退出；本次 DMA 从未启动，收尾却又因全局标志为真而不减计数。这是额外的计数错误，不能用“本次 DMA 结果未知”解释。

修复应依据**本次 COPY 是否启动、是否已经结束**决定计数去留，而不是只检查设备级的历史故障标志。

## 5. TLB 与翻译失效

面试可能问：GPU 的 TLB 怎样组织？页表改了以后，怎样保证设备不再使用旧翻译？失效请求和正在进行的访问怎样避免竞争？

### 5.1 AMD：两级翻译缓存，按 PASID 失效

页表已经建立后，Kernel 通常会连续访问同一页或相邻页。如果每次都从根读四级表，翻译成本会很高。AMD 用 UTCL1 和 UTCL2 缓存翻译；下面是按功能画出的查找关系，不表示物理布局：

```text
访存请求：VMID、GPUVA、访问类型
  → 客户端的 UTCL1：命中最终翻译 → 检查权限并访问数据
  → 未命中，查询共享的 UTCL2（VM L2）
      → 命中最终翻译：返回目标页
      → 只有目录信息命中：Walker 从已知的下级表继续查
      → 均未命中：Walker 从页表根开始查
```

UTCL1 靠近各访存客户端，只保存最终翻译；一个 hub 内共享的 UTCL2 还保存 PDE 信息。缓存叶子翻译可以免去整次遍历，缓存中间目录则能在叶子未命中时少读几级表。

FRAG 解决的是“一项翻译覆盖多少地址”。它把连续、属性相同且满足对齐条件的一组 4 KiB 页标成同一片段，片段长度为 `2^(12+FRAG)` 字节，L1 可用一项覆盖整段。例如 FRAG 为 2 时覆盖 16 KiB，而不是只覆盖一页。这种连续片段合并与“目录项直接作为大页叶子”的 PDE-as-PTE 不是同一种编码；本设备目前两者都未实现。

**[BOUNDARY]** MI300X 各级 TLB 的容量、相联度和替换策略没有公开资料。gem5 的 Vega TLB 默认是 64 项全相联、LRU 替换，另有 64 项页遍历缓存；这是模拟器的可配置参数，不能据此推断真机。

失效时要同时考虑“清谁的翻译”和“清哪些层”。硬件 REQ 以 VMID 位图选上下文，并指定刷新类型和缓存种类（L1 PTE、L2 PTE、L2 PDE0/1/2）；ACK 按 VMID 逐位确认。每个 hub 有 18 个失效引擎，驱动可通过相应寄存器发请求。虽然硬件提供地址范围寄存器，固定基线把范围初始化为全范围，本文讨论的路径实际按整个 VMID 刷新。

软件的计算 VM 以 PASID 标识，`amdgpu_vm_flush_compute_tlb()` 先比较页表变更序号 `tlb_seq`：自上次刷新后没有新变化，就跳过；有变化则对各 XCC 按 PASID 请求失效，作用于该地址空间当前绑定的硬件上下文。因此“软件按 PASID 请求”和“硬件清 VMID 的缓存项”是同一过程的两层描述。

KFD 建立映射后会刷新；GC 9.4.2 及以后（包括本文的 9.4.3）解除映射后也执行 heavyweight 刷新。AMD 允许队列存活时修改映射，但仍要求应用不解除任务正在使用的对象。驱动则保证先等写表 fence，再完成 TLB 刷新，最后撤销 DMA 映射和释放存储，不能靠写了新 PTE 就立即回收旧页（第 4.6 节）。

### 5.2 本设备：单级 TLB，按 VPN 范围同步失效

本设备只有一级 TLB，CP 窗口与执行器共用。GPUVA 除以 4 KiB 得到 VPN，再用 `VPN % 64` 选一组；组内有 4 路，每路保存 VMID、VPN、目标物理页和权限。只有 VMID 与 VPN 都相同才算命中，所以相同 GPUVA 的不同 VM 不会互相命中；但它们仍可能竞争同一组的存储位置。

X 的 17 页对应 VPN `0x400`～`0x410`，分别落在第 0～16 组。另一会话把对象映射到同一 GPUVA，会使用同样的组，但标签里的 VMID 不同。组内怎样优先使用空路、怎样按 LRU 替换，统一见 [GPUVM 规格第 5.2.1 节](<./GPUVM 第一版规格.md#gpuvm-tlb-lru>)。TLB 只缓存成功的叶子翻译，不缓存失败结果和中间 PDE；命中、未命中、替换三个计数由全设备共用。

设备同时提供**整 VMID 失效**和**VPN 范围失效**。例如要清 VMID 1 中 X 的翻译，寄存器协议是：

```text
VM_INV_VPN_START = 0x400，VM_INV_VPN_END = 0x410（首尾都包含）
  → VM_INV_REQ = VMID 1 的位图位（1 << 1，即 0x2）| RANGE
  → 设备检查整个请求 → 清匹配项 → VM_INV_ACK = 0x2 → 寄存器写入处理结束
```

REQ 写的是 VMID **位图**，不是编号 1 本身。不带 RANGE 时忽略 VPN 范围，清所选 VMID 的全部项。REQ 含保留位、位图为空、范围非法，或任一所选上下文还有激活 HQD／在途访问时，设备整体拒绝，不清任何项，ACK 只置 ERROR。驱动读回的 ACK 必须恰好匹配本次请求位图，才能确认完成。

还要区分设备能力和当前驱动用法：驱动的 MAP、UNMAP 调用范围失效辅助函数，但 VM 此时不占 VMID，函数直接返回；当前实际发出的失效主要在取得、归还 VMID 时，清整个 VMID。范围失效保留给直接寄存器使用及后续 A2，并不表示当前已经支持运行中改映射。

### 5.3 同步失效为什么成立：模拟器的并发模型

真实硬件上，Walker 可能已经读了旧页表，但还没把结果填进 TLB。如果失效只清除当时已有的项，旧结果随后又填回，就会破坏失效保证。AMD 的刷新类型、ACK 和页表更新／释放顺序共同处理这类并发。本设备没有模拟异步 Walker，失效能在一次寄存器写入内完成，依赖的是当前 QEMU 回调模型。

在双进程配置中，Host 指运行 Linux 驱动的 aarch64 客体；设备、执行器和 RV64 CP 位于另一个 QEMU 进程。BQL 是**设备进程**的主锁，不会阻止客体驱动发消息。关键在于设备收到消息后何时执行回调：

```text
设备进程（持 BQL）                                 Host 侧
vm_translated_rw()：accesses++
  gpgpu_phys_rw() → 发出 vfio-user DMA 请求 ──────▶ 访问客体内存
  等待 DMA 回复                                    驱动写 VM_INV_REQ
  期间收到的 Host 命令只接收、暂存，不执行设备回调
  ◀────────────────────────────── DMA 回复
accesses--，本次用户访问返回
之后处理暂存的 VM_INV_REQ → vm_invalidate()
  此时旧访问已结束，才检查条件、清 TLB、发布 ACK
```

设备等待 DMA 回复时没有释放 BQL，接收函数也不重入设备回调。因此 Host 可以在访问中途发出 REQ，但**设备实际处理 REQ 时**，这次同步访问已经结束，`accesses` 已归零。`gpuvm.c`、`phys.c` 中“DMA 可能暂时释放主锁”的注释与当前实现不符；在途计数检查目前主要是防御性约束，不能把它当作真实的异步失效实现。

不过，单次访问结束不代表整个任务结束。Dispatch 按定时器分段推进，两段之间可以处理 Host MMIO；CP 处理一个包也会发起多次窗口访问，期间可以插入 Host 操作。这些跨回调的任务仍由激活 HQD 标识。因此当前真正禁止任务中途改翻译的，是设备的“所选 VMID 没有激活 HQD”检查，加上驱动“先卸载队列、再改映射”的规则。只谈 BQL，解释不了整个 Dispatch 的保护。

### 5.4 取舍与代价

- **单级、只缓存叶子。** 结构简单，组相联加 LRU 足以讲清 TLB 的基本行为。代价是每次未命中都要读 3 次表项，没有 PDE 缓存；也无法演示 AMD 失效时要分别选择 L1、L2、PDE 各级的原因。
- **没有 FRAG。** 256 项 × 4 KiB，最多覆盖 1 MiB。AMD 靠 FRAG 让一项覆盖一整段连续内存。
- **组号不含 VMID。** **[INFERENCE]** 库在不同会话中都从相同区间起点首次适配，对象容易取得相同 GPUVA，因而竞争相同的组。四路没有按 VMID 分配固定份额；两边访问量接近时可能各保留约一半，一边访问更频繁时也可能替换另一边的大多数项。标签保证隔离，不能保证缓存份额。
- **按范围失效。** 设备接口比 AMD 驱动在本文路径中的整 VMID 刷新更细，只清一个对象的范围时可以保留其他对象的翻译。实现仍扫描全部 256 项，只是按 VMID 和 VPN 决定是否清除。当前驱动改映射时不占 VMID，所以不会发出这个请求；运行中使用范围失效属于 [A2](#item-a2)，现有设备语义由寄存器 QTest 覆盖。
- **冻结映射。** 因为队列存活期间不改映射，同步失效就不需要 fence 和刷新类型。代价是运行中不能改映射，见 [A2](#item-a2)。
- **计数全设备共用。** 无法区分是哪个 VMID 或哪个访存主体造成的未命中。

对应改进：[A2](#item-a2)、[A3](#item-a3)，后续方向 [E2](#item-e)。

## 6. 访存故障

面试可能问：GPU 访问一个没有映射的地址会怎样？能像 CPU 缺页那样恢复吗？

### 6.1 AMD：可重试故障与不可恢复故障

Kernel 访问一个地址时，可能是合法页面暂未建立 GPU 映射，也可能是地址本就非法、权限不足，或者翻译与存储访问失败。恢复策略首先取决于故障是否可重试，以及这段地址是否由可恢复的内存管理路径负责：

```text
访存 → UTCL2 / Walker 检测故障 → IH 报告地址、访问类型、VMID、PASID
  ├─ 可重试且属于可恢复的 SVM 范围 → 检查 VMA / 权限 → 恢复映射 → 重试访问
  └─ 不可恢复 → KFD 停止进程队列 → 内存异常事件 → 运行时处理
```

IH 记录带故障页地址、是否可重试和是否为写等信息。驱动还读取 `VM_L2_PROTECTION_FAULT_STATUS`，进一步判断客户端编号（CID）、读写方向（RW）、页表遍历错误（WALKER_ERROR）、权限错误（PERMISSION_FAULTS）、映射错误（MAPPING_ERROR），以及是否还有后续故障（MORE_FAULTS）。这些字段用于定位哪次访问在哪个环节失败。

- **可重试故障**：在可恢复 SVM 路径中，硬件保留待重试访问，驱动经 `amdgpu_vm_handle_fault()` 进入 `svm_range_restore_pages()`，检查 CPU VMA 和权限，必要时迁移页面、补好 PTE，然后让访问重试。只有恢复成功，Kernel 才能继续；任意未映射地址不会因此自动变成合法内存。固定基线的 9.4.3 默认 `noretry=1`，需要用参数打开重试，这里描述的是具备相应配置时的恢复路径。
- **不可恢复故障**：没有被调试器接管时，KFD 驱逐这个进程在该设备上的全部队列，再发内存异常事件。ROCr 的 `VMFaultHandler` 如果也没有自定义处理器接管，最终调用 `abort()` 终止进程。

### 6.2 本设备：只检测、记录和停止

本设备没有补页或重试路径。假设 X 跨页，Kernel 已读完前一页，访问下一页时找不到有效 PTE：

```text
执行器访问 X 的下一页 → GPUVM 记录 UNMAPPED 故障
  → Dispatch 失败 → CP 停止源队列、提交 IH 队列错误记录
  → 驱动把故障保存到队列对象，并使该队列仍为 PENDING 的事件失败
  → 应用等待返回错误，再查询故障地址、访问类型和阶段
```

此前已经写入 Z 的部分保留，失败不会回滚，也不会重放整个 Dispatch。CP 取包、读描述对象或写完成对象发生访存错误时，同样按源队列错误处理。

故障编码区分六类：上下文未启用（CONTEXT）、范围或对齐错误（RANGE）、未映射（UNMAPPED）、页表编码或目标页不合法（TABLE）、权限不足（PERMISSION）、后备存储访问失败（STORAGE）。TABLE 不只表示页表内容被破坏，也可能是 SYSTEM 与目标地址域不匹配等格式问题。每个 HQD 槽只保留首次故障的地址、原因、VMID、访问类型和阶段；驱动复制到软件队列后，后续复用硬件槽不会丢掉该队列的诊断信息。完整规则见 [GPUVM 规格第 6 节](<./GPUVM 第一版规格.md#gpuvm-signal>)。

### 6.3 取舍与代价

- **为什么不恢复。** 对象在创建时取得存储，队列创建前完成映射，因此本设备没有“合法访问缺少驻留页，需要现场补页”的需求。未映射或权限故障通常应检查应用的地址与权限；TABLE、STORAGE 还可能来自驱动、页表或访存通道，不能把所有故障都归咎于应用。当前统一停止并报告。若以后引入按需驻留，执行器还要能停在故障指令并重试，驱动也要负责恢复存储和映射，见 [E4](#item-e)。
- **停止范围。** AMD 在普通路径上停掉进程在该设备上的全部队列，本设备只停源队列。目前每个 VM 只有一条队列，两者效果相同；以后允许一个 VM 有多条队列时，应同时停掉同一 VM 的其他队列。
- **记录方式。** 本设备每槽只留首次故障，后续故障丢失；AMD 的 IH 记录逐条上报，状态寄存器另有 MORE_FAULTS 标记。教学上首次故障已经足够定位问题。

## 7. 完成通知与事件等待

面试可能问：Kernel 执行完以后，Host 怎样得知？等待的线程怎样避免错过唤醒？

### 7.1 AMD：自动复位事件与 `event_age`

这里有两个不同对象：**Signal 保存应用要等待的数值，事件负责让等待线程睡眠和唤醒**。中断只告诉线程“条件可能变化了”，线程醒来还要复查 Signal，不能把一次唤醒直接当作当前任务成功。

```text
AQL 包完成 → release，保证先前结果按要求发布 → 原子递减 Signal
  → mailbox 非空时：写事件槽、产生中断
  → KFD 按 PASID 找进程、按事件编号找事件 → 唤醒等待者
  → ROCr 复查 Signal 是否满足本次等待条件
```

`amd_signal_t` 为 64 字节、64 字节对齐：偏移 8 是信号值，偏移 16 是 `event_mailbox_ptr`，偏移 24 是 `event_id`。KFD 为每个进程提供 4,096 个 8 字节事件槽，共 32 KiB；中断记录里的事件编号可能只有部分位，能唯一定位时直接查找，否则扫描已写入的槽。

ROCr 创建信号事件时传 `manual_reset=false`，选择自动复位：通知到达时若已有等待者，就唤醒它们并恢复为未置位；若通知先到、线程后等，等待调用会消费已有置位状态。这样旧通知不会永远留下一个“立即成功”的事件。

`event_age` 进一步记录“发生过几次通知”：每次置位递增，等待者可带上次看到的 age。若准备睡眠期间通知已经发生，age 已改变，等待就立即返回，不必等下一次中断。自动复位处理通知的消费，age 识别两次等待之间的新通知；配合唤醒后复查 Signal，同一个事件才能服务多次派发。

### 7.2 本设备：一次性事件

本设备的 Signal 为 24 字节。应用在发布任务前准备值 1；任务完成后由 CP 单独把值写成 0，不存在多个完成方竞争递减同一个值。每个 VM 预先分配一页 Host 通知页，开启 GPUVM 时映射在 `0xffff_f000`，提供 512 个 8 字节槽。EVENT_CREATE 只从已有页中分配槽位，不新建页表映射。

CP 的完成步骤与驱动消费通知是先后两个阶段：

```text
CP：结果已写回 → Signal = 0 → 通知槽写事件编号 → IH 写 SIGNAL_NOTIFY
      → 包头改回 INVALID → 回报消费进度

驱动：消费 IH → 按 MQD 地址找到队列 → 核对事件编号和通知槽
        → PENDING 事件变为 NOTIFIED → 唤醒等待线程
```

IH 记录还带类型和 HQD 槽。MQD 地址用来找源队列，事件编号和通知槽再用来确认应唤醒谁；不是只看一个“完成中断”就唤醒所有事件。Signal 归零早于驱动处理 IH，因此线程可能已经观察到结果完成，而事件仍是 PENDING，队列消费进度也尚未回报。

事件只允许 `PENDING → NOTIFIED` 或 `PENDING → FAILED`，等待不会消费状态。一次事件结束后，后来的等待也会立即看到同一个结果，这适合一次完成对应多个等待者，但没有自动复位语义。完整规则见 [GPUVM 规格第 6.1 节](<./GPUVM 第一版规格.md#gpuvm-signal>)。

### 7.3 差异与代价

- **单写者与原子递减。** CP 是唯一更新 Signal 的一方，写 0 就够了；需要多个更新者时再扩展原子操作。
- **没有缓存。** 本设备没有 GPU 缓存，完成时不需要像 AMD 那样先 release 回写，结果写回后就对 Host 可见。
- **来源怎样识别。** 本设备用 MQD 地址定位队列，AMD 用 PASID 加事件编号。引入 PASID 见 [A1](#item-a1)。
- **事件语义。** 一次性事件本身没有问题，问题在运行时把它当成可复用的事件用，见下面的 D7。

<a id="item-d7"></a>

**D7 同一运行时连续派发时，等待退化为忙循环，故障只报超时（P0）。** 驱动提供一次性事件，运行时却只在首次派发时创建一个事件，随后反复把同一事件编号和通知槽写入 Signal。当驱动已经消费第一次 `SIGNAL_NOTIFY`、把事件置为 NOTIFIED 后，这个状态就不再回到 PENDING。

第二次派发会把 Signal 重新准备为 1，但旧事件仍是 NOTIFIED。若当前任务超过约 200 μs 的主动轮询期，等待路径变成：

```text
wait_signal()
  主动轮询当前 Signal 约 200 μs，仍未完成
  → gpgpuKmtWaitEvent()：旧事件已是 NOTIFIED，ioctl 立即返回成功
  → 复查当前 Signal，仍为 1 → 再次调用 ioctl → 立即返回 → ……
```

线程没有睡眠，而是在反复调用 ioctl、复查 Signal。若第二次 Kernel 在 Signal 归零前发生访存故障，`gpgpu_fail_queues()` 只会把 PENDING 事件改成 FAILED，旧的 NOTIFIED 事件不变。等待者因而空转到期限，得到 `WAIT_TIMEOUT` 而非 `WAIT_FAILURE`；无限期等待则不能退出。

这个故障表现以**旧通知已被驱动处理**为前提。若第一次 Signal 已归零、IH 却尚未消费，事件还可能是 PENDING，此时后续故障仍能使它失败。两种时序都说明 Signal 完成和事件状态不是同一个时刻变化，不能仅按“已经派发过一次”判断状态。

还有一条半初始化路径：建队列成功、建事件失败后，`rt->queue` 已设置而 `rt->event` 为空；后续派发跳过初始化，在填写 Signal 时解引用空事件指针。

示例程序为每个计算单独建运行时，只派发一次就销毁，所以现有计算示例不覆盖复用路径。按源码推导，可在同一运行时连续派发，用超过主动轮询期的 Kernel 观察第二次等待的 `EVENT_WAIT` 调用持续增长；在旧事件已为 NOTIFIED 时让下一次派发访问非法地址，预期会误报超时。这些是缺陷触发场景，实际运行记录仍只在软件栈第 5 节维护。

## 8. Kernel 启动状态

面试可能问：GPU 线程启动时，怎样知道自己的编号、工作组大小和参数地址？

向量加法的 Kernel 除了取得 X、Y、Z 的地址，还要计算自己负责的元素编号：`i = 工作组编号 × 每组线程数 + 组内线程编号`。数组地址和 N 放在 kernarg 中，线程坐标与执行规模则来自启动状态。两侧都在真正执行第一条指令前准备这些信息，但交给 Kernel 的接口不同：

```text
Host 准备：Dispatch 包（执行规模、描述对象地址、kernarg 地址）
  → CP 读描述对象，取得代码入口和资源要求
  → 启动 Wave / Warp，初始化线程可读取的状态
      AMD：VGPR 保存组内坐标，SGPR 保存启用的用户数据和工作组信息
      本设备：只读 CSR 提供坐标和规模，a0 保存 kernarg 的 GPU 地址
  → Kernel 算出 i → 从 kernarg 取得数组地址与 N → 检查 i < N → 读写数组
```

**AMD。** 启动状态有几个来源，需要分开看：

- VGPR 是每个 Lane 各自的向量寄存器。硬件在 VGPR0 中按 `{2'b00, Z[9:0], Y[9:0], X[9:0]}` 打包组内坐标，不同线程取得不同的 X、Y、Z。
- SGPR 是一个 Wave 内共享的标量寄存器。开头最多装入 16 个 user data SGPR，是否包含 kernarg 指针、dispatch packet 指针等由描述符使能位决定；随后按配置装入启用的 workgroup ID 分量和工作组信息。不能假设所有 Kernel 都在固定 SGPR 位置取得同一组字段。
- 描述符和运行时 ABI 还决定怎样取得完整执行规模。Kernel 可通过启用的 dispatch packet 指针读取 Grid、工作组尺寸；运行时也按 Kernel 元数据在显式参数之后填写相应隐藏参数。规范的启动表另列出 TTMP6/7 中的 dispatch packet 地址、TTMP8～10 中的 Grid 三维尺寸，属于陷阱临时寄存器状态，不应与 user data SGPR 的布局混为一谈。

AMD Kernel 描述符为 64 字节，既包含工作组共享段、私有段和参数块长度，也包含相对描述符的代码入口偏移及 `compute_pgm_rsrc1/2/3` 等资源配置。CP 依据它准备执行资源和启动寄存器；描述符并非只保存代码地址。偏移 `0x0c` 在这个布局中是保留字段。

**本设备。** 描述对象只有四个 32 位字段，共 16 字节：代码入口（绝对 GPU 地址，不是相对偏移）、代码长度、参数块长度和 `kernel_abi_version = 4`。开启 GPUVM 时，代码入口和 `a0` 中的参数地址都是 GPUVA；关闭时才直接使用 GPU 物理地址。CP 校验描述对象后把执行规模、地址和 VMID 交给执行器，取指时还逐次检查 PC 是否落在声明的代码范围内。

创建新 Warp 时，执行器保存一份 Warp 共享的 Block 编号、Block 尺寸和 Grid 中的 Block 数，并为各 Lane 保存组内坐标。Kernel 经只读 CSR `0xCC0`～`0xCCB` 读取这些值；普通通用寄存器被覆盖不会改变 CSR 返回的启动信息。同一个 Warp 分段继续时保留状态，切换到新 Warp 才重新初始化。

仍用 17,003 个元素的向量加法，设 `blockDim.x = 64`、`gridDim.x = 266`。本设备的 `gridDim` 数的是 **Block 个数**。最后一个 Block 中的线程可以这样定位数据：

```text
CSR 读取：blockIdx.x = 265，blockDim.x = 64，threadIdx.x = 42
  → i = 265 × 64 + 42 = 17,002
读取 a0 指向的 kernarg：X、Y、Z 的 GPU 地址，以及 N = 17,003
  → i < N，处理 Z[17,002]
组内下一个线程的 i = 17,003 → 不满足 i < N，直接结束
```

每个 Warp 为 32 Lane，所以一个 64 线程 Block 分两次 Warp 执行；不能把 Block、Warp 和单线程坐标当作同一个编号。CSR 的完整分组和字段规则只在 [CP/MEC 规格第 6.2 节](<./CP_MEC 第一版规格.md#spec-kernel-descriptor>) 维护。

### 9.1 缺陷修法

以下按各缺陷说明建议改动和失败收尾，均未实现。“验证”描述修复后需要核对的核心结果，不是已运行记录；现有构建和计算回归仍沿用软件栈的入口，不为本文另建一套检查。

**D1：先预分配表页，再登记绑定。**

把所有可能因分配不足失败的步骤放到对象绑定之前，避免对外返回确定失败、内部却留下半份对象映射：

```text
gpgpu_vm_map()（建议顺序）
  1. 校验参数与 VM 状态（不变）
  2. 首次 vm_init()：准备通知页、根表及通知页映射
       初始化分配失败 → 释放本次初始化资源，恢复 ready = false，不置 failed
  3. gpuvm=on：按 [va, va + size) 覆盖的 2 MiB 区段预先建立目录路径
       只分配中间表，不写这个 BO 的叶子 PTE
       分配失败 → 返回相应错误（如 -ENOSPC），BO 未绑定，VM 仍可使用
  4. 登记 gpu_addr、permissions、bound，取得绑定引用
  5. 写 BO 的叶子 PTE：目录路径已齐全，不再因缺表页而失败
  6. 如占有 VMID，完成范围失效；当前 MAP 不占编号，直接返回
       失效未确认 → 保留资源，把 VM 置为 failed
```

第 2 步尚未占 VMID，也未把根交给设备，分配失败可以确定地回滚。第 3 步失败时已建的空表页可以暂留给 D2 管理，但不得留下这个 BO 的有效叶子映射。保证的是**失败后没有登记该 BO 的绑定，VM 仍能继续使用**，而不是所有内部状态都与调用前完全相同。

对 `ENOSPC` 路径，用户库原有“确定失败、关闭句柄”的处理可以保留；修复驱动后，两侧理解一致。元数据分配仍可能返回 `ENOMEM`，库目前会保守地把它归入结果未知，这条错误分类还需单独核对，不能概括成任何分配错误都无需处理库侧。

验证：预留一个未绑定对象后，把 VRAM 用到不足一页，再将该对象 MAP 到新 2 MiB 区段，应返回 `-ENOSPC`；释放空间后重试应成功，现有计算示例仍通过。

**D2：表页按有效项计数回收，或者设配额。** 推荐回收空表：叶表记录有效 PTE 数，目录表记录有效 PDE 数。UNMAP 清完叶子后，若 L2 已空，先清除父 L1 中指向它的 PDE，再归还 L2；父 L1 也空时，沿同样方向继续处理。

```text
清 BO 的叶子 PTE → 确认旧叶子翻译已清除
  → 空 L2：清父 PDE → 释放 L2
  → 空 L1：清根表中的父 PDE → 释放 L1
```

当前 UNMAP 前已卸载队列并归还 VMID，旧翻译在归还时清除，不需要另外等一个范围 ACK；若配合 A2 允许占着 VMID 改映射，就必须先完成相应失效。现有 TLB 不缓存 PDE，清父 PDE 后无需为目录缓存再刷一次；加入 A3 的 PDE 缓存后，须在清父 PDE 后、释放表页前再完成目录缓存失效，防止缓存继续指向已释放的表页。

更简单的替代方案是限制每个 VM 的表页配额，超额时在登记 BO 绑定前返回 `-ENOSPC`。配额只能限制单个 VM 的占用，不能代替空表回收，也不能保证全局池永不耗尽。验证仍围绕回收结果：在多个不同的 2 MiB 区段反复 MAP、UNMAP 后，空表不再持续挤占可分配给 BO 的空间。

**D3：去掉预先取整。** 请求长度改为 `max(mapped_size, alignment)`，不再取 2 的幂：

- VRAM：`gpgpu_vram_alloc()` 目前把长度同时当作 `min_block_size` 传给 gpu_buddy，而 buddy 要求这个参数是 2 的幂，17 页会被直接拒绝。所以要把两者分开：长度传请求长度，`min_block_size` 传 `PAGE_SIZE`。带连续标志时，buddy 在内部取整、分配后裁掉多余部分，块的起点仍按取整后的长度对齐，不小于对齐要求；清零只清请求的长度。
- Host：把同样的长度直接交给 `dma_alloc_coherent()`，对齐由 DMA API 的保证提供。

验证：X 的 VRAM 实际占用 17 页；Ring 等有对齐要求的对象地址仍满足对齐；现有计算示例仍通过。

> **[SOURCE]** 本仓库 `0e7b8e7`：长度与 `min_block_size` 传同一个值，见 [gpgpu_vram.c 第 45～46 行](vscode://vscode-remote/wsl+Ubuntu/home/book/1.project/gpu_study/4.experiments/gpu-study-qemu/software/gpgpu/linux/gpgpu_vram.c:45:1)。Linux `248951dd`：`min_block_size` 必须是 2 的幂，见 [buddy.c 第 1331～1332 行](vscode://vscode-remote/wsl+Ubuntu/home/book/1.project/gpu_study/2.%E6%BA%90%E7%A0%81/linux/drivers/gpu/buddy.c:1331:1)。

**D4：按 CP 返回的结果分别收尾。** `uncertain` 只应保留给“命令可能已执行，但结果无法确认”。拿到有效结果后，先按结果判断 CP 当前持有什么资源，再决定恢复、重试或回收：

```text
UNMAP_QUEUES 的结果
  OK                 → 消费旧 IH、放下 Ring/进度的 users、标记 dead，并执行 VMID detach
  从未发布           → 撤销本次 UNLOADING/uncertain，恢复原状态
  RECOVERY_REQUIRED  → CP 未停用队列：清 uncertain，恢复原状态，返回 -EBUSY
                       调用者停止新提交、排空后重试
  MQD_FAULT          → CP 已停止取包、仍占着槽：清 uncertain，置 FAULTED
                       保留资源，允许再次按“已出错队列”路径卸载
  NOT_MAPPED         → 当前找不到该 MQD：消费旧 IH 后，按已卸载路径回收并执行 VMID detach
  结果未知           → 保持 UNLOADING 与 uncertain，全部资源保留
```

`MQD_FAULT` 的再次卸载仍可能因 MQD 存储不可写而失败，不能承诺一定恢复；VMID detach 也只有在上下文停用和失效均确认后才归还编号。草案解决的是“收到明确结果后还能按实际状态继续清理”，不是用一个失败码直接释放全部资源。

验证：在驱动排空检查与 CP 再检查之间插入新预留，且新增包尚未消费时，卸载应返回 `-EBUSY`、队列仍可使用；停止新提交并排空后再卸载，确认 VMID 可供其他会话借用。

**D5：按本次 DMA 的执行状态撤销计数。** 在 `gpgpu_bo_copy()` 中记录本次搬运是否启动、是否已确认结束。未启动（设备已移除、故障或已有未知 DMA）时撤销本次加到两端的 `users`；已启动且确认结束时也撤销；只有本次确实启动、却无法确认结束时才保留。这样不会把历史上另一笔 COPY 的未知状态，误当成本次也可能仍在访问。

全局 `dma_uncertain` 仍不能直接清零：它保护的那笔未知 DMA 还可能在执行，须由第四阶段的复位恢复（[E5](#item-e)）确认引擎已停止后解除。修正计数和增加恢复能力是两个范围不同的改动。

**D6：只冻结影响 GPU 映射的操作。** 去掉 `gpgpu_bo_create()` 中对存活队列的检查，保留对 VM failed 的检查。关闭未绑定对象的句柄本来就不受限制。MAP、UNMAP 的放开见 A2。验证：队列存活期间 BO_CREATE 成功，现有计算示例仍通过。

**D7：每次派发使用新事件。** 最小修法只改运行时，保留驱动的一次性事件协议。新事件服务当前派发，旧事件只负责等待迟到通知和安全回收，两者不再混用：

```text
gpgpu_rt_dispatch()
  1. rt_ensure_queue() 只保证队列存在，不创建事件
  2. 尝试回收旧事件；EVENT_CREATE 得到本次的新编号和通知槽
       创建失败 → 不发布新任务；下次仍单独执行创建事件这一步
  3. 写参数块，准备 Signal：value = 1，event_id、mailbox 来自新事件
  4. Reserve → Publish → WaitSignal(signal, 本次事件)
  5. 成功后尝试 EVENT_DESTROY
       事件仍 PENDING、返回 -EBUSY → 放入待回收列表，后续再尝试
     失败或超时 → 保留本次事件和相关对象，停止继续派发
       按既有规则确认队列卸载后，再统一回收；卸载未确认则继续保留
```

旧事件不一定在下一次派发前就能销毁：Signal 归零时，CP 可能还没有发布通知，EVENT_DESTROY 即使先消费了已到达的 IH，也仍会因 PENDING 返回 `-EBUSY`；FAILED 事件在源队列卸载前也不能销毁。待回收列表因此需要允许继续保留，而不能把“一次重试”当作完成保证。

正常通知及时到达时，每次派发增加一次创建和一次销毁 ioctl，通知槽可及时复用。若回收持续不能完成，仍可能耗尽槽位，必须把创建失败正常返回给调用者。特别是等待超时后，旧任务可能还在运行，不能覆盖共享 Signal、参数块后直接提交下一次任务。

本次故障对应新建的 PENDING 事件，驱动就能把它置为 FAILED，让等待返回 `WAIT_FAILURE`。建队列和建事件分开，也避免“已有队列、空事件指针”导致下一次跳过初始化。

另一个更接近 AMD 的方案是修改驱动 UAPI，支持自动复位和 `event_age`：等待带上次看到的 age，通知推进 age，消费通知后事件可回到 PENDING；队列故障则使相关事件进入 FAILED，不受旧通知状态影响。这个可复用事件方案列为 P2，与前面的运行时最小修法分开考虑，等待唤醒后仍须复查 Signal。

验证：同一运行时连续派发，后续等待不再因旧事件产生持续的 `EVENT_WAIT` 空转；让后续 Kernel 访问非法地址，返回 `WAIT_FAILURE`；现有计算示例仍通过。

### 9.2 设计升级草案

<a id="item-a1"></a>

**A1 引入 PASID（P2）。** 目标是把长期存在的软件 VM 身份与短期借用的 VMID 分开，接近 AMD 非 HWS 模式的组织。VMID 随驻留借用已经实现，现状见[第 3.2 节](#review-identity)；剩余改动是在设备可见记录中加入稳定身份。本设备的 VM 属于 DRM 会话，因此这里先为每个会话 VM 分配编号，不另外改变会话与进程的对应关系。

```text
驱动创建 VM_A → 分配 16 位 PASID，在 VM_A 存续期间保留
  → 首次建队列：MQD 同时携带稳定 PASID 和本次 VMID
  → CP 把 PASID 带入 IH / 故障记录
  → 队列卸载：归还 VMID，PASID 随 VM_A 保留
  → 再建队列：VMID 可以改变，记录仍能认出同一个 VM_A
```

IH 仍可按 MQD 地址找队列，PASID 主要补足诊断身份，并为按地址空间发起失效提供稳定编号；实际失效仍要作用于该 VM 当前占用的硬件上下文。这个教学编号不随 PCIe DMA 请求发送，不能因此宣称 SMMUv3 已具备逐进程 PASID 翻译。

需要改动的不只是 MQD 填值：固件当前要求 MQD 保留字段为 0，设备也拒绝保留字段非零的 IH 记录，所以字段定义、生成和校验都要一起升级，拟纳入协议版本 5。验证：同一会话前后借用不同 VMID 时，故障记录中的 PASID 仍相同；现有计算示例仍通过。

> **[SOURCE]** 本仓库 `0e7b8e7`：保留字段必须为 0，见 [mgmt.c 第 77～79 行](vscode://vscode-remote/wsl+Ubuntu/home/book/1.project/gpu_study/4.experiments/gpu-study-qemu/software/gpgpu/firmware/mgmt.c:77:1)、[hw/gpgpu/irq/ih.c 第 58～59 行](vscode://vscode-remote/wsl+Ubuntu/home/book/1.project/gpu_study/4.experiments/gpu-study-qemu/hw/gpgpu/irq/ih.c:58:1)。AMD 对应做法见第 3.1 节。

<a id="item-a2"></a>

**A2 队列存活期间允许修改映射（P1）。** 目标是解除“有队列就冻结整个 VM”的限制，改为只强制保留队列基础资源，其余对象可在队列存活期间 MAP、UNMAP。这接近 AMD KFD 的使用方式，但不表示驱动会自动知道每个 Kernel 正在使用哪些数组；这部分寿命仍由应用保证。

假设向量加法正在使用 X、Y、Z，另有一个 Kernel 不再访问的备用对象 U，`U.users == 0`：

```text
UNMAP(U)
  驱动：清 U 的叶子 PTE → 写 VPN 范围 → REQ = 当前 VMID 的位图位 | RANGE
  设备：在 BQL 下处理请求，清旧翻译，写 ACK；不再仅因 HQD 激活而拒绝
  驱动：核对 ACK → 解除 U 的绑定、放下引用 → 条件满足后回收存储
  正在运行的 Kernel 继续使用 X、Y、Z，不受 U 的解绑影响

若应用误解绑仍会使用的 X：
  后续访问 X → UNMAPPED 故障 → 停止源队列；不会自动保留 X 或恢复任务
```

设备不缓存失败的遍历结果，新 MAP 写好 PTE 后仍按相同接口做范围失效。这样映射更新都有“写表、发布、失效确认”的统一收尾，而不是为新增映射另建一条隐含完成路径。

改动分三层完成：

1. 设备失效检查去掉“HQD 激活即拒绝”，上下文根地址与 ENABLE 的修改仍保留忙检查。依据第 5.3 节的同步回调模型，处理 REQ 时单次访问已结束，`accesses` 用于断言这个前提；这不是要增加真实硬件式异步 Walker。
2. 驱动去掉 MAP、UNMAP、BO_CREATE 的存活队列检查，同时解决 D6；保留 VM 失败、未知 DMA 和 `bo->users` 等相关限制，也保留 VM 操作串行化。库释放对象时的“存在队列”检查一并放开。
3. 把设备语义变化纳入协议版本 5，同步更新 GPUVM 规格第 1.2、5.2 节、硬件手册第 17 章，并调整现有 QTest 中“激活 HQD 必须拒绝失效”的旧断言。

放开后，Ring、进度对象仍由 `users` 保护，内部通知页也不向应用提供解绑入口；但代码、描述对象、参数、数组和 Signal 不能靠 `users` 自动保活。应用必须保证 CP 和执行器不再使用它们后才解绑。Dispatch 分段之间、CP 两次窗口访问之间都可能观察到新映射，不能把一次 Dispatch 当成页表快照；误解绑时后续访问可能失败，已经完成的写入不回滚。

验证：长 Kernel 运行期间解绑无关对象，操作成功且计算结果正确；解绑随后仍会访问的输出数组时，报告 UNMAPPED 故障；现有计算示例仍通过。

<a id="item-a3"></a>

**A3 TLB 分层（P2）。** 目标是在现有软件 Walker 上增加客户端 L1 与目录缓存，表现 AMD 分层翻译的作用，不模拟其真实容量或时延。草案暂取每个 L1 为 8 项、PDE 缓存为 16 项，这些都是教学参数：

```text
gpgpu_user_rw(访问主体 = CP 窗口 / 执行器取指 / 执行器数据, VMID, GPUVA)
  → 该主体的 L1：8 项全相联，标签 VMID + VPN
      命中 → 取得物理页和权限，继续访问
      未命中 → 共享 L2（沿用现有 64 组 × 4 路）
        L2 命中 → 返回并填 L1
        L2 未命中 → 查 PDE 缓存
          命中 → 已知叶表地址，只读 1 次叶子 PTE
          未命中 → 读完整 3 级表，填目录缓存和叶子翻译缓存

VM_INV_REQ：对相应范围清各客户端 L1 与共享 L2，并清所选 VMID 的 PDE 缓存
ROOT / ENABLE 改变：额外清该 VMID 的 PDE 缓存；既有整 VMID 失效流程仍保留
```

这里“L2 TLB”和“L2 表页”不是同一对象：前者是共享翻译缓存，后者是本设备三级页表的叶表。PDE 缓存保存的是**找到叶表的结果**，标签用 VMID 加 `GPUVA[31:21]`，一项对应 2 MiB 区段。以 X 的相邻页为例，最终翻译都未命中时，仍可复用同一个叶表地址，省去两次上层目录读取。

实现上，`gpgpu_user_rw()` 要增加“访问主体”参数，CP 窗口、执行器取指和数据访存分别选择自己的 L1。现有三个计数继续对应共享 TLB，现在称为 L2；L1 命中不再计入 L2 的访问。MISSES 仍表示实际到达 L2 后的未命中次数，但加入 L1 会改变访问流，不能保证原 QTest 的具体计数断言原样成立，应随层级语义调整。拟从 `0x092c` 起新增 L1 命中、PDE 命中计数，纳入协议版本 5。

PDE 缓存只保存有效路径，不缓存未建立的目录。新增目录不会命中一份“无效结果”，但撤销目录、回收表页时可能存在旧的有效路径，必须按 D2 在释放前清掉。范围失效可以保留无关叶子翻译，草案为简单起见仍清所选 VMID 的全部 PDE 缓存。AMD 的请求还能分别选择 L1 PTE、L2 PTE、各级 PDE，本草案只表现分层与失效依赖，不复制完整控制位。

验证：首次访问后反复读同页，L1 命中增加、L2 MISSES 不变；失效后再次访问，不能命中旧的叶子或目录缓存；现有 TLB 用例按新层级语义继续核对。

### 9.3 后续方向

- **E1 GPU 物理地址与 PTE 地址字段扩宽。** 目标是解除低 2 GiB IOVA 窗口限制：把 PTE 地址字段扩到 `[47:12]`，SYSTEM 页直接表达 DMA 地址，配合修改 Host 路由和管理地址表示，不再先加固定窗口起点。DMA mask 随之放宽。GPUVA 可继续保持 32 位，即每个 VM 的可见地址空间仍有限，但能映射到更宽的设备／系统地址范围。改动会经过公共物理入口和协议各层，不能只扩大一个掩码。

- **E2 FRAG 大页。** 这里先考虑连续片段合并，不等同于把 PDE 直接变成大页叶子。PTE 的 bit 7～11 当前保留，正好对应 AMD FRAG 的位置；buddy 的连续分配与自然对齐可提供基础条件，但仍须检查每个片段的物理连续性、属性一致性和对齐，GPUVA 也要按片段对齐。Walker 接受片段信息后，TLB 才能按覆盖长度匹配多页，失效也要判断范围重叠，不能仍只比较一个 VPN。

- **E3 TTM 驱逐与迁移。** 固定存储改为可移动后，BO 的身份和 GPUVA 可以保留，背后的页会变化。需要先停访问，再搬内容、更新页表并失效旧翻译，确认后才回收旧页和恢复队列。因此先依赖 E5 的抢占与恢复能力；只有分配器而没有同步、恢复机制，不能完成迁移。范围见[大纲的 GPUVM 扩展](<./QEMU GPGPU 实验大纲.md#gpuvm-advanced-extension>)。

- **E4 可恢复缺页。** 当前访存失败会结束 Dispatch，没有可继续的故障指令状态。若要补页后重试，执行器须保留并重放失败访问，驱动须判断地址是否合法、准备后备存储、恢复映射并确认失效；已完成的写入不能因重放整项任务而重复执行。范围见[大纲的 GPUVM 扩展](<./QEMU GPGPU 实验大纲.md#gpuvm-advanced-extension>)。

- **E5 抢占、强制中止与复位恢复。** 属于第四阶段，需要分别定义“暂停后可继续”和“终止旧任务、报告失败”的状态与完成保证。只有确认旧访问不再发生，才能解除 orphan 保留或清除 D5 的全局 `dma_uncertain`，不能仅靠软件清标志恢复分配。范围见[大纲的异常恢复扩展](<./QEMU GPGPU 实验大纲.md#stalled-task-recovery-extension>)。
