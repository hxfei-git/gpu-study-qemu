### 1.2 贯穿例子：一次向量加法经过的路径

应用计算 `Z[i] = X[i] + Y[i]`，共 17,003 个 `float`。下面的地址是示例取值，与 GPUVM 规格使用的数值一致：X 的 GPUVA 为 `0x0040_0000`，放在 VRAM 偏移 `0x0020_0000`；参数块（kernarg）放在 Host，IOVA 为 `0x4100_2000`；Ring、进度和 Signal 也在 Host；每个 VM 的通知页固定在 GPUVA `0xffff_f000`。

```text
本设备（gpuvm=on）
应用 → lib/rt → lib/kmt → DRM 驱动：BO_CREATE 分配存储，MAP 写页表，QUEUE_CREATE 装载队列
  → 应用写 AQL 包，8 字节写 Doorbell
  → RV64 CP：按管理域（GPU 物理地址）读 MQD，按队列的 VMID 读 Ring 与描述对象
  → RV32 执行器：CSR 给出线程坐标，a0 = kernarg 的 GPUVA，LW/SW 经 GPUVM
  → GPUVM：TLB（64 组 × 4 路）→ 三级页表 → GPU 物理地址
  → 公共物理入口：VRAM；或 Outbound（0x8000_0000 + IOVA）→ PCIe DMA → Host 内存
  → CP 依次写 Signal、通知槽、IH 记录 → 驱动唤醒等待者

AMD（MI300X）
应用 → HIP/ROCr → libhsakmt → KFD/AMDGPU：分配 BO，用户态选 GPUVA，驱动写页表
  → 应用写 AQL 包，写 Doorbell
  → MEC：用 VMID 0 读 MQD，用队列的 VMID 读 Ring
  → CU 上的 Wave：SGPR/VGPR 预置启动信息，按 GPUVA 访存
  → UTCL1 → UTCL2（含 PDE 缓存）→ 四级页表 → 物理地址
  → HBM；或 PTE 中的 DMA 地址 → PCIe（经 IOMMU）→ Host 内存
  → 完成信号原子递减，写事件槽，IH 记录带 PASID → KFD 唤醒等待者
```

两条路径的骨架相同：队列提交、CP 取包、执行单元访存、多级页表翻译、完成通知。差别集中在地址宽度、地址空间身份、映射何时可以修改，以及驱动怎样管理存储，后面各节分别展开。

### 1.3 评审结论

1. **翻译主路径与 AMD 同构。** 两侧都用多级页表，都用 SYSTEM 位区分显存与系统内存，都按 VMID 选择页表根，TLB 都缓存叶子翻译，失效都用 REQ/ACK 确认。本设备 PTE 的 VALID、SYSTEM、X、R、W 位与 AMDGPU 位置相同。主要简化是 32 位地址、固定 Outbound 窗口和只有两个用户 VMID，见[第 2 节](#review-address)、[第 3 节](#review-identity)。
2. **最大的语义差异在“什么时候可以改映射”。** AMD 允许队列运行时修改映射，靠 fence 和 TLB 刷新保证安全；本设备在队列存活期间冻结整个 VM，并依靠模拟器主锁让同步失效成立，见[第 5 节](#review-tlb)。
3. **驱动内存采用固定存储模型。** 对象创建时就分配连续存储，之后不迁移、不驱逐；AMD 用 TTM 管理放置与迁移，用 `dma_resv` 中的 fence 和 KFD 的 eviction fence 协调搬移与释放。固定模型的代价是按 2 的幂取整造成浪费、页表页不回收，以及结果未知时只能长期保留资源，见[第 4 节](#review-driver-memory)。
4. **有 3 个缺陷应优先修复**：MAP 失败后驱动与用户库状态不一致（[D1](#item-d1)）；卸载被 CP 拒绝后队列和 VMID 一直被占用（[D4](#item-d4)）；同一运行时连续派发时事件被复用，等待退化为忙循环，故障只报超时（[D7](#item-d7)）。
5. **最值得做的改进**是队列存活期间允许修改映射（[A2](#item-a2)）。VMID 已改为在队列驻留时绑定；引入 PASID（[A1](#item-a1)）和 TLB 分层（[A3](#item-a3)）主要用于对齐 AMD 的结构，按兴趣安排。

待优化项分三类：D 为缺陷，A 为对齐 AMD 的设计升级，E 为后续扩展。优先级 P0 表示影响状态一致或资源回收、应在版本 4 内先修；P1 是第四阶段候选；P2 是改进项；P3 是后续扩展。完整列表见[第 9.4 节](#review-index)。

## 2. 地址翻译与物理地址空间

面试可能问：一个 GPUVA 怎样变成物理地址？GPU 怎样访问主机内存？

### 2.1 AMD：四级页表，系统内存页直接填 DMA 地址

固定基线中，9.4.3 的默认配置是 48 位 VA、最多四级页表（VM 大小和块大小可以用模块参数调整）：PDB2 → PDB1 → PDB0 → PTB。每级用 9 位索引，每张表 512 项、每项 8 字节。以 X 的 GPUVA `0x0040_0000` 为例，四级索引依次是 `[47:39] = 0`、`[38:30] = 0`、`[29:21] = 2`、`[20:12] = 0`，页内偏移为 0。

叶子 PTE 除了地址，还带一组属性：VALID（bit 0）、SYSTEM（bit 1）、SNOOPED（bit 2）、EXECUTABLE/READABLE/WRITEABLE（bit 4～6）、FRAG（bit 7～11）、PRT（bit 51）、PDE-as-PTE（bit 54，用于大页）、TF（bit 56）和 MTYPE（bit 57～58）。地址字段的含义由 SYSTEM 决定：

```text
X 在 HBM：  PTE.addr = vram_base_offset + BO 在显存中的偏移，SYSTEM = 0，MTYPE = RW（默认值）
kernarg 在系统内存：PTE.addr = 该页的 DMA 地址（启用 IOMMU 时为 IOVA），SYSTEM = 1，SNOOPED = 1，MTYPE = UC
```

系统内存页逐页填自己的 DMA 地址，所以 GTT 对象可以由分散的物理页组成。另外，内核使用的 VMID 0 还有三种额外的地址窗口：FB 窗口把一段 MC 地址线性对应到显存；AGP 窗口把一段 MC 地址线性对应到系统总线地址；GART 是 VMID 0 的页表，用来映射分散的内核对象。在固定基线的 GC 9 路径上，AGP 窗口默认关闭，只有模块参数 `amdgpu_agp=1` 时才启用。用户 VMID 不经过这些窗口，系统内存页的 DMA 地址直接写在用户页表里。

### 2.2 本设备：三级页表与固定 Outbound 窗口

本设备的 GPUVA 只有 32 位，用三级页表：`[31:30]` 索引根表（只用 4 项），`[29:21]`、`[20:12]` 各索引 512 项。同一个 `0x0040_0000` 的三级索引是 0、2、0。叶子项沿用 AMDGPU 的位置：bit 0 VALID、bit 1 SYSTEM、bit 4/5/6 为 X/R/W，地址字段为 `[31:12]`。

```text
X 的第 0 页：PTE = 0x0020_0000 | VALID | R | W = 0x0020_0061
  SYSTEM = 0 → 地址字段是 VRAM 偏移 → GPU 物理地址 0x0020_0000 → VRAM

kernarg 页：PTE = 0x4100_2000 | SYSTEM | VALID | R = 0x4100_2023
  SYSTEM = 1 → 地址字段是 Host IOVA → GPU 物理地址 0x8000_0000 + 0x4100_2000 = 0xc100_2000
  → 公共物理入口判断落在 Outbound → 减去 0x8000_0000 → IOVA 0x4100_2000 → vfio-user DMA
```

GPU 物理空间也是 32 位：`[0, vram_size)` 为 VRAM，`[vram_size, 0x8000_0000)` 为不可路由的空洞，`[0x8000_0000, 0x1_0000_0000)` 为 2 GiB 的 Outbound 窗口。页表遍历、CP 管理域访问和 DMA 引擎都走同一个公共物理入口。具体规则见 [GPUVM 规格第 3.2、3.3 节](<./GPUVM 第一版规格.md#gpuvm-addresses>)。

### 2.3 取舍与代价

**地址宽度。** 32 位 GPUVA 来自 RV32 执行器：寄存器和参数块中的地址字段都是 32 位，三级页表已经能覆盖 4 GiB。代价是每个 VM 最多 4 GiB，也没有大页；AMD 的 PDE-as-PTE 和 FRAG 都不存在。

**系统内存怎样接入。** AMD 的 SYSTEM PTE 直接保存 48 位 DMA 地址。本设备的 GPU 物理空间只有 32 位，Host 内存只能挤进一个固定窗口，所以 SYSTEM PTE 中的 IOVA 还要再加窗口起点。**[INFERENCE]** 这个窗口最接近 AMD VMID 0 的 AGP 窗口：都是把一段地址线性换算成总线地址。差别在于 AMD 的 AGP 只服务内核上下文，而且默认关闭，用户 VMID 不依赖它；本设备的管理域和用户的 SYSTEM 页都依赖这个窗口。由此带来两个代价：

- Host 对象的 IOVA 必须小于 2 GiB，驱动因此设置 31 位 DMA mask（AMD 是 48 位）。在 `IOMMU=none` 下 IOVA 就是物理地址；客体内存超过 2 GiB 时，一致性 DMA 分配只能使用低端内存。
- 管理域直接使用 GPU 物理地址，相当于只保留了 AMD VMID 0 的 FB 和 AGP 两种线性窗口，没有 GART。内核对象因此必须占用一段连续的 GPU 物理地址（Host 对象就是一段连续的 IOVA），也无法用页表隔离。

**缓存属性。** 模拟器里没有 GPU 缓存，所有访问都直接读写后备存储，CPU 和设备看到的始终是同一份数据，所以本设备不需要 MTYPE 和 SNOOPED，release 时也不用回写。代价是无法演示 AMD 对显存用 RW、对系统内存用 UC 这类一致性取舍。

**`gpuvm=off` 只用于调试。** 关闭翻译后，用户 Kernel 可以访问 VRAM 首页和固件区以外的全部 VRAM，以及整个 2 GiB 的 IOVA 窗口。在当前的验证配置（1 GiB 客体内存、`IOMMU=none`）下，这包括全部客体内存，也包括 MQD、管理 Ring 和 IH。AMD 没有对应的模式：用户访问一律经过页表。

## 3. 地址空间身份：VM、VMID、PASID 与队列绑定

面试可能问：多个进程怎样隔离？VMID 只有 16 个，进程更多时怎么办？

### 3.1 AMD：PASID 是身份，VMID 只是硬件槽位

AMD 区分两种编号。**PASID** 属于进程的 GPUVM，在 VM 存在期间不变；IH 记录携带它，驱动按 PASID 找到进程，也按 PASID 发起 TLB 失效。**VMID** 是硬件上下文槽位的下标，每个槽保存一个页表根和一组控制寄存器，每个 hub 有 16 个。VMID 0 留给内核；MI300 这类纯计算 GPU 上，KFD 从 VMID 3 开始使用。

VMID 在队列驻留时才绑定。非 HWS 模式下，进程的第一条队列创建时 KFD 分配 VMID，建立 PASID 与 VMID 的对应，写入页表根并刷新 TLB；最后一条队列销毁时归还 VMID，VM 和页表仍然保留。HWS 模式下，`MAP_PROCESS` 包携带 PASID、页表根和 SH_MEM 配置，由 CP 中的调度固件安排 VMID。这样进程数可以多于 VMID 数，轮流占用槽位。

```text
AMD（非 HWS）
进程 P：PASID 0x8001 → amdgpu_vm（页表根在显存）
  第一条队列创建 → allocate_vmid：取空闲 VMID 9，建立 PASID 0x8001 ↔ VMID 9，写根，刷新 TLB
  MQD.cp_hqd_vmid = 9 → CP 用 VMID 9 访问 Ring、rptr、wptr
  最后一条队列销毁 → 归还 VMID 9；VM 与页表仍在，PASID 不变
```

CP 访问队列时也分两种上下文：读 MQD 使用 `CP_MQD_CONTROL` 中的 VMID（驱动保持为 0），访问用户 Ring 和 rptr/wptr 使用 `CP_HQD_VMID`，也就是队列所属的 VMID。

### 3.2 本设备：VMID 随队列驻留绑定，没有 PASID

本设备的 DRM 文件与 VM 一一对应。VM 在第一次 MAP 时建好根表和通知页，这时不占 VMID。用户 VMID 只有 1、2 两个，建队列时驱动才取一个空闲的写进 MQD，队列确认卸载后归还，绑定时机与 AMD 非 HWS 模式相同。`gpuvm=off` 时建队列也要占一个 VMID，用来标识队列来源。CP 访问队列时，管理域（MQD、管理 Ring、IH）直接使用 GPU 物理地址，用户域（Ring、描述对象、Signal、通知槽）按 MQD 中的 VMID 翻译。CP 每次访问前在本地窗口里显式写好访问域和 VMID，不按 `VMID == 0` 推断。

```text
本设备
DRM 文件 A：VM_A（页表根在 VRAM）
  第一次 MAP → vm_init()：建根表和通知页；不取 VMID，不失效
  QUEUE_CREATE → gpgpu_vm_attach()：取 VMID 1 → 写根 → 失效整个 VMID → 启用上下文
  MQD.vmid = 1 → CP 窗口按 VMID 1 访问 Ring
  QUEUE_DESTROY 确认卸载并消费旧 IH → gpgpu_vm_detach()：停用 → 失效整个 VMID → 清根 → 归还 VMID 1
  VM_A 与页表仍在；下次建队列时取到的可能是 VMID 2
```

TLB 项按 VMID 打标签，同一个编号会先后交给不同的 VM，所以取得和归还时都失效整个 VMID：取得时清掉上一个使用者可能留下的翻译，归还时不把本 VM 的翻译留给下一个。VM 不占编号时，TLB 里没有它的翻译，MAP、UNMAP 只写页表项，`vm_invalidate_range()` 直接返回，不发失效。

驱动用两个字段区分这两件事：`vm->ready` 表示 VM 已经建好通知页和页表，建队列、会话清理都看它；`vm->vmid` 只表示当前是否占着槽位，0 表示没有占用。设备和固件不需要配合修改：固件处理 `MAP_QUEUES`、设备激活 HQD 时，只检查 MQD 中 VMID 的上下文已经启用，不关心它是什么时候启用的。

### 3.3 取舍与代价

VMID 改为驻留时借用以后，页表根、TLB 标签、MQD 和故障记录仍然使用同一个编号，驱动不需要维护 PASID 到 VMID 的映射表。剩下的取舍有以下几点：

- **VM 的数量不再受 VMID 限制，同时驻留的队列仍然最多 2 条。** 用户 HQD 槽和用户 VMID 都是 2 个，每个 VM 最多一条队列，两个上限相等，VMID 不会成为额外瓶颈；三个进程轮流建队列的例子见 [GPUVM 规格第 5.1 节](<./GPUVM 第一版规格.md#gpuvm-context-tlb>)。AMD 每个 hub 有 16 个 VMID，HWS 模式下还能由固件轮换，进程数可以远多于槽位。
- **每次建队列、卸载队列都失效整个 VMID。** 队列重新驻留后，TLB 中没有本 VM 的翻译，要重新遍历页表。AMD 重新绑定 VMID 时同样要刷新。本设备的队列通常跑完一批任务才卸载，这部分开销可以忽略。
- **没有稳定身份。** IH 记录用 MQD 地址定位来源队列，不依赖 VMID，所以 VMID 改为驻留时绑定后，路由不受影响。但故障记录和上下文寄存器里的 VMID 只说明当时用的是哪个槽位；同一个编号会先后属于不同进程，单看编号判断不出属于哪个进程，按地址空间发起失效也要先查出当前槽位。AMD 用 PASID 解决这个问题。
- **三种编号不要混淆。** GPU 的 VMID 选择 GPU 页表；KFD 的 PASID 标识进程的 GPU 地址空间；SMMUv3 的 StreamID 以及可选的 SubstreamID（即 PCIe PASID）选择 IOMMU 上下文。本设备开启 SMMUv3 时，整个设备共用一个 StreamID，IOMMU 负责 IOVA 到物理地址这一级，GPU 页表负责 GPUVA 到 IOVA 这一级。

对应改进：[A1 引入 PASID](#item-a1)。

## 4. Linux 驱动的内存管理

面试可能问：驱动怎样分配 GPU 能用的内存，怎样建立映射？GPU 可能还在访问时，怎样安全地释放？显存不够时怎么办？

本节沿向量加法里两个对象的寿命，把驱动的内存代码逐段讲清：X 是放在 VRAM 的数组，kernarg 是放在 Host 的参数块。每一段先讲本设备，再讲 AMDGPU 的对应做法。

### 4.1 阅读顺序与对象寿命总图

驱动中与内存有关的代码，建议按下面的顺序读：

1. `gpgpu_drv.h` 的文件头，以及 `struct gpgpu_bo`、`struct gpgpu_vm`：对象关系、引用种类和锁的顺序；
2. `gpgpu_bo.c`：对象创建、句柄关闭、CPU 映射和 COPY；
3. `gpgpu_vram.c`：用 gpu_buddy 管理的 VRAM；
4. `gpgpu_dev.c` 中的 `gpgpu_dma_buf_alloc()`：Host 内存的分配和 Outbound 地址换算；
5. `gpgpu_vm.c`：页表、MAP/UNMAP、VMID 的取得与归还、会话清理；
6. `gpgpu_drm.c` 中的 `gpgpu_postclose()`：文件关闭时能否回收，不能回收时转为 orphan。

两个对象从创建到回收经过的步骤如下：

```text
               X（VRAM，68,012 字节）                       kernarg（Host，16 字节）
BO_CREATE      buddy 分配 0x2_0000 字节连续块并清零           dma_alloc_coherent 一页并清零
               phys_addr = VRAM 偏移，例如 0x0020_0000        phys_addr = 0x8000_0000 + IOVA
               引用：会话列表、GEM 句柄                       引用：会话列表、GEM 句柄
准备内容       COPY：设备 DMA 从 Host 暂存对象搬入            mmap 后 CPU 直接写（mmap 再持一个引用）
MAP            写 17 个叶子 PTE                               写 1 个带 SYSTEM 的叶子 PTE
               取得绑定引用                                   取得绑定引用
               VM 还不占 VMID，不发失效
```

### 4.2 对象模型、引用与锁

**本设备。** `struct gpgpu_bo` 记录对象种类（Host 或 VRAM）、应用请求的长度 `size` 和页对齐后的 `mapped_size`、存储（`host` 或 `vram_blocks`）、GPU 物理地址 `phys_addr`、绑定后使用的地址 `gpu_addr`，以及 `bound`、`permissions`、`users`。

对象的寿命由四类引用决定：会话列表、GEM 句柄、GPU 绑定、CPU mmap，它们都是 GEM 对象上的引用计数，最后一个放下时 `bo_free()` 归还存储。`users` 不是引用，而是“正在使用”的计数：队列的 Ring 和进度对象、进行中的 COPY 都会让它加一，非零时禁止解绑。

并发由一把设备级的 `dev->lock` 统一保护，`vm_serial` 再把建队列、MAP、UNMAP 串行化；等待设备完成时会释放 `dev->lock`，避免阻塞 IH 消费。创建句柄是一个典型的竞争点：`drm_gem_handle_create()` 返回前，句柄已经对其他线程可见，另一个线程可能立刻关闭它，而关闭回调 `bo_close()` 需要 `dev->lock`。所以 `gpgpu_bo_create()` 先取一个临时引用，解锁后再创建句柄，重新加锁后检查对象是否已被关闭。

### 4.3 存储从哪里来

**本设备。** 两种对象都在创建时一次分配一整块连续存储，之后不再移动：

```c
133	/* 分配存储：长度取页对齐与对齐要求中较大者，并向上取 2 的幂以满足对齐。 */
134	static int bo_storage_alloc(struct gpgpu_bo *bo, u64 alignment)
135	{
136		u64 size = roundup_pow_of_two(max_t(u64, bo->mapped_size, alignment));
137		int ret;
138
139		if (bo->kind == GPGPU_MEMORY_HOST) {
140			ret = gpgpu_dma_buf_alloc(bo->dev, &bo->host, size, alignment);
141			bo->phys_addr = bo->host.addr;

143		}
144		return gpgpu_vram_alloc(bo->dev, size, &bo->vram_blocks, &bo->phys_addr);
```

第 136 行先把长度取整到 2 的幂，这是为了借助“自然对齐”满足对齐要求：

- **Host 对象**交给 `gpgpu_dma_buf_alloc()`。它调用 `dma_alloc_coherent()`，检查返回的 DMA 地址整段落在 2 GiB 窗口内，再把 `0x8000_0000 + DMA 地址` 作为设备协议使用的 GPU 物理地址，最后清零。DMA API 保证一致性分配按“不小于请求长度的最小页阶”对齐，所以只要请求长度不小于对齐要求，返回的地址就已经满足对齐。
- **VRAM 对象**交给 `gpgpu_vram_alloc()`。它向 gpu_buddy 申请一个连续块，块长和对齐都等于这个 2 的幂，再经 BAR2 用 `memset_io()` 清零。gpu_buddy 只管理固件区之前的 60 MiB，首页预先占住，页表页也从同一个池中分配。

### 4.4 CPU 怎样读写对象

**本设备。** Host 对象只能整段、共享、不可执行地映射给用户态，由 `dma_mmap_coherent()` 建立。VRAM 对象不能映射，只能用 COPY 搬运：驱动给源、目的对象的 `users` 各加一，持 `dma_lock` 把两端的 GPU 物理地址写进 DMA 引擎，然后等完成中断，最长 5 秒。超时说明无法确认 DMA 是否已经停止，驱动置全局的 `dma_uncertain`，之后两端对象一直保留。

### 4.5 GPU 映射的建立

**本设备。** 库先为 X 选 GPUVA：在可分配区间里按首次适配找一段对齐、空闲的地址，然后调用 MAP。驱动内部依次执行：

```text
MAP(X, address = 0x0040_0000, perms = R | W)
  1. 检查：VM 未失败、没有存活队列、对象未绑定、地址区间合法且不与已有绑定重叠
  2. vm_init()（仅首次）：分配通知页 → 分配根表 → 写通知页的 PTE；不取 VMID
  3. bo->bound = true，取得绑定引用
  4. 逐页写叶子 PTE（共 17 页）：
       vm_leaf() 每页都从根开始，经 BAR2 读 L0、L1；中间级缺失就分配表页并写 PDE
       第 0 页写入 0x0020_0000 | VALID | R | W = 0x0020_0061
  5. vm_invalidate_range()：没有驻留队列，VM 不占 VMID，直接返回
       占有 VMID 时才发范围失效：wmb() → VPN_START = 0x400、VPN_END = 0x410
       → REQ = VMID 1 | RANGE → 读 ACK，必须等于 0x2
```

MAP 只能在没有存活队列时执行，所以第 5 步现在总是直接返回。设备要等建队列时 `gpgpu_vm_attach()` 写根、失效整个 VMID 并启用上下文之后，才会经这棵页表翻译 X。

**差异与代价。**

1. **失败时能否回滚。** AMD 把“登记映射”和“写页表”分开，写表失败时调用 `unmap_bo_from_gpuvm()` 撤销登记、清除已写的表项（个别清理步骤的错误会被忽略），尽量不留下半建立的映射。本设备先置绑定再写表，失败后不回滚。
2. **同步与异步。** AMD 可以把写表交给 SDMA 异步执行，用 fence 表示何时完成；本设备由 CPU 经 BAR2 同步写完，返回时页表已经生效。
3. **写入可见性。** AMD 的 CPU 经 BAR 写显存时会经过 HDP，HDP 可能暂存写入，所以 `mb()` 之后还要刷新 HDP，GPU 才能看到新页表。本设备的 BAR2 用 `pci_iomap()` 映射，没有 HDP 这一层；每次写入都是一条发往设备进程的 vfio-user 消息，与随后写 REQ 的消息走同一条通道、按发送顺序处理，`wmb()` 就够了。
4. **写表效率。** 本设备每写一页都从根读一次 L0、L1，17 页就是 34 次 BAR2 读和 17 次写；AMD 的页表游标只沿树走一遍。这只影响速度。
5. **GPUVA 由谁选。** 两侧都由用户态选址，内核只校验。本设备由库按首次适配选择，驱动检查区间并用链表查重叠；AMD 由 libhsakmt 管理地址区间，内核用区间树查重叠。

### 4.6 解除映射与释放

**本设备。** UNMAP 依次检查：VM 没有失败、没有存活队列、没有结果未知的 DMA，对象的 `users` 为零。然后清叶子 PTE（不分配表页，不会失败），放下绑定引用。UNMAP 和 MAP 一样只能在没有存活队列时执行，这时 VM 不占 VMID，TLB 里没有它的翻译，不必失效；占有 VMID 时才按对象的 VPN 范围失效，读到 ACK 后再放下引用。如果句柄早已关闭，还要同时放下会话列表的引用。存储在最后一个引用放下时，由 `bo_free()` 在 `dev->lock` 下归还。

“设备不再访问”是由协议保证的：队列存活期间整个 VM 冻结；队列排空并卸载之后，驱动停用上下文、失效整个 VMID 并归还编号，设备不可能再经这个 VM 访问任何对象；COPY 则由 `users` 保护。

### 4.7 页表与 VMID 的寿命

### 4.8 结果未知时怎样处理

驱动在四个地方记录“无法确认设备是否还在访问”，一旦记录，对应资源就一直保留：

- `vm->failed`：写 PTE 或失效的结果未知，VM 此后禁止修改，也禁止建队列；
- 队列的 `uncertain`：管理命令的结果未知；
- 设备的 `dma_uncertain`：某次 COPY 超时，影响整个设备；
- 会话的 `orphan`：文件关闭时设备可能还在访问，会话保留到设备确认停止。

orphan 会话只在设备确认停止，也就是驱动移除时才回收。AMD 的处理方式不同：fence 可以带着错误完成；任务超时触发 GPU 复位恢复，复位后 fence 全部完成，内存随之释放。

### 4.9 本节缺陷

每个缺陷写明根因、触发方式和影响，修法见[第 9.1 节](#review-fixes)。

<a id="item-d1"></a>

**D1 MAP 失败后，驱动与用户库的状态不一致（P0）。** 根因见第 4.5 节：驱动先置绑定再写 PTE，表页分配失败返回 `-ENOSPC` 时 VM 进入 failed，但对象仍然绑定。用户库只把 `EIO`、`ETIMEDOUT`、`ENOMEM` 当作“结果未知”，`ENOSPC` 被当作确定失败，于是库关闭了句柄并忘掉这个对象。之后该会话的 BO_CREATE、MAP、UNMAP 和建队列全部返回 `-EBUSY`，只能关闭文件。触发方式：连续分配 VRAM 对象，直到池中剩余不足一页，再 MAP 一个需要新表页的对象，例如一个落在新的 2 MiB 区段的对象。[D2](#item-d2) 让这个条件更容易出现。首次 MAP 时，`vm_init()` 中的分配（通知页、根表、通知页所需的表页）失败，同样会把 VM 置为 failed。

<a id="item-d2"></a>

**D2 表页永不回收，并与 BO 共用 VRAM 池（P1）。** 反复在不同区段 MAP、UNMAP 的会话，表页只增不减，最多约 8 MiB/VM，会挤占 BO 的空间并触发 D1。

<a id="item-d3"></a>

**D3 存储按 2 的幂取整（P2）。** 见第 4.3 节：X 只需 17 页却占 32 页。两侧的预先取整都可以去掉；Host 侧在直接映射且不经 CMA 时，分配器内部仍按页阶整块分配。

<a id="item-d4"></a>

**D4 卸载被 CP 拒绝后，队列和 VMID 一直被占用（P0）。** `gpgpu_queue_destroy()` 发命令前把队列置为 `UNLOADING` 并设置 `uncertain`。CP 明确拒绝（命令已发布、结果码是有效的失败码）时，驱动把队列标为 FAULTED，却没有清除 `uncertain`；之后每次 `QUEUE_DESTROY` 都在开头检查到 `uncertain`，直接返回 `-EBUSY`。CP 的拒绝有三种：

- `RECOVERY_REQUIRED`：队列没有排空。驱动检查 R == W 之后、CP 检查之前，另一个线程只要取了号（W 加一）就会触发。这时 HQD 仍在运行，驱动却标成了 FAULTED。
- `MQD_FAULT`：有两个来源。一是 CP 读不到 W，记录 RING 错误；二是 CP 已停止取包、把进度保存到 MQD 时写入失败，记录 SAVE 错误。两种情况下槽都仍然占用。
- `NOT_MAPPED`：CP 并没有装载这条队列。

后果依次是：队列永远不会变成 dead → 文件关闭时会话因“有存活队列”转为 orphan → orphan 只在设备停止时回收 → VMID、页表和对象一直被占用。VMID 本应在卸载成功后归还，这条队列卡住时就一直占着；发生两次之后，全设备再也分不到 VMID。

## 5. TLB 与翻译失效

面试可能问：GPU 的 TLB 怎样组织？页表改了以后，怎样保证设备不再使用旧翻译？失效请求和正在进行的访问怎样避免竞争？

### 5.1 AMD：两级翻译缓存，按 PASID 失效

AMD 的翻译缓存分两级。UTCL1 靠近各个访存客户端，只保存最终翻译；UTCL2 也叫 VM L2，由一个 hub 内的客户端共享，既保存最终翻译，也保存 PDE，帮助 Walker 少读几级页表。PTE 的 FRAG 字段表示这一页属于一段连续、属性相同、长度为 2^(12+FRAG) 字节的区域，L1 用一项就能覆盖整段，这是扩大 TLB 覆盖范围的主要手段。

**[BOUNDARY]** MI300X 各级 TLB 的容量、相联度和替换策略没有公开资料。gem5 的 Vega TLB 默认是 64 项全相联、LRU 替换，另有 64 项页遍历缓存；这是模拟器的可配置参数，不能据此推断真机。

失效以 VMID 为单位。每个 hub 有 18 个失效引擎，REQ 中同时写入目标 VMID 位图、刷新类型，以及要清除的缓存种类（L1 PTE、L2 PTE、L2 PDE0/1/2）；ACK 按 VMID 逐位确认。失效引擎虽然有地址范围寄存器，驱动初始化时却把它设成全范围，所以实际总是失效整个 VMID。计算任务走 `amdgpu_vm_flush_compute_tlb()`：页表自上次刷新以来没变（`tlb_seq` 相同）就跳过，否则对每个 XCC 按 PASID 发起失效。KFD 在建立映射后刷新；9.4.2 及以后，解除映射后也刷新，类型为 heavyweight。

AMD 允许队列运行时修改映射。保证安全的是顺序：先等页表更新的 fence，再刷新 TLB，最后才撤销 DMA 映射、释放存储（见第 4.6 节）。

### 5.2 本设备：单级 TLB，按 VPN 范围同步失效

本设备只有一级 TLB，CP 窗口和执行器共用：64 组 × 4 路，组号为 VPN % 64，标签是 VMID 加 VPN，只缓存叶子翻译，遍历失败的结果不进 TLB。组内的使用顺序和替换过程见 [GPUVM 规格第 5.2.1 节](<./GPUVM 第一版规格.md#gpuvm-tlb-lru>)。命中、未命中和替换三个计数由全设备共用。

失效寄存器 `VM_INV_REQ` 同时写入 VMID 位图和 RANGE 位，配合 `VM_INV_VPN_START/END` 只清一段 VPN；设备在这次寄存器写入内完成清除，写好 ACK 后返回。以下情况整体拒绝、不清任何项，ACK 只置 ERROR：REQ 带保留位、位图为空、范围非法，或者所选 VMID 还有激活的 HQD 或在途访问。驱动在 MAP、UNMAP 时只失效这个对象的 VPN 范围，在启用、停用上下文时失效整个 VMID。由于队列存活期间不允许 MAP/UNMAP，失效总是发生在 VM 没有激活队列的时候。

以 X 为例：VPN `0x400`～`0x410` 落在第 0～16 组。另一个进程把自己的对象映射到同样的 GPUVA 时，会落进同样的组，与 X 争用每组的 4 路，因为组号的计算没有用到 VMID。

### 5.3 同步失效为什么成立：模拟器的并发模型

真实硬件上，失效请求到达时可能有翻译正在进行，用旧页表查到的结果随后又被填回 TLB。AMD 用 ACK 加 heavy flush 的语义，以及 fence 和释放顺序来处理这个问题。本设备的失效在一次寄存器写入内就完成，靠的是 QEMU 设备模型的执行方式：

```text
设备侧（持 QEMU 主锁 BQL）                         Host 驱动
vm_translated_rw()：accesses++
  gpgpu_phys_rw() → 发出 vfio-user DMA 请求 ──────▶
  等待回复；这期间收到的 Host 命令只完整接收、暂存      写 VM_INV_REQ → 被暂存
  ◀────────────────────────────── DMA 回复
accesses--，本次访问结束
之后处理暂存的命令：vm_invalidate()                ← 此时 accesses 一定为 0
```

设备在等待 DMA 回复时一直持有主锁，期间到达的 Host 命令只是收下暂存，不进入设备回调，等这次访问结束后再处理。所以 Host 写 `VM_INV_REQ` 时，在途计数 `accesses` 一定是 0。`gpuvm.c` 和 `phys.c` 的注释说 DMA 期间“可能暂时释放主锁”，与实际不符，计数检查在当前实现中只起防御作用。

会跨越 Host 写入的过程只有两种：一是按定时器分段推进的 Dispatch，两段之间设备会处理 MMIO；二是 CP 为一个包做的多次窗口访问，两次访问之间 CP 线程不持锁。这两种过程都只在队列的 HQD 激活时发生，所以起实际保护作用的，是失效检查中的“所选 VMID 没有激活的 HQD”，再加上驱动“先卸载队列、再改映射”的协议。

### 5.4 取舍与代价

- **单级、只缓存叶子。** 结构简单，组相联加 LRU 足以讲清 TLB 的基本行为。代价是每次未命中都要读 3 次表项，没有 PDE 缓存；也无法演示 AMD 失效时要分别选择 L1、L2、PDE 各级的原因。
- **没有 FRAG。** 256 项 × 4 KiB，最多覆盖 1 MiB。AMD 靠 FRAG 让一项覆盖一整段连续内存。
- **组号不含 VMID。** **[INFERENCE]** 库对每个进程都从同一个区间起点开始首次适配，两个进程的对象往往拿到相同的 GPUVA，于是落进相同的组，每个 VM 在这些组里实际只分到约一半的路。
- **按范围失效。** 粒度比 AMD 驱动的实际用法更细，解绑一个对象不会清掉同一 VM 其他对象的翻译；在模拟器中扫描全部 256 项的成本可以忽略。驱动现在只在没有驻留队列时改映射，这时 VM 不占 VMID，范围失效实际不会发出；它留给 [A2](#item-a2) 在队列存活期间改映射时使用，设备侧由寄存器 QTest 覆盖。
- **冻结映射。** 因为队列存活期间不改映射，同步失效就不需要 fence 和刷新类型。代价是运行中不能改映射，见 [A2](#item-a2)。
- **计数全设备共用。** 无法区分是哪个 VMID 或哪个访存主体造成的未命中。

对应改进：[A2](#item-a2)、[A3](#item-a3)，后续方向 [E2](#item-e)。

## 6. 访存故障

面试可能问：GPU 访问一个没有映射的地址会怎样？能像 CPU 缺页那样恢复吗？

### 6.1 AMD：可重试故障与不可恢复故障

故障由 UTCL2 和 Walker 检测，经 IH 上报：记录中带故障页地址、是否可重试、是否为写、VMID 和 PASID；驱动再读 `VM_L2_PROTECTION_FAULT_STATUS`，其中有客户端编号（CID）、读写方向（RW）、WALKER_ERROR、PERMISSION_FAULTS、MAPPING_ERROR 和 MORE_FAULTS 等字段。

- **可重试故障**：硬件先挂起这次访问，驱动经 `amdgpu_vm_handle_fault()` 进入 `svm_range_restore_pages()`，检查 CPU 侧的 VMA 和权限，必要时迁移页面，补好 PTE，然后硬件重试，Kernel 继续执行。9.4.3 默认关闭重试（`noretry` 为 1），可以用参数打开。
- **不可恢复故障**：没有被调试器接管时，KFD 驱逐这个进程在该设备上的全部队列，再发出内存异常事件。ROCr 的 `VMFaultHandler` 在没有自定义处理器接管时最终调用 `abort()`。

### 6.3 取舍与代价

- **为什么不恢复。** 本设备的对象都在创建时分配好存储，并在队列创建前映射完毕，合法程序的访问一定有映射，故障只说明程序有错，停下来报告就够了。要支持恢复，执行器需要停在出错的指令处并能重放，驱动需要按需分配后备存储，改动很大，见 [E4](#item-e)。
- **停止范围。** AMD 在普通路径上停掉进程在该设备上的全部队列，本设备只停源队列。目前每个 VM 只有一条队列，两者效果相同；以后允许一个 VM 有多条队列时，应同时停掉同一 VM 的其他队列。
- **记录方式。** 本设备每槽只留首次故障，后续故障丢失；AMD 的 IH 记录逐条上报，状态寄存器另有 MORE_FAULTS 标记。教学上首次故障已经足够定位问题。

## 7. 完成通知与事件等待

面试可能问：Kernel 执行完以后，Host 怎样得知？等待的线程怎样避免错过唤醒？

### 7.1 AMD：自动复位事件与 `event_age`

`amd_signal_t` 为 64 字节、64 字节对齐：偏移 8 是信号值，偏移 16 是 `event_mailbox_ptr`，偏移 24 是 `event_id`。AQL 包完成时，CP 先执行 release，再原子递减信号值；如果设置了 mailbox，就把事件编号写入事件槽并产生中断。KFD 为每个进程准备 4,096 个 8 字节的事件槽，共 32 KiB。中断到达后，先按 PASID 找到进程，再按记录中的部分事件编号查找事件；编号不够用时，扫描所有已写入的槽。

信号事件是自动复位的：事件被置位时如果已有等待者，就唤醒它们并恢复为未置位；新的等待者开始等待时，会消费掉已置位的状态。另外，每次置位都把 `event_age` 加一，等待者可以带上自己上次看到的 age，age 变了就立即返回。所以 ROCr 可以用同一个事件服务许多次派发，既不会错过唤醒，也不会因为旧的置位状态而空转。ROCr 创建信号事件时传入 `manual_reset=false`。

### 7.2 本设备：一次性事件

本设备的 Signal 为 24 字节，CP 是唯一的写者，完成时把值从 1 写成 0。每个 VM 有一页 Host 通知页，映射在固定 GPUVA `0xffff_f000`，共 512 个 8 字节槽。完成顺序是：Signal → 通知槽 → IH 记录 → 包头改回 INVALID → 回报消费进度。IH 记录带类型、HQD 槽、MQD 地址和事件编号；驱动按 MQD 地址找到队列，再核对事件编号和通知槽内容，把事件置为 NOTIFIED 并唤醒等待者。

事件的状态只前进不回退：PENDING → NOTIFIED 或 FAILED；等待不消费状态，同一次完成可以唤醒多个等待者。规则见 [GPUVM 规格第 6.1 节](<./GPUVM 第一版规格.md#gpuvm-signal>)。

### 7.3 差异与代价

- **单写者与原子递减。** CP 是唯一更新 Signal 的一方，写 0 就够了；需要多个更新者时再扩展原子操作。
- **没有缓存。** 本设备没有 GPU 缓存，完成时不需要像 AMD 那样先 release 回写，结果写回后就对 Host 可见。
- **来源怎样识别。** 本设备用 MQD 地址定位队列，AMD 用 PASID 加事件编号。引入 PASID 见 [A1](#item-a1)。
- **事件语义。** 一次性事件本身没有问题，问题在运行时把它当成可复用的事件用，见下面的 D7。

<a id="item-d7"></a>

**D7 同一运行时连续派发时，等待退化为忙循环，故障只报超时（P0）。** 运行时只在第一次派发时创建一个事件，之后每次派发都把同一个事件编号和通知槽写进 Signal。第一次派发完成后，事件永远停在 NOTIFIED。从第二次派发起，只要 Kernel 的运行时间超过约 200 μs 的主动轮询期：

```text
wait_signal()
  主动轮询 Signal 约 200 μs，仍未完成
  → gpgpuKmtWaitEvent()：事件已是 NOTIFIED，ioctl 立即返回成功
  → 回到开头复查 Signal，仍未完成 → 再次调用 ioctl → 立即返回 → ……
```

等待变成了反复调用 ioctl 的忙循环。如果第二次派发的 Kernel 访存出错，Signal 不会归零，`gpgpu_fail_queues()` 只把 PENDING 的事件置为 FAILED，这个已经 NOTIFIED 的事件不受影响，等待方要一直空转到期限，最后拿到的是 `WAIT_TIMEOUT`，而不是 `WAIT_FAILURE`；期限为无穷时则永不返回。另外，如果建队列成功、建事件失败，`rt->queue` 已经设置而 `rt->event` 为空，下一次派发在写 Signal 时会解引用空指针。

当前验收没有暴露这个问题：示例程序为每个计算单独建立运行时，只派发一次就销毁。触发方式：在同一个运行时上连续调用两次 `gpgpu_rt_dispatch()`，用一个运行超过 200 μs 的 Kernel，`strace` 能看到第二次等待中的 `EVENT_WAIT` 调用次数随运行时间增长；让第二次派发访问非法地址，可以看到返回超时。

## 8. Kernel 启动状态

面试可能问：GPU 线程启动时，怎样知道自己的编号、工作组大小和参数地址？

```text
     只建中间级、不写叶子；失败时返回 -ENOSPC，对象仍未绑定，VM 不进入 failed
  4. 置 bound，取得绑定引用
  5. vm_set_ptes()：只写叶子，不再分配表页，不会因为空间不足而失败
  6. 占有 VMID 时范围失效（现在 MAP 时不占，直接返回）；只有失效的结果未知时，才把 VM 置为 failed
```

用户库不用改：`ENOSPC` 本来就按确定失败处理，修复后两侧的理解一致。第 3 步失败时已经建好的空表页留在 VM 中，随 D2 的回收一起处理。这与 AMD `map_bo_to_gpuvm()` 的“登记、写表、失败撤销”目标相同：要么完整建立，要么什么都没改。验证：把 VRAM 用到只剩不足一页，再 MAP 一个落在新 2 MiB 区段的对象，应得到 `-ENOSPC`；释放一个对象后再次 MAP 应成功；三个计算示例仍通过。

**D2：表页按引用计数回收，或者设配额。** 推荐计数回收：每张表页记录有效项个数；UNMAP 清完叶子、读到失效 ACK 后，个数降为 0 的 L2 表页先清掉 L1 中指向它的 PDE，再释放；L1 同理。顺序是“清叶子 → 失效 → 清 PDE → 释放表页”。本设备的 TLB 不缓存 PDE，清 PDE 后不必再失效；加入 PDE 缓存（A3）后，释放前还要再失效一次。更简单的替代做法是每个 VM 的表页设上限，超过时 MAP 在改动任何状态之前就返回 `-ENOSPC`。验证：在 64 个不同的 2 MiB 区段循环 MAP、UNMAP，结束后仍能分配到与开始时相同大小的对象。

**D3：去掉预先取整。** 请求长度改为 `max(mapped_size, alignment)`，不再取 2 的幂：

- VRAM：`gpgpu_vram_alloc()` 目前把长度同时当作 `min_block_size` 传给 gpu_buddy，而 buddy 要求这个参数是 2 的幂，17 页会被直接拒绝。所以要把两者分开：长度传请求长度，`min_block_size` 传 `PAGE_SIZE`。带连续标志时，buddy 在内部取整、分配后裁掉多余部分，块的起点仍按取整后的长度对齐，不小于对齐要求；清零只清请求的长度。
- Host：把同样的长度直接交给 `dma_alloc_coherent()`，对齐由 DMA API 的保证提供。

验证：X 的 VRAM 实际占用 17 页；Ring 等有对齐要求的对象地址仍满足对齐；三个计算示例仍通过。

> **[SOURCE]** 本仓库 `0e7b8e7`：长度与 `min_block_size` 传同一个值，见 [gpgpu_vram.c 第 45～46 行](vscode://vscode-remote/wsl+Ubuntu/home/book/1.project/gpu_study/4.experiments/gpu-study-qemu/software/gpgpu/linux/gpgpu_vram.c:45:1)。Linux `248951dd`：`min_block_size` 必须是 2 的幂，见 [buddy.c 第 1331～1332 行](vscode://vscode-remote/wsl+Ubuntu/home/book/1.project/gpu_study/2.%E6%BA%90%E7%A0%81/linux/drivers/gpu/buddy.c:1331:1)。

**D4：按 CP 返回的结果分别收尾。**

```text
UNMAP_QUEUES 的结果
  OK                 → 消费旧 IH → 放下 Ring、进度的 users → 标记 dead（不变）
  从未发布           → 恢复原状态（不变）
  RECOVERY_REQUIRED  → 队列仍在运行：清 uncertain，恢复原状态，返回 -EBUSY，调用者排空后重试
  MQD_FAULT          → CP 已记录 RING 或 SAVE 错误：清 uncertain，置 FAULTED；重试时 CP 按“已出错”的路径卸载，
                       能否成功取决于 MQD 所在存储是否恢复可写
  NOT_MAPPED         → CP 并没有装载这条队列：消费旧 IH 后按已卸载回收
  结果未知           → 保持 UNLOADING 与 uncertain，资源全部保留（不变）
```

验证：一个线程卸载队列的同时，另一个线程取号，第一次卸载应返回 `-EBUSY` 且队列仍可用；排空后重试成功，VMID 随即归还，其他会话可以建队列。

**D5：DMA 没有启动时撤销计数。** 在 `gpgpu_bo_copy()` 中记录 DMA 是否真的启动；没启动（设备已移除、已故障或已有结果未知的 DMA）就无条件撤销两端的 `users`。全局 `dma_uncertain` 本身仍然保留，要靠第四阶段的复位恢复（[E5](#item-e)）确认 DMA 引擎已停止后才能清除，对应 AMD 中任务超时后的复位恢复。

**D6：只冻结影响 GPU 映射的操作。** 去掉 `gpgpu_bo_create()` 中对存活队列的检查，保留对 VM failed 的检查。关闭未绑定对象的句柄本来就不受限制。MAP、UNMAP 的放开见 A2。验证：队列存活期间 BO_CREATE 成功，三个计算示例仍通过。

**D7：每次派发使用新事件。** 最小修法只改运行时，不改协议：

```text
gpgpu_rt_dispatch()
  1. rt_ensure_queue() 只建队列，不再建事件
  2. EVENT_CREATE，得到新的事件编号和通知槽地址
  3. 写参数块；写 Signal：value = 1，event_id 与 mailbox 取自新事件
  4. Reserve → Publish → WaitSignal(signal, 新事件)
  5. 成功后 EVENT_DESTROY。Signal 先归零、IH 记录还没被驱动消费时，WaitSignal 已经返回而事件仍是
     PENDING，EVENT_DESTROY 返回 -EBUSY；这时把事件记入 rt 的待回收列表，下次派发开始时再销毁
     失败或超时：同样记入待回收列表，rt_destroy() 在队列卸载后统一销毁
```

每次派发多两次 ioctl。运行时是同步派发，待回收的事件在下一次派发前销毁，占用的通知槽很少。故障时等待的是新建的、处于 PENDING 的事件，`gpgpu_fail_queues()` 会把它置为 FAILED，等待方得到 `WAIT_FAILURE`；建队列与建事件分开以后，半初始化的问题也不存在了。更接近 AMD 的做法是让驱动支持自动复位和 `event_age`：`EVENT_WAIT` 带上次看到的 age，通知时 age 加一，等待者发现 age 变化就立即返回并把状态消费回 PENDING；队列出错时不论事件处于什么状态都置为 FAILED。这需要修改 UAPI，列为 P2。验证：同一运行时连续派发两次，第二次等待中不再出现随运行时间增长的 `EVENT_WAIT` 空转；让第二次派发访问非法地址，返回 `WAIT_FAILURE`；三个计算示例仍通过。

### 9.2 设计升级草案

<a id="item-a1"></a>

**A1 引入 PASID（P2）。** 目标是对齐 AMD 非 HWS 模式的结构：页表和进程身份始终属于进程，VMID 只在队列驻留期间借用。借用 VMID 这一半已经实现，不改设备和固件，协议版本不变，现状见[第 3.2 节](#review-identity)；剩下的是稳定身份 PASID。

做法是由驱动为每个 VM 分配一个 16 位编号，VM 存在期间不变，写进 MQD 的保留字段，再由 CP 带进 IH 记录和故障记录。固件现在要求 MQD 的保留字段为 0，设备也拒绝保留字段非零的 IH 记录，这两处检查和记录的生成都要改，需要协议版本 5。IH 仍可按 MQD 地址路由，PASID 主要用于诊断和按地址空间失效。这里的 PASID 是 GPU 侧的进程身份，不是 SMMUv3 使用的 PCIe PASID。验证：同一会话先后两次建队列、拿到不同的 VMID 时，故障记录中的 PASID 不变；三个计算示例仍通过。

> **[SOURCE]** 本仓库 `0e7b8e7`：保留字段必须为 0，见 [mgmt.c 第 77～79 行](vscode://vscode-remote/wsl+Ubuntu/home/book/1.project/gpu_study/4.experiments/gpu-study-qemu/software/gpgpu/firmware/mgmt.c:77:1)、[hw/gpgpu/irq/ih.c 第 58～59 行](vscode://vscode-remote/wsl+Ubuntu/home/book/1.project/gpu_study/4.experiments/gpu-study-qemu/hw/gpgpu/irq/ih.c:58:1)。AMD 对应做法见第 3.1 节。

<a id="item-a2"></a>

**A2 队列存活期间允许修改映射（P1）。** 目标是对齐 AMD 的语义：只保护队列自身使用的对象，其余对象在计算期间也可以 MAP、UNMAP。

```text
队列存活期间 UNMAP(Y)（Y 不是 Ring 或进度对象，users == 0）
  驱动：清 Y 的叶子 PTE → REQ = VMID | RANGE → 读 ACK
  设备：失效不再因 HQD 激活而拒绝；REQ 在主锁下处理，不会落在一次访问的中途
  此后 Kernel 若再访问 Y → UNMAPPED 故障 → 停队列（与 AMD 相同，由应用保证不解绑正在使用的对象）
队列存活期间 MAP(Z)：写 PTE 后照常范围失效（设备不缓存失败的遍历，这次失效只为保持对称）
```

改动：设备的失效检查去掉“HQD 激活”这一项（上下文寄存器的写入仍保留忙检查），`accesses` 只作断言；驱动去掉 MAP、UNMAP 和 BO_CREATE 中对存活队列的检查（同时解决 D6），保留 `bo->users` 检查，它的作用相当于 AMD 的 `queue_refcount`；用户库释放对象时对“存在队列”的检查也要同步放开。需要同步修改 QTest 中“队列激活时失效被拒绝”的断言，以及 GPUVM 规格第 1.2、5.2 节和硬件手册第 17 章；设备语义变化，需要协议版本 5。风险：分段推进的 Dispatch 可能在两段之间看到映射变化，之后的访问报故障，这与 AMD 一致。CP 处理一个包时会读 Ring、进度和描述对象，并写 Signal 和通知槽：Ring 和进度受 `users` 保护；通知页由驱动内部映射，应用无法解绑；描述对象和 Signal 不受保护，应用在派发期间解绑它们，CP 访问失败，队列以错误停止。AMD 同样由应用管理信号和代码对象的寿命。验证：长时间运行的 Kernel 执行期间 UNMAP 一个无关对象，成功且结果正确；执行期间 UNMAP 输出数组，报 UNMAPPED 故障；三个计算示例仍通过。

<a id="item-a3"></a>

**A3 TLB 分层（P2）。** 目标是用最小的改动体现 AMD 的 UTCL1/UTCL2 加 PDE 缓存结构。

```text
gpgpu_user_rw(访问主体 = CP 窗口 / 执行器取指 / 执行器数据, VMID, GPUVA)
  → 该主体的 L1：8 项全相联，标签 VMID + VPN；命中即返回
  → L2：现有的 64 组 × 4 路；命中后填回 L1
  → PDE 缓存：16 项，标签 VMID + GPUVA[31:21]，保存 L2 表页地址；命中只需读 1 次叶子项
  → 全部未命中：完整遍历，读 3 次表项
VM_INV_REQ：同一次写入内清除 L1、L2，并清除该 VMID 的 PDE 缓存
ROOT 或 ENABLE 改变：设备自动清除该 VMID 的 PDE 缓存
```

`gpgpu_user_rw()` 需要增加“访问主体”参数，调用点在 CP 窗口和执行器的取指、数据访存。现有三个计数保持 L2 的含义，MISSES 仍等于 L2 未命中、需要查页表的次数，QTest 中按 MISSES 和 EVICTIONS 写的断言继续成立；L1 命中数和 PDE 缓存命中数用 `0x092c` 起的空闲偏移新增。PDE 缓存只保存有效的 PDE，驱动新建 PDE 时原位置一定无效，所以 MAP 不会留下旧的目录翻译；D2 释放表页之前必须先失效。新增寄存器需要协议版本 5。对照 AMD：失效请求可以分别选择 L1 PTE、L2 PTE 和 PDE 各级（第 5.1 节）。验证：QTest 中反复访问同一页，L1 命中数增加而 MISSES 不变；失效后再访问，各级都未命中；现有 TLB 用例仍通过。

### 9.3 后续方向

- **E1 GPU 物理地址与 PTE 地址字段扩宽。** PTE 地址字段扩到 `[47:12]`，SYSTEM 页直接保存 IOVA，不再经过窗口，DMA mask 随之放宽；GPUVA 可以继续保持 32 位。改动遍及协议各层。
- **E2 FRAG 大页。** PTE 的 bit 7～11 目前是保留位，正好是 AMD FRAG 的位置；buddy 分配的连续块按 2 的幂对齐，已经满足 FRAG 对连续和对齐的要求。需要库按片段大小对齐 GPUVA，遍历时接受这些位，TLB 项记录覆盖长度。
- **E3 TTM 驱逐与迁移。** 搬移存储之前必须先停止访问，所以要先具备队列的抢占与恢复（E5）。范围见[大纲的 GPUVM 扩展](<./QEMU GPGPU 实验大纲.md#gpuvm-advanced-extension>)。
- **E4 可恢复缺页。** 执行器需要停在故障指令处并能重放，驱动需要按需分配后备存储。范围同上。
- **E5 抢占、强制中止与复位恢复。** 属于第四阶段，也是清除 D5 中全局 `dma_uncertain` 的前提，见[大纲的异常恢复扩展](<./QEMU GPGPU 实验大纲.md#stalled-task-recovery-extension>)。
