### 1.2 贯穿例子：一次向量加法经过的路径

应用计算 `Z[i] = X[i] + Y[i]`，共 17,003 个 `float`。Host CPU 负责准备数据和提交任务，GPU Kernel 读取 X、Y 并写 Z。本文对照的 AMD 环境是外部 Host CPU 加 MI300X 独立 GPU；本设备则由 QEMU 模拟，不把它的简化设计当作 MI300X 的硬件行为。

下面使用教学取值，不是实测日志：X 的 GPUVA 为 `0x0000_ffff_8a40_0000`，与用户库为它取得的 CPU 地址相同；后备存储放在 VRAM 偏移 `0x0020_0000`。CPU 地址在这里仅作 `PROT_NONE` 占位，不能直接读写 X 的内容。参数块（kernarg）放在 Host 内存，假设所在页的 IOVA 为 `0x4100_2000`；块内保存 X、Y、Z 的 GPU 地址和元素数，每项 8 字节，共 32 字节。Kernel 先读参数，再按数组地址访存。Ring 保存 AQL 包，进度对象保存提交与消费位置，Signal 保存任务完成值；这些共享对象也放在 Host。通知页由库在 Open 时创建、映射并登记，不使用固定 GPUVA。

下图只比较执行路径，不表示两侧使用相同的地址编码、页表格式或硬件布局。

```text
本设备（gpuvm=on）
应用 → lib/rt → lib/kmt → DRM 驱动：BO_CREATE 分配存储，MAP 写页表，QUEUE_CREATE 装载队列
  → 应用写 AQL 包，8 字节写 Doorbell
  → RV64 CP：按管理域（GPU 物理地址）读 MQD，按队列的 VMID 读 Ring 与描述对象
  → RV64 执行器：CSR 给出线程坐标，a0 = kernarg 的 GPUVA，取指与数据访问经 GPUVM
  → GPUVM：TLB（64 组 × 4 路）→ 四级页表 → GPU 物理地址
  → 公共物理入口：VRAM；或 Outbound（0x8000_0000 + IOVA）→ PCIe DMA → Host 内存
  → CP 依次写 Signal、通知槽、IH 记录 → 驱动唤醒等待者

AMD（MI300X）
应用 → HIP/ROCr → libhsakmt → KFD/AMDGPU：分配 BO，用户态选 GPUVA，驱动写页表
  → 应用写 AQL 包，写 Doorbell
  → MEC：用 VMID 0 读 MQD，用队列的 VMID 读 Ring
  → CU 上的 Wave：SGPR/VGPR 预置启动信息，按 GPUVA 访存
  → UTCL1 → UTCL2（含 PDE 缓存）→ 四级页表 → 物理地址
  → HBM；或 PTE 中的 DMA 地址 → PCIe（经 IOMMU）→ Host 内存
  → 完成信号原子递减，写事件槽，IH 记录带 PASID → KFD 唤醒等待者
```

两条路径都经过队列提交、CP 取包、执行单元访存、多级页表翻译和完成通知。差别集中在物理地址布局、地址空间身份、翻译与任务的同步方式，以及驱动怎样管理存储，后面各节分别展开。

### 1.3 评审结论

1. **翻译主路径的对象关系相近。** 两侧都按 VMID 选择页表根，用多级页表建立映射，用 TLB 缓存叶子翻译，并通过 REQ/ACK 确认失效。本设备的 GPUVA 已是 48 位、页表为四级，但 GPU 物理地址仍为 32 位，Host 访问依赖固定 Outbound 窗口；PTE 只采用 AMDGPU 的部分位位置，不兼容完整硬件格式，见[第 2 节](#review-address)。
2. **软件 VM 与硬件驻留已经分开。** VMID 随队列驻留借用和归还，软件 VM 与页表可以继续保留。本设备仍只有两个用户 VMID，没有独立的稳定 PASID，也没有固件驻留轮换，见[第 3 节](#review-identity)。
3. **驱动内存管理单独阅读。** 固定存储、对象寿命及 AMDGPU/TTM/fence 对照见[Linux 驱动内存管理](<./Linux 驱动内存管理.md>)。这部分是实现讲解，不列为待确认规格。
4. **队列存活期间可以改映射，但任务寿命仍须由应用配合。** 本设备在占有 VMID 时按对象范围同步失效，依靠 QEMU 回调与主锁避免旧遍历在 ACK 后重新填入。驱动保护 Ring、进度对象和通知页，却不追踪任意 Kernel 使用的数组、代码和参数；应用须确认不再访问后才能解绑，见[第 5 节](#review-tlb)。

剩余方案分为对齐 AMD 的设计升级和后续扩展，见[第 9 节](#review-items)。完成通知与一次性事件的现行配合、Kernel 启动信息的差异，分别见[第 7 节](#review-event)、[第 8 节](#review-startup)。

## 2. 地址翻译与物理地址空间

面试可能问：一个 GPUVA 怎样变成物理地址？GPU 怎样访问主机内存？

### 2.1 AMD：四级页表，系统内存页直接填 DMA 地址

MI300X 上的 Kernel 已拿到 X 的 GPUVA，访存单元还需要知道“这次访问属于哪个地址空间”。队列携带的 VMID 选择页表根；TLB 未命中时，页表遍历器（Walker）从这个根开始逐级查表。

固定 Linux 基线为 GC 9.4.3 选择 48 位 VA、最多四级页表，默认路径为 PDB2 → PDB1 → PDB0 → PTB；VM 大小和块大小还可以用模块参数调整。前三层目录项指向下一张表，最后一层 PTE 指向实际数据页。每级用 9 位索引，一张表有 512 项，每项 8 字节，正好占一页 4 KiB。以 X 的 GPUVA `0x0000_ffff_8a40_0000` 为例：

```text
VMID → 页表根
  → PDB2[0x1ff]  GPUVA[47:39] = 0x1ff，找到 PDB1
  → PDB1[0x1fe]  GPUVA[38:30] = 0x1fe，找到 PDB0
  → PDB0[0x52]   GPUVA[29:21] = 0x52，找到 PTB
  → PTB[0]       GPUVA[20:12] = 0，取得数据页地址和属性
  → 数据页地址 + GPUVA[11:0]（本例偏移为 0）→ 访问 X[0]
```

PTE 需要回答三个问题：这一页是否有效、允许什么访问、实际存储在哪里。VALID 在 bit 0，执行／读／写权限在 bit 4～6；SYSTEM（bit 1）决定地址字段指向显存还是系统内存，SNOOPED（bit 2）和 MTYPE（bit 57～58）描述缓存与一致性属性。本例采用普通本地 BO 的默认属性和普通系统内存属性：

```text
X 在 HBM：
  PTE.addr = vram_base_offset + BO 在显存中的偏移
  SYSTEM = 0，MTYPE = RW（本地 BO 的默认缓存类型）

kernarg 在系统内存：
  PTE.addr = 该页的 DMA 地址（启用 IOMMU 时为 IOVA）
  SYSTEM = 1，SNOOPED = 1，MTYPE = UC（不缓存）
```

MTYPE 的 `RW` 是缓存类型的名称，和 PTE 中独立的读、写权限不是一组位。后文还会用到 FRAG（bit 7～11，连续片段信息）和 PDE-as-PTE（bit 54，让目录项直接映射大页）；其他位的完整定义留在下面的源码索引中，本文不展开与评审主线无关的功能。

系统内存对象的每一页分别填写自己的 DMA 地址。因此，连续的 GPUVA 可以映射到一组分散的系统内存页，不要求整个对象的 DMA 地址连续。

内核的 VMID 0 另有地址窗口和 GART：FB 窗口把一段 MC 地址线性对应到显存；AGP 窗口把一段 MC 地址线性对应到系统总线地址；GART 则通过页表映射分散的内核对象。前两者做线性换算，GART 做分页翻译，作用不要混在一起。在固定基线的 GC 9 路径上，AGP 默认关闭，只有 `amdgpu_agp=1` 时才启用。用户 VMID 通过自己的页表访问系统内存，不依赖 VMID 0 的这些窗口。

### 2.2 本设备：四级页表与固定 Outbound 窗口

本设备同样先按 VMID 找根，GPUVA 有效 48 位，位 63..48 必须为零。四级表的每级索引均占 9 位，各张表都是 512 项、4 KiB；页内偏移占 12 位。仍沿 X 的地址查找：

```text
VMID → L0 根表
  → L0[0x1ff]  GPUVA[47:39]，找到 L1
  → L1[0x1fe]  GPUVA[38:30]，找到 L2
  → L2[0x52]   GPUVA[29:21]，找到 L3
  → L3[0]      GPUVA[20:12]，取得数据页地址和权限
  → 加 GPUVA[11:0]，访问 X[0]
```

这里的索引拆分与前面的 AMD 例子相同，但目录项、叶子项的允许位和物理地址表示仍按本设备协议解释。

叶子项沿用 AMDGPU 的部分位位置：VALID 为 bit 0，SYSTEM 为 bit 1，X/R/W 为 bit 4/5/6，地址字段为 `[31:12]`。沿着 X 和 kernarg 两个对象，可以看清地址字段怎样变成设备最终访问的地址：

```text
X 的第 0 页：PTE = 0x0020_0000 | VALID | R | W = 0x0020_0061
  SYSTEM = 0 → 地址字段是 VRAM 偏移
  → GPU 物理页 0x0020_0000 → 公共物理入口 → VRAM

kernarg 页：PTE = 0x4100_2000 | SYSTEM | VALID | R = 0x4100_2023
  SYSTEM = 1 → 地址字段是 Host IOVA 0x4100_2000
  → 加 Outbound 起点：GPU 物理页 = 0x8000_0000 + 0x4100_2000 = 0xc100_2000
  → 公共物理入口识别为 Outbound，减去 0x8000_0000
  → IOVA 0x4100_2000 → vfio-user DMA → Host 内存
```

SYSTEM 在解释 PTE 时使用；公共物理入口只接收换算后的 GPU 物理地址，再按地址范围选择 VRAM 或 Outbound。因此，Host 页的 PTE 填 `0x4100_2000`，不能把已加窗口起点的 `0xc100_2000` 再填进去。页内偏移在翻译后保留：读取 `X[3]` 的 GPUVA 是 `0x0000_ffff_8a40_000c`，最终访问 VRAM 偏移 `0x0020_000c`。

GPU 物理空间仍为 32 位：`[0, vram_size)` 为 VRAM，`[vram_size, 0x8000_0000)` 为不可路由的空洞，`[0x8000_0000, 0x1_0000_0000)` 为 2 GiB 的 Outbound 窗口。这是**翻译后的地址布局**；GPUVM 开启时，GPUVA 的相同数值并不自动代表 Outbound，仍须先查页表。

页表遍历、CP 管理域访问和 DMA 引擎也走这个公共物理入口，但它们本来就使用 GPU 物理地址，不再按用户 VMID 翻译。具体规则见 [GPUVM 规格第 3.2、3.3 节](<./GPUVM 第一版规格.md#gpuvm-addresses>)。

### 2.3 取舍与代价

**地址宽度。** 库把 CPU 映射地址用作 GPUVA，RV64 寄存器与 8 字节参数项能够保存这个地址，四级页表覆盖 48 位虚拟空间。但 PTE 地址域仍为 `[31:12]`，更宽的 GPUVA 不会扩大物理空间或 Host IOVA 窗口。AMD 的 PDE-as-PTE 和 FRAG 本设备也都没有实现。

**系统内存怎样接入。** AMD 的 SYSTEM PTE 直接保存 DMA 地址，固定基线的 DMA 地址能力是 48 位。本设备只定义了 32 位 GPU 物理空间，并把其中的高 2 GiB 留作 Outbound；PTE 中的 IOVA 因而要先加窗口起点，才能交给公共物理入口。**[INFERENCE]** 只看“线性地址换算”这一功能，它最接近 AMD VMID 0 的 AGP 窗口。但 AMD 的 AGP 只服务内核上下文，且默认关闭；本设备的管理域和用户 SYSTEM 页都依赖 Outbound，不能据此把两种完整访存路径视为相同。

这个布局带来两个限制：

- Host 对象的**完整 DMA 地址区间**必须落在低 2 GiB，驱动因此设置 31 位 DMA mask。DMA mask 限制的是设备能够发出的 DMA 地址。`IOMMU=none` 时，DMA 地址直接对应客体物理地址，超过这个地址范围的内存不能用于分配；启用 SMMUv3 时，限制的是 IOVA，背后的物理页可以位于更高地址。
- 管理域没有 GART，不能把分散的存储页拼成连续的管理地址。每个管理对象必须占一段连续的 GPU 物理地址；Host 对象对应连续 IOVA，不一定对应连续物理页。管理对象也不通过用户页表隔离。

**缓存属性。** 本设备没有模拟 GPU 数据缓存，VRAM 访问直接读写后备存储，Host 访问通过一致性 DMA 内存完成；因此没有 MTYPE、SNOOPED 的选择，也没有需要在完成时回写的 GPU 脏缓存。代价是无法演示 AMD 为显存选择 RW、为普通系统内存选择 UC 的一致性取舍。这里省去的是缓存维护，应用仍须遵守“先准备数据、再发布任务，先确认完成、再读结果”的访问顺序。

**`gpuvm=off` 只用于调试。** 关闭翻译后，用户 Kernel 可以访问 VRAM 首页和固件区以外的全部 VRAM，以及整个 2 GiB 的 IOVA 窗口。例如在 `IOMMU=none` 且客体内存全部位于低 2 GiB 的配置下，窗口内可路由的客体内存也包括 MQD、管理 Ring 和 IH，用户访问没有按会话隔离。AMD 的用户访问仍经过页表，没有本设备这样的用户直通调试模式。

## 3. 地址空间身份：VM、VMID、PASID 与队列绑定

面试可能问：多个进程怎样隔离？VMID 只有 16 个，进程更多时怎么办？

### 3.1 AMD：PASID 是身份，VMID 只是硬件槽位

进程可以长期保留 GPU 内存和页表，硬件却只有有限的翻译上下文。AMD 因而把“地址空间属于谁”和“当前占哪个硬件槽”分开：

- **PASID 是稳定身份。** 在这里讨论的 KFD 进程路径中，它在进程地址空间存续期间保持不变。IH 记录携带 PASID，驱动据此找进程，也能以 PASID 为目标发起 TLB 失效。
- **VMID 是可复用槽位。** 它是硬件上下文寄存器组的下标，该组保存当前页表根和控制状态。每个 hub 有 16 个 VMID，0 留给内核；MI300X 对应的纯计算 GPU 路径中，KFD 从 VMID 3 开始使用。一个进程暂时不占槽位时，软件 VM 和页表仍可保留。

下面先用**非 HWS 模式**说明绑定过程：进程在该设备上的第一条队列创建时，KFD 分配 VMID，建立 PASID 与 VMID 的对应，写页表根并刷新 TLB；最后一条队列销毁时归还编号。没有空闲 VMID 时，这条路径不能仅靠已有页表就让新队列驻留。

**HWS 模式**把驻留调度交给 CP 固件。`MAP_PROCESS` 包携带 PASID、页表根和 SH_MEM（着色器访存环境）配置，固件安排当前驻留进程使用的 VMID。在支持的调度范围内，进程可以轮流驻留，因此进程总数可以多于同时可用的槽位数。不要把这种轮换能力套到非 HWS 路径上。

```text
AMD（非 HWS）
进程 P：PASID 0x8001 → amdgpu_vm（页表根在显存）
  第一条队列创建 → allocate_vmid：取空闲 VMID 9，建立 PASID 0x8001 ↔ VMID 9，写根，刷新 TLB
  MQD.cp_hqd_vmid = 9 → CP 用 VMID 9 访问 Ring、rptr、wptr
  最后一条队列销毁 → 归还 VMID 9；VM 与页表仍在，PASID 不变
```

CP 访问队列时也分两种上下文：读 MQD 使用 `CP_MQD_CONTROL` 中的 VMID（驱动保持为 0），访问用户 Ring 和 rptr/wptr 使用 `CP_HQD_VMID`，也就是队列所属的 VMID。

### 3.2 本设备：VMID 随队列驻留绑定，没有 PASID

本设备以一个 DRM 文件上下文为一个会话，每个会话有一个软件 VM；它不是按进程号全局合并 VM。首次 MAP 成功建立根表时，VM 还不占硬件槽。建队列时驱动才借用用户 VMID 1 或 2，把页表根装入对应上下文，并把编号写入 MQD。队列确认卸载后归还 VMID，软件 VM、页表和已绑定对象继续保留，绑定时机接近 AMD 非 HWS 模式。

CP 必须先读到 MQD，才知道访问用户 Ring 时应使用哪个 VMID，所以它的访存分两条路径：管理域用于 MQD、管理 Ring 和 IH，直接使用 GPU 物理地址；用户域用于用户 Ring、描述对象、Signal 和通知槽，按 MQD 中的 VMID 翻译。每次访问前，CP 在本地窗口中显式设置访问域和 VMID，不根据 `VMID == 0` 猜地址含义。`gpuvm=off` 时仍借用一个用户 VMID 管理队列来源，但不启用页表翻译。

以下流程以 `gpuvm=on` 为例。通知页也走普通 BO 的分配和映射路径，由库在 Open 中准备，不由 `vm_init()` 创建：

```text
DRM 文件 A：VM_A（页表根在 VRAM）
  Open → 库创建、映射并登记 Host 通知页
    首次 MAP → vm_init() 建根表；不取 VMID，不失效
  QUEUE_CREATE → 取 VMID 1 → 写根 → 失效整个 VMID → 启用上下文
  MQD.vmid = 1 → CP 窗口按 VMID 1 访问 Ring
  MAP / UNMAP → 修改对象的叶子项 → 范围失效并确认，队列可以仍驻留
  QUEUE_DESTROY 确认卸载并消费旧 IH
    → 停用上下文 → 失效整个 VMID → 清根 → 归还 VMID 1
  VM_A 与页表仍在；下次建队列时取到的可能是 VMID 2
```

TLB 的标签只有 VMID 和虚拟页号，不知道同一编号前后属于不同 VM。假设 VM_A 和 VM_B 都使用 GPUVA `0x0000_ffff_8a40_0000`，VMID 1 从 A 交给 B 时，旧 TLB 项若还在，B 就可能命中 A 的存储。因此驱动取得和归还编号时都失效整个 VMID；归还前还要消费旧 IH，避免迟到通知被误认成新队列的通知。

MAP、UNMAP 是否发范围失效，取决于 VM 当前是否占有 VMID。占有时，驱动写页表后清除该对象范围的旧翻译并核对 ACK；未占有时只改页表，下次借用 VMID 时统一失效。运行中的任务是否仍在使用被解绑对象，另由对象使用计数和应用寿命约定处理，见[独立说明第 6 节](<./Linux 驱动内存管理.md#memory-unmap>)。

`vm->ready` 表示软件 VM 初始化成功，开启 GPUVM 时已经取得根表；`vm->vmid` 表示当前占哪个槽，0 表示未占用。`ready = true`、`vmid = 0` 是正常状态，不意味着通知页一定已登记或所有对象都已映射。通知页另由 `vm->notify` 指向，EVENT_CREATE 还会检查它已登记、已绑定。

### 3.3 取舍与代价

VMID 在驻留时借用，页表根、TLB 标签、MQD 和故障记录都使用这个编号，驱动不需要维护 PASID 到 VMID 的映射表。剩下的取舍有以下几点：

- **VM 的数量不再受 VMID 限制，同时驻留的队列仍然最多 2 条。** 用户 HQD 槽和用户 VMID 都是 2 个，每个 VM 最多一条队列，两个上限相等，VMID 不会成为额外瓶颈；三个进程轮流建队列的例子见 [GPUVM 规格第 5.1 节](<./GPUVM 第一版规格.md#gpuvm-context-tlb>)。AMD 每个 hub 有 16 个 VMID，HWS 模式下还能由固件轮换，进程数可以远多于槽位。
- **每次建队列、卸载队列都失效整个 VMID。** 队列重新驻留后，TLB 中没有本 VM 的翻译，要重新遍历页表。AMD 重新绑定 VMID 时同样要刷新。本设备的队列通常跑完一批任务才卸载，这部分开销可以忽略。
- **记录中没有独立的稳定地址空间编号。** IH 仍用 MQD 地址定位源队列，驱动能由队列找到会话，所以现有通知路由不受影响。但故障记录中的 VMID 只说明当时用了哪个槽；同一编号会先后属于不同会话，脱离队列和绑定时序就无法判断来源。按地址空间发起失效时，也要先找到它当前借用的槽位。AMD 的 PASID 提供了独立于槽位的身份。
- **GPU 翻译和系统 IOMMU 翻译使用不同上下文。** VMID 选择 GPU 页表；KFD 的 PASID 标识进程地址空间。系统 IOMMU 则按设备请求中的 StreamID 及可选 SubstreamID／PCIe PASID 选择自己的上下文，不能把 GPU VMID 直接当作 IOMMU 的编号。本设备启用 SMMUv3 时，设备共用一个 StreamID，不为各 VM 发送 PCIe PASID：GPU 页表先把 GPUVA 映射到 Host IOVA，SMMUv3 再把 IOVA 映射到客体物理页。[A1](#item-a1) 拟加入的稳定编号也只用于 GPU 侧记录，不自动增加 PCIe PASID 传递能力。

对应改进：[A1 引入 PASID](#item-a1)。

## 5. TLB 与翻译失效

面试可能问：GPU 的 TLB 怎样组织？页表改了以后，怎样保证设备不再使用旧翻译？失效请求和正在进行的访问怎样避免竞争？

### 5.1 AMD：两级翻译缓存，按 PASID 失效

页表已经建立后，Kernel 通常会连续访问同一页或相邻页。如果每次都从根读四级表，翻译成本会很高。AMD 用 UTCL1 和 UTCL2 缓存翻译；下面是按功能画出的查找关系，不表示物理布局：

```text
访存请求：VMID、GPUVA、访问类型
  → 客户端的 UTCL1：命中最终翻译 → 检查权限并访问数据
  → 未命中，查询共享的 UTCL2（VM L2）
      → 命中最终翻译：返回目标页
      → 只有目录信息命中：Walker 从已知的下级表继续查
      → 均未命中：Walker 从页表根开始查
```

UTCL1 靠近各访存客户端，只保存最终翻译；一个 hub 内共享的 UTCL2 还保存 PDE 信息。缓存叶子翻译可以免去整次遍历，缓存中间目录则能在叶子未命中时少读几级表。

FRAG 解决的是“一项翻译覆盖多少地址”。它把连续、属性相同且满足对齐条件的一组 4 KiB 页标成同一片段，片段长度为 `2^(12+FRAG)` 字节，L1 可用一项覆盖整段。例如 FRAG 为 2 时覆盖 16 KiB，而不是只覆盖一页。这种连续片段合并与“目录项直接作为大页叶子”的 PDE-as-PTE 不是同一种编码；本设备目前两者都未实现。

**[BOUNDARY]** MI300X 各级 TLB 的容量、相联度和替换策略没有公开资料。gem5 的 Vega TLB 默认是 64 项全相联、LRU 替换，另有 64 项页遍历缓存；这是模拟器的可配置参数，不能据此推断真机。

失效时要同时考虑“清谁的翻译”和“清哪些层”。硬件 REQ 以 VMID 位图选上下文，并指定刷新类型和缓存种类（L1 PTE、L2 PTE、L2 PDE0/1/2）；ACK 按 VMID 逐位确认。每个 hub 有 18 个失效引擎，驱动可通过相应寄存器发请求。虽然硬件提供地址范围寄存器，固定基线把范围初始化为全范围，本文讨论的路径实际按整个 VMID 刷新。

软件的计算 VM 以 PASID 标识，`amdgpu_vm_flush_compute_tlb()` 先比较页表变更序号 `tlb_seq`：自上次刷新后没有新变化，就跳过；有变化则对各 XCC 按 PASID 请求失效，作用于该地址空间当前绑定的硬件上下文。因此“软件按 PASID 请求”和“硬件清 VMID 的缓存项”是同一过程的两层描述。

KFD 建立映射后会刷新；GC 9.4.2 及以后（包括本文的 9.4.3）解除映射后也执行 heavyweight 刷新。AMD 允许队列存活时修改映射，但仍要求应用不解除任务正在使用的对象。驱动则保证先等写表 fence，再完成 TLB 刷新，最后撤销 DMA 映射和释放存储，不能靠写了新 PTE 就立即回收旧页，详见[解除映射与释放](<./Linux 驱动内存管理.md#memory-unmap>)。

### 5.2 本设备：单级 TLB，按 VPN 范围同步失效

本设备只有一级 TLB，CP 窗口与执行器共用。GPUVA 除以 4 KiB 得到 VPN，再用 `VPN % 64` 选一组；组内有 4 路，每路保存 VMID、VPN、目标物理页和权限。只有 VMID 与 VPN 都相同才算命中，所以相同 GPUVA 的不同 VM 不会互相命中；但它们仍可能竞争同一组的存储位置。

X 的 17 页对应 VPN `0xf_fff8_a400`～`0xf_fff8_a410`，分别落在第 0～16 组。另一会话把对象映射到同一 GPUVA，会使用同样的组，但标签里的 VMID 不同。组内怎样优先使用空路、怎样按 LRU 替换，统一见 [GPUVM 规格第 5.2.1 节](<./GPUVM 第一版规格.md#gpuvm-tlb-lru>)。TLB 只缓存成功的叶子翻译，不缓存失败结果和中间 PDE；命中、未命中、替换三个计数由全设备共用。

设备同时提供**整 VMID 失效**和**VPN 范围失效**。例如要清 VMID 1 中 X 的翻译，先把起止 VPN 分别写入 LO/HI 寄存器对，再提交请求：

```text
VM_INV_VPN_START = 0xf_fff8_a400，VM_INV_VPN_END = 0xf_fff8_a410（首尾都包含）
  → VM_INV_REQ = VMID 1 的位图位（1 << 1，即 0x2）| RANGE
  → 设备检查整个请求 → 清匹配项 → VM_INV_ACK = 0x2 → 寄存器写入处理结束
```

REQ 写的是 VMID **位图**，不是编号 1 本身。不带 RANGE 时忽略 VPN 范围，清所选 VMID 的全部项。REQ 含保留位、位图为空或范围非法时，设备整体拒绝，不清任何项，ACK 只置 ERROR。合法请求在一次寄存器写回调内完成，没有独立的失效 busy 状态；所选 VMID 有激活 HQD 也允许失效。驱动读回的 ACK 必须恰好匹配本次请求位图，才能确认完成。

驱动的 MAP、UNMAP 在 VM 占有编号时实际使用范围失效，保留同一 VM 其他对象的翻译；没有 VMID 时辅助函数直接返回。取得、归还 VMID 时则清整个编号。ROOT/ENABLE 的修改仍检查激活 HQD 和在途访问，不能把“允许运行中失效”理解为“允许运行中换根”。

### 5.3 同步失效为什么成立：模拟器的并发模型

真实硬件上，Walker 可能已经读了旧页表，但还没把结果填进 TLB。如果失效只清除当时已有的项，旧结果随后又填回，就会破坏失效保证。AMD 的刷新类型、ACK 和页表更新／释放顺序共同处理这类并发。本设备没有模拟异步 Walker，失效能在一次寄存器写入内完成，依赖的是当前 QEMU 回调模型。

在双进程配置中，Host 指运行 Linux 驱动的 aarch64 客体；设备、执行器和 RV64 CP 位于另一个 QEMU 进程。BQL 是**设备进程**的主锁，不会阻止客体驱动发消息。关键在于设备收到消息后何时执行回调：

```text
设备进程（持 BQL）                                 Host 侧
vm_translated_rw()：accesses++
  gpgpu_phys_rw() → 发出 vfio-user DMA 请求 ──────▶ 访问客体内存
  等待 DMA 回复                                    驱动写 VM_INV_REQ
  期间收到的 Host 命令只接收、暂存，不执行设备回调
  ◀────────────────────────────── DMA 回复
accesses--，本次用户访问返回
之后处理暂存的 VM_INV_REQ → vm_invalidate()
  此时旧访问已结束，才检查条件、清 TLB、发布 ACK
```

设备等待 DMA 回复时没有释放 BQL，接收函数也不重入设备回调。因此 Host 可以在访问中途发出 REQ，但**设备实际处理 REQ 时**，这次同步访问已经结束，`accesses` 已归零。失效入口用断言检查这一前提，清除后也不会有旧遍历再填回。ACK 确认本次同步失效已经完成；异步 Walker、异步刷新队列及其排空机制不在当前模型范围内。

不过，单次访问结束不代表整个任务结束。Dispatch 按定时器分段推进，两段之间可以处理 Host MMIO；CP 处理一个包也会发起多次窗口访问，期间可以插入 Host 操作。当前允许这些间隙中的页表更新与范围失效，所以同一任务的后续访问可能看到新映射。BQL 只保护一次同步访问与一次失效回调，不为整个 Dispatch 固定一份页表快照。应用必须在 MAP 成功返回后才使用新地址，并在 UNMAP 前确认任务不再访问旧对象；保护细节见独立说明中的[GPU 映射建立](<./Linux 驱动内存管理.md#memory-map>)和[解除映射与释放](<./Linux 驱动内存管理.md#memory-unmap>)。

### 5.4 取舍与代价

- **单级、只缓存叶子。** 组相联加 LRU 足以讲清 TLB 的基本行为。代价是每次未命中都要读四级表，没有 PDE 缓存；也无法演示 AMD 失效时分别选择 L1、L2、PDE 各级的原因。
- **没有 FRAG。** 256 项 × 4 KiB，最多覆盖 1 MiB。AMD 可用 FRAG 让一项覆盖一整段连续内存。
- **组号不含 VMID。** **[INFERENCE]** 两个 VM 的 VPN 模 64 相同时，会竞争同一组。四路没有按 VMID 分配固定份额，一边访问更频繁时可能替换另一边的大多数项。标签保证隔离，不能保证缓存份额；GPUVA 由 CPU mmap 取得，也不保证不同会话会选到不同组。
- **按范围失效。** 设备接口比 AMD 驱动在本文路径中的整 VMID 刷新更细，只清一个对象的范围时可以保留其他对象的翻译。实现仍扫描全部 256 项，只是按 VMID 和 VPN 决定是否清除。
- **同步访问与同步失效。** 当前回调模型无需另外排空异步 Walker，但不跟踪整个 Kernel 的内存依赖。以后增加异步翻译或搬移时，必须重新定义完成保证，不能照搬“写 REQ 后立即读 ACK”的实现前提。
- **计数全设备共用。** 无法区分是哪个 VMID 或哪个访存主体造成的未命中。

对应改进：[A3 TLB 分层](#item-a3)；后续方向：[E2 FRAG 连续片段](#item-e2)。

## 6. 访存故障

面试可能问：GPU 访问一个没有映射的地址会怎样？能像 CPU 缺页那样恢复吗？

### 6.1 AMD：可重试故障与不可恢复故障

Kernel 访问一个地址时，可能是合法页面暂未建立 GPU 映射，也可能是地址本就非法、权限不足，或者翻译与存储访问失败。恢复策略首先取决于故障是否可重试，以及这段地址是否由可恢复的内存管理路径负责：

```text
访存 → UTCL2 / Walker 检测故障 → IH 报告地址、访问类型、VMID、PASID
  ├─ 可重试且属于可恢复的 SVM 范围 → 检查 VMA / 权限 → 恢复映射 → 重试访问
  └─ 不可恢复 → KFD 停止进程队列 → 内存异常事件 → 运行时处理
```

IH 记录带故障页地址、是否可重试和是否为写等信息。驱动还读取 `VM_L2_PROTECTION_FAULT_STATUS`，进一步判断客户端编号（CID）、读写方向（RW）、页表遍历错误（WALKER_ERROR）、权限错误（PERMISSION_FAULTS）、映射错误（MAPPING_ERROR），以及是否还有后续故障（MORE_FAULTS）。这些字段用于定位哪次访问在哪个环节失败。

- **可重试故障**：在可恢复 SVM 路径中，硬件保留待重试访问，驱动经 `amdgpu_vm_handle_fault()` 进入 `svm_range_restore_pages()`，检查 CPU VMA 和权限，必要时迁移页面、补好 PTE，然后让访问重试。只有恢复成功，Kernel 才能继续；任意未映射地址不会因此自动变成合法内存。固定基线的 9.4.3 默认 `noretry=1`，需要用参数打开重试，这里描述的是具备相应配置时的恢复路径。
- **不可恢复故障**：没有被调试器接管时，KFD 驱逐这个进程在该设备上的全部队列，再发内存异常事件。ROCr 的 `VMFaultHandler` 如果也没有自定义处理器接管，最终调用 `abort()` 终止进程。

### 6.2 本设备：只检测、记录和停止

本设备没有补页或重试路径。假设 X 跨页，Kernel 已读完前一页，访问下一页时找不到有效 PTE：

```text
执行器访问 X 的下一页 → GPUVM 记录 UNMAPPED 故障
  → Dispatch 失败 → CP 停止源队列、提交 IH 队列错误记录
  → 驱动把故障保存到队列对象，并使该队列仍为 PENDING 的事件失败
  → 应用等待返回错误，再查询故障地址、访问类型和阶段
```

此前已经写入 Z 的部分保留，失败不会回滚，也不会重放整个 Dispatch。CP 取包、读描述对象或写完成对象发生访存错误时，同样按源队列错误处理。

### 6.3 取舍与代价

- **为什么不恢复。** 对象在创建时取得存储，应用须在第一次访问前完成映射，因此本设备没有“合法访问缺少驻留页，需要现场补页”的需求。未映射或权限故障通常应检查应用的地址与权限；TABLE、STORAGE 还可能来自驱动、页表或访存通道，不能把所有故障都归咎于应用。当前统一停止并报告。若以后引入按需驻留，执行器还要能停在故障指令并重试，驱动也要负责恢复存储和映射，见 [E4](#item-e4)。
- **停止范围。** AMD 在普通路径上停掉进程在该设备上的全部队列，本设备只停源队列。目前每个会话 VM 只有一条队列，停源队列也就停止了该 VM 的队列访问；但若同一进程直接打开多个 DRM 会话，其他会话不会因此一并停止。以后允许一个 VM 有多条队列时，应同时考虑同一 VM 的其他队列。
- **记录方式。** 本设备每槽只留首次故障，后续故障丢失；AMD 的 IH 记录逐条上报，状态寄存器另有 MORE_FAULTS 标记。教学上首次故障已经足够定位问题。

## 7. 完成通知与事件等待

面试可能问：Kernel 执行完以后，Host 怎样得知？等待的线程怎样避免错过唤醒？

### 7.1 AMD：自动复位事件与 `event_age`

这里有两个不同对象：**Signal 保存应用要等待的数值，事件负责让等待线程睡眠和唤醒**。中断只告诉线程“条件可能变化了”，线程醒来还要复查 Signal，不能把一次唤醒直接当作当前任务成功。

```text
AQL 包完成 → release，保证先前结果按要求发布 → 原子递减 Signal
  → mailbox 非空时：写事件槽、产生中断
  → KFD 按 PASID 找进程、按事件编号找事件 → 唤醒等待者
  → ROCr 复查 Signal 是否满足本次等待条件
```

`amd_signal_t` 为 64 字节、64 字节对齐：偏移 8 是信号值，偏移 16 是 `event_mailbox_ptr`，偏移 24 是 `event_id`。KFD 为每个进程提供 4,096 个 8 字节事件槽，共 32 KiB；中断记录里的事件编号可能只有部分位，能唯一定位时直接查找，否则扫描已写入的槽。

ROCr 创建信号事件时传 `manual_reset=false`，选择自动复位：通知到达时若已有等待者，就唤醒它们并恢复为未置位；若通知先到、线程后等，等待调用会消费已有置位状态。这样旧通知不会永远留下一个“立即成功”的事件。

`event_age` 进一步记录“发生过几次通知”：每次置位递增，等待者可带上次看到的 age。若准备睡眠期间通知已经发生，age 已改变，等待就立即返回，不必等下一次中断。自动复位处理通知的消费，age 识别两次等待之间的新通知；配合唤醒后复查 Signal，同一个事件才能服务多次派发。

### 7.2 本设备：一次性事件

本设备的 Signal 为 24 字节。应用在发布任务前准备值 1；任务完成后由 CP 单独把值写成 0，不存在多个完成方竞争递减同一个值。库在 Open 时创建一页 Host 通知 BO，并完成 CPU 映射、GPU 绑定和驱动登记；开启 GPUVM 时，它使用库取得的 CPU 地址作为 GPUVA。通知页提供 512 个 8 字节槽，EVENT_CREATE 只从已登记、已绑定的页中分配槽位，返回“通知页 GPU 地址 + 槽号 × 8”，不新建页表映射。

CP 的完成步骤与驱动消费通知是先后两个阶段：

```text
CP：结果已写回 → Signal = 0 → 通知槽写事件编号 → IH 写 SIGNAL_NOTIFY
      → 包头改回 INVALID → 回报消费进度

驱动：消费 IH → 按 MQD 地址找到队列 → 核对事件编号和通知槽
        → PENDING 事件变为 NOTIFIED → 唤醒等待线程
```

IH 记录还带类型和 HQD 槽。MQD 地址用来找源队列，事件编号和通知槽再用来确认应唤醒谁；不是只看一个“完成中断”就唤醒所有事件。Signal 归零早于驱动处理 IH，因此线程可能已经观察到结果完成，而事件仍是 PENDING，队列消费进度也尚未回报。

事件只允许 `PENDING → NOTIFIED` 或 `PENDING → FAILED`，等待不会消费状态。一次事件结束后，后来的等待也会立即看到同一个结果，这适合一次完成对应多个等待者，但没有自动复位语义。完整规则见 [GPUVM 规格第 6.1 节](<./GPUVM 第一版规格.md#gpuvm-signal>)。

### 7.3 差异与代价

当前运行时每次派发创建一个新事件，顺序与一次性协议一致：

```text
本次派发：建事件 → 把事件编号和通知槽地址写入 Signal → 发布任务
  → 等待 Signal；需要睡眠时等待本次事件，醒来继续复查 Signal
  → Signal 已为 0，尝试销毁事件
      已通知：释放事件和槽
      IH 尚未消费、仍不可销毁：登记为待回收，之后再试，不忙等
下一次派发：使用另一个新事件；旧通知仍由旧事件接收
```

Signal 归零早于驱动消费 IH，所以运行时确认计算成功后，事件仍可能等待回收。驱动拒绝销毁仍可能被 CP 或旧 IH 引用的事件，运行时将其留待后续回收；销毁整个运行时时，先卸载队列，再处理剩余事件。提交或等待失败后，运行时保留本次事件与对象并拒绝再次派发，避免覆盖设备可能仍在使用的参数和 Signal。

## 8. Kernel 启动状态

面试可能问：GPU 线程启动时，怎样知道自己的编号、工作组大小和参数地址？

向量加法的 Kernel 除了取得 X、Y、Z 的地址，还要计算自己负责的元素编号：`i = 工作组编号 × 每组线程数 + 组内线程编号`。数组地址和 N 放在 kernarg 中，线程坐标与执行规模则来自启动状态。两侧都在真正执行第一条指令前准备这些信息，但交给 Kernel 的接口不同：

```text
Host 准备：Dispatch 包（执行规模、描述对象地址、kernarg 地址）
  → CP 读描述对象，取得代码入口和资源要求
  → 启动 Wave / Warp，初始化线程可读取的状态
      AMD：VGPR 保存组内坐标，SGPR 保存启用的用户数据和工作组信息
      本设备：只读 CSR 提供坐标和规模，a0 保存 kernarg 的 GPU 地址
  → Kernel 算出 i → 从 kernarg 取得数组地址与 N → 检查 i < N → 读写数组
```

**AMD。** 启动状态有几个来源，需要分开看：

- VGPR 是每个 Lane 各自的向量寄存器。硬件在 VGPR0 中按 `{2'b00, Z[9:0], Y[9:0], X[9:0]}` 打包组内坐标，不同线程取得不同的 X、Y、Z。
- SGPR 是一个 Wave 内共享的标量寄存器。开头最多装入 16 个 user data SGPR，是否包含 kernarg 指针、dispatch packet 指针等由描述符使能位决定；随后按配置装入启用的 workgroup ID 分量和工作组信息。不能假设所有 Kernel 都在固定 SGPR 位置取得同一组字段。
- 描述符和运行时 ABI 还决定怎样取得完整执行规模。Kernel 可通过启用的 dispatch packet 指针读取 Grid、工作组尺寸；运行时也按 Kernel 元数据在显式参数之后填写相应隐藏参数。规范的启动表另列出 TTMP6/7 中的 dispatch packet 地址、TTMP8～10 中的 Grid 三维尺寸，属于陷阱临时寄存器状态，不应与 user data SGPR 的布局混为一谈。

AMD Kernel 描述符为 64 字节，既包含工作组共享段、私有段和参数块长度，也包含相对描述符的代码入口偏移及 `compute_pgm_rsrc1/2/3` 等资源配置。CP 依据它准备执行资源和启动寄存器；描述符并非只保存代码地址。偏移 `0x0c` 在这个布局中是保留字段。

创建新 Warp 时，执行器保存一份 Warp 共享的 Block 编号、Block 尺寸和 Grid 中的 Block 数，并为各 Lane 保存组内坐标。Kernel 经只读 CSR `0xCC0`～`0xCCB` 读取这些值；普通通用寄存器被覆盖不会改变 CSR 返回的启动信息。同一个 Warp 分段继续时保留状态，切换到新 Warp 才重新初始化。

```text

用 LD 读取 a0 指向的 kernarg：四项各占 8 字节，依次为 X、Y、Z 的 GPU 地址和 N = 17,003
  → i < N，处理 Z[17,002]
组内下一个线程的 i = 17,003 → 不满足 i < N，直接结束
```

每个 Warp 为 32 Lane，所以一个 64 线程 Block 分两次 Warp 执行；不能把 Block、Warp 和单线程坐标当作同一个编号。CSR 的完整分组和字段规则只在 [CP/MEC 规格第 6.2 节](<./CP_MEC 第一版规格.md#spec-kernel-descriptor>) 维护。

### 9.2 设计升级草案

<a id="item-a1"></a>

**A1：加入稳定的地址空间标识（P2）。** VMID 的驻留关系、现有 MQD 通知路由与 AMD 对照见[第 3 节](#review-identity)。这里待决定的是是否让诊断记录具有独立于驻留槽位的身份。

**[DESIGN]** 草案为每个会话 VM 分配一个稳定的 16 位教学 PASID：

```text
会话 A 创建 VM_A → 保存 PASID 0x8001
  → 第一次建队列：借到 VMID 1，MQD 携带 PASID 与 VMID
  → CP 报告 IH / 故障：记录 PASID 0x8001
  → 卸载队列：归还 VMID 1，VM_A 和 PASID 保留
  → 再次建队列：可能借到 VMID 2，记录仍指向 PASID 0x8001
  → VM_A 安全拆除，相关旧通知不再引用它后，才可复用 PASID
```

本设备按 DRM 会话建立 VM，并不按进程号合并多次打开的会话；这个方案保持该关系不变。它借鉴 PASID 的稳定身份作用，不把会话编号宣称为完整的 AMD 进程身份协议。

建议只把稳定编号加入 MQD、IH 与故障诊断，并保留按 MQD 地址路由通知的方式。按地址空间发起失效时，软件仍须找到该 VM 当前占用的 VMID；不同时增加驻留调度或 VMID 超额轮换。

这个教学编号不随 PCIe DMA 请求发送，不改变系统 IOMMU 的上下文选择，也不赋予 SMMUv3 逐进程 PASID 翻译能力。

MQD 与 IH 的保留字段目前必须为零，加入编号需要一起修改字段定义、生成与校验，并升级协议，不能只在驱动里填一个新值。

**A3：TLB 分层与目录缓存（P2）。** 当前单级查找与 AMD 的分层关系见[第 5 节](#review-tlb)。本方案只借鉴分层与失效依赖，不模拟 MI300X 的真实容量或时延。

**[DESIGN]** 暂取每个客户端 L1 为 8 项全相联、共享 PDE 缓存为 16 项，均为可调整的教学参数；现有 TLB 用作共享 L2：

```text
gpgpu_user_rw(访问主体、VMID、GPUVA)
  访问主体：CP 窗口 / 执行器取指 / 执行器数据
  → 对应主体的 L1：标签 VMID + VPN
      命中 → 返回物理页和权限
      未命中 → 共享 L2（沿用现有 64 组 × 4 路）
        命中 → 返回并填 L1
        未命中 → PDE 缓存：标签 VMID + GPUVA[47:21]
          命中 → 取得 L3 叶表地址，只读本次的叶子 PTE
          未命中 → 从 L0 读完四级表，填目录缓存与叶子翻译缓存
  → 检查本次访问权限 → 访问目标数据
```

这里的“L2 TLB”是翻译缓存，“L2 表页”是四级页表中的倒数第二级目录，最终叶表为 L3。PDE 缓存保存找到 L3 的结果，一项覆盖一个 2 MiB 的 GPUVA 区段。用完整的 `GPUVA[47:21]` 作标签，才能区分高位不同的区段。

例如 X 的相邻两页都落在同一个 2 MiB 区段：第二页的最终翻译即使未命中，也可从缓存的 L3 基址直接读取叶子项，省去 L0、L1、L2 三次目录读取。

**失效与计数。**

目录缓存一旦存在，叶子 TLB 已清除也不能直接释放目录页：缓存中还可能保存该页的旧地址。草案让现有请求一次覆盖所有新增缓存：

```text
VM_INV_REQ
  → 按 VMID 和 VPN 范围清各客户端 L1、共享 L2
  → 清所选 VMID 的全部 PDE 缓存
  → 完成以上动作后才发布 ACK

ROOT / ENABLE 改变
  → 清该 VMID 的目录缓存；取得、归还 VMID 的整 VMID 失效流程保留
```

PDE 缓存只保存有效路径，不缓存失败遍历。现阶段空表保留到会话清理；以后若增加空表回收，必须先清父 PDE、完成相应缓存失效，再归还表页，不能让目录缓存指向已复用的存储。

`gpgpu_user_rw()` 需要增加“访问主体”参数，由 CP 窗口、执行器取指和数据访问分别选择对应 L1。现有三个 TLB 计数继续描述共享 L2，新增 L1 命中与目录命中统计。L1 命中时不会再访问 L2，所以原测试的具体计数不能原样套用。新增寄存器的位置须按当前硬件手册安排，不能从 `0x092c` 连续向后分配，因为 `0x0930～0x093c` 已用于 VPN 范围寄存器。对外统计与寄存器语义变化需要升级协议。

**可复用事件：自动复位与通知代次（P2）。** 当前每次派发使用独立的一次性事件；对象关系和 AMD 自动复位对照见[第 7 节](#review-event)。这里待决定的是是否通过事件复用降低逐次创建、销毁的开销。

**[DESIGN]** 若需要复用，建议由驱动维护通知代次，而不是由应用把 NOTIFIED 强行改回 PENDING。以等待者上次看到 `age=7` 为例：

```text
应用准备本次 Signal 并提交任务

等待者带入 last_age=7
  → 当前 age 已为 8：直接返回，避免漏掉睡眠前到达的通知
  → 当前 age 仍为 7：登记等待，与通知更新同步
  → 返回后复查 Signal，再决定本次任务是否完成
```

还需明确通知消费、多个等待者、迟到通知、代次回绕和事件销毁的规则。队列故障必须使相关等待以错误结束，不能被旧通知状态遮住；事件可复用也不代表超时后可以覆盖仍被任务访问的参数或 Signal。

这需要修改事件 UAPI、驱动和用户库并升级协议。待确认的是是否承担这项扩展，还是继续使用一次性事件。现有方案可继续运行，不以此为第四阶段的前置条件。

<a id="item-e"></a>

### 9.3 后续方向

本节保留尚未展开成完整规格的方向，不预先固定全部接口或验收矩阵。阶段依赖见[实验大纲](<./QEMU GPGPU 实验大纲.md>)；下面只写每项仍需决定的范围。

<a id="item-e1"></a>

**E1：GPU 物理地址与 PTE 地址字段扩宽（P3）。**

当前 GPUVA 已是 48 位，但 GPU 物理空间仍是 32 位，Host IOVA 仍受低 2 GiB Outbound 窗口限制。两种位宽约束作用于翻译的不同阶段：

```text
48 位 GPUVA → 四级页表
  SYSTEM = 0：PTE 地址域给出 VRAM 偏移
  SYSTEM = 1：PTE 地址域给出低 2 GiB IOVA
              → 加 0x8000_0000 → 公共物理入口 → Host DMA
```

**[DESIGN]** 草案把 PTE 地址域扩到 `[47:12]`，将 SYSTEM 页的完整 DMA 地址交给 Host 访问后端，不再加固定 Outbound 起点来转换成 32 位 GPU 物理地址。Host 路由、管理地址表示和 DMA mask 随之修改，GPUVA 沿用现有 48 位。

待确认的是是否需要解除物理地址与 Outbound 限制。若采用，必须一起规定 VRAM 和 Host 地址的路由方式，涉及公共物理入口和各层协议，不能只扩大 PTE 掩码。

<a id="item-e2"></a>

**E2：用 FRAG 合并连续页的翻译（P3）。**

当前一项 TLB 翻译只覆盖一页。FRAG 的方向是把物理连续、属性相同、满足对齐的多个 4 KiB 页合成一个翻译片段；它不等同于让 PDE 直接充当大页叶子。

**[DESIGN]** 例如选取 16 KiB 片段时，过程为：

```text
四个连续的 4 KiB 页，GPUVA 与物理起点均按 16 KiB 对齐
  → 驱动核对地址连续、权限与 SYSTEM 一致，填写片段信息
  → Walker 读取该信息，TLB 保存起点与覆盖长度
  → 后续访问片段内任一页，按偏移求目标地址
  → 失效范围与片段相交时，清除整个相关缓存项
```

待确认的是是否先只实现连续片段合并，并继续不做 PDE 大页。当前 PTE 的 bit 7～11 保留，使用这些位需要同步修改表项校验、TLB 匹配与失效规则。对象分配长度可能不是片段长度的整数倍，仍须逐段核对连续性、属性和对齐。

<a id="item-e3"></a>

**E3：TTM 驱逐与存储迁移（P3）。**

应用仍持有 X 的 BO 和 GPUVA，但显存紧张时，希望把内容换到另一份存储。迁移必须让对象身份保持不变，同时阻止任务继续访问旧页：

```text
停止对 X 旧存储的访问并确认停止
  → 分配新存储、搬移内容
  → 更新 X 的 PTE、失效旧翻译并确认
  → 归还旧存储、恢复队列访问
```

AMDGPU 的 TTM 与进程级 eviction fence 如何配合，见独立说明中的[存储分配](<./Linux 驱动内存管理.md#memory-storage>)和[解除映射与释放](<./Linux 驱动内存管理.md#memory-unmap>)。这里需要先有停止与恢复协议，不能仅增加一个分配器就开始搬移仍被任务访问的存储。

待确认的是是否继续推进可移动存储，以及首期只做什么迁移。保持正在运行的任务可继续执行，需要 E5 中的可恢复暂停能力；仅有“复位并终止旧任务”还不能实现这种迁移。范围归[大纲的 GPUVM 扩展](<./QEMU GPGPU 实验大纲.md#gpuvm-advanced-extension>)。

<a id="item-e4"></a>

**E4：可恢复缺页（P3）。**

当前访存失败会结束 Dispatch，详细错误规则见 [GPUVM 规格第 6 节](<./GPUVM 第一版规格.md#gpuvm-signal>)。补页后重试则需要保留失败指令的执行状态：

```text
Kernel 访问合法但尚未驻留的页
  → 保留故障指令与线程状态，报告地址和访问类型
  → 驱动检查地址合法性，准备存储并补映射，确认失效完成
  → 只重试失败访问，之后继续 Kernel
```

不能重放整个 Dispatch 来模拟重试，否则故障前已完成的写入可能重复发生。AMD 的 SVM 恢复路径会检查 CPU VMA 与权限、准备页面并重建映射；也不是任意非法地址都能补页。固定 Linux 基线中 GC 9.4.3 默认 `noretry=1`，这里只对照启用重试且地址由可恢复路径管理时的流程。

待确认的是是否引入按需驻留，以及先支持哪些可恢复故障。执行器重试、存储后备和驱动恢复必须一起设计，不能只增加故障原因码。

<a id="item-e5"></a>

**E5：强制中止、复位恢复与可恢复暂停（P3）。**

当前尚未解决的是“设备操作结果未知后，怎样确认旧访问停止并恢复可用”，而不是收到明确失败后的普通收尾。一次 COPY 超时会使设备进入全局 `dma_uncertain`；后续 COPY、解绑和会话清理受限。文件已关闭但仍不能安全回收的会话保留为 orphan，当前由设备移除时的停机路径处理。

**[DESIGN]** 第四阶段可以先围绕终止旧任务、恢复设备接收新任务来界定范围：

```text
等待超时或设备故障
  → 阻止新提交，保留旧访问可能涉及的对象、页表和管理结果区
  → 执行选定的停止或复位动作
  → 确认旧 DMA、CP、执行器访问及旧通知均已结束
  → 旧任务以失败结束，解除相应资源保留
  → 重建必要上下文，允许新任务计算
```

“暂停后继续旧任务”是另一项能力，需要保存、恢复执行状态，不能与上述终止路径共用一个含糊的“恢复成功”结果。建议先确定终止与复位的最小范围，再决定是否纳入可恢复暂停；后者是运行中迁移和抢占调度的重要前提。
